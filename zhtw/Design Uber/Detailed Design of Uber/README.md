## Components (組件)
讓我們詳細討論我們 Uber 系統設計的組件。

### Location manager (位置管理器)
乘客和司機連接到位置管理器服務。當乘客打開應用程式時，此服務向乘客顯示附近的司機。此服務還每四秒接收一次來自司機的位置更新。然後將司機的位置傳達給四叉樹地圖服務，以確定司機在地圖上屬於哪個段。位置管理器將所有司機的最後位置保存在資料庫中，並保存司機在行程中遵循的路線。

### Quadtree map service (四叉樹地圖服務)
四叉樹地圖服務更新司機的位置。主要問題是我們如何有效地處理尋找附近司機的問題。

我們將根據我們的需求修改 Yelp 章節中討論的解決方案。我們在 Yelp 上使用四叉樹來查找位置。四叉樹有助於將地圖劃分為段。如果司機數量超過一定限制，例如 500，那麼我們將該段拆分為四個子節點，並將司機分配到其中。

四叉樹中的每個葉節點都包含無法進一步劃分的段。我們可以使用相同的四叉樹來查找司機。我們現在最大的區別是我們的四叉樹設計沒有考慮定期升級。所以，我們的動態段解決方案有以下問題。

我們必須更新我們的資料結構，以指出所有活躍司機每四秒更新一次位置。每當司機的位置發生變化時，修改四叉樹需要更長的時間。為了識別司機的新位置，我們必須首先根據司機的先前位置找到一個合適的網格。如果新位置與當前網格不匹配，我們應該將司機從當前網格中移除並將其轉移到正確的網格。如果新網格超過司機限制 (即我們最初設置的每個區域的司機數量)，我們必須重新分區。此外，我們的平台必須在行程進行時告知司機和乘客汽車的當前位置。

為了克服上述問題，我們可以使用雜湊表來儲存司機的最新位置，並偶爾更新我們的四叉樹，比如說在 10-15 秒後。我們可以在大約每 15 秒而不是 4 秒更新四叉樹中司機的位置，我們使用一個雜湊表，每 4 秒更新一次並反映司機的最新位置。通過這樣做，我們使用更少的資源和時間。

```
四叉樹是一種樹狀資料結構，其中每個內部節點恰好有四個子節點。四叉樹是八叉樹的二維模擬，最常用於通過遞歸地將二維空間細分為四個象限或區域來對其進行分區。與葉單元相關聯的資料因應用程式而異，但葉單元代表“有趣的空間資訊單位”。來源：維基百科
```

### Request vehicle (請求車輛)
乘客聯繫請求車輛服務以請求乘車。乘客在此處新增下車地點。然後請求車輛服務與尋找司機服務通訊以預訂車輛，並使用位置管理器服務獲取車輛的詳細資訊。

### Find driver (尋找司機)
尋找司機服務找到可以完成行程的司機。它將所選司機的資訊和行程資訊發送回請求車輛服務，以將詳細資訊傳達給乘客。尋找司機服務還聯繫行程管理器來管理行程資訊。

### Trip manager (行程管理器)
行程管理器服務管理所有與行程相關的任務。它在資料庫中創建一個行程，並將行程的所有資訊儲存在資料庫中。

### ETA service (ETA 服務)
ETA 服務處理預計到達時間。它在安排行程時向乘客顯示接載 ETA。此服務考慮路線和交通等因素。在道路網路上給定起點和終點預測 ETA 的兩個基本組件如下：

- 計算從起點到終點的最短路線。
-計算行駛該路線所需的時間。
整個道路網路表示為圖。交叉路口由節點表示，而邊緣表示路段。該圖還描繪了單行道、轉彎限制和速度限制。

[圖表示](./presentation.jpg)

為了識別源和目的地之間的最短路徑，我們可以利用諸如 Dijkstra 演算法之類的路由演算法。然而，Dijkstra 或任何其他在未處理圖之上運行的演算法對於此類系統來說都相當慢。因此，這種方法在這些網約車平台運行的規模上是不切實際的。

為了解決這些問題，我們可以將整個圖拆分為分區。我們使用收縮層次結構預處理分區內的最佳路徑，並僅處理分區邊界。這種策略可以顯著降低時間複雜度，因為它將圖劃分為彼此很大程度上獨立的微小單元層。必要時，預處理階段在分區中並行執行以提高速度。在下圖中，所有分區並行處理最佳路線。例如，如果每個分區花費一秒鐘來找到路徑，我們可以在一秒鐘內獲得完整路徑，因為所有分區都並行工作。

```
收縮層次結構是一種加速方法，經過優化以利用表示道路網路的圖的屬性。加速是通過在預處理階段創建捷徑來實現的，然後在最短路徑查詢期間使用這些捷徑來跳過不重要的頂點。來源：維基百科
```

[劃分圖](./partitions.jpg)

一旦確定了最佳路線，我們會計算行駛路段的預期時間，同時考慮交通情況。交通資料將是節點之間的邊緣權重。

我們使用名為 DeepETA 的機器學習組件來立即改進生產中的指標。它建立了一個可以重複用於多個消費者用例的模型基礎。

我們還使用一個路由引擎，該引擎使用實時交通資訊和地圖資料來預測遍歷源和目的地之間最佳路徑的 ETA。我們使用後處理 ML 模型，該模型考慮空間和時間參數，例如源、目的地、請求時間和關於實時交通的知識，以預測 ETA 殘差。

### Database (資料庫)
讓我們根據我們的需求選擇資料庫：

資料庫必須能夠水平擴展。定期有新客戶和司機，因此我們應該能夠毫無問題地新增更多儲存空間。
資料庫應該處理大量的讀取和寫入，因為司機的位置每四秒更新一次。
我們的系統應該永遠不會停機。
我們已經在資料庫章節中討論了各種類型的資料庫及其規格。因此，根據我們的理解和需求 (高可用性、高可擴展性和容錯性)，我們可以使用 Cassandra 來儲存司機的最後已知位置和行程完成後的行程資訊，並且不會對其進行更新。

我們可以使用 MySQL 資料庫來儲存正在進行的行程資訊。我們將 MySQL 用於正在進行的行程以進行頻繁更新，因為行程資訊是關係型的，並且需要在表之間保持一致。我們使用 Cassandra 是因為我們儲存的資料量巨大且不斷增加。

```
Cassandra 是一個列式資料庫，這是一種 NoSQL 資料庫，旨在處理許多商品伺服器上的大量資料，提供高可用性且無單點故障。來源：維基百科
```

```
注意：最近，Uber 將其資料儲存遷移到 Google Cloud Spanner。它提供全局事務、強一致性讀取以及自動多站點複製和故障轉移功能。
```

Question 1
為什麼我們不只使用 MySQL 資料庫？

Answer
隨著時間的推移，資料變得巨大，它會降低我們系統的效能。此外，擴展 MySQL 資料庫並不容易。
```

```
Question 2
為什麼我們不只使用 Cassandra 資料庫？

Answer
我們為每次行程儲存的資料具有高度關係性，它分佈在多個表中，並且必須在所有表中相同。MySQL 有助於儲存此關係資料並保持表之間的一致性。

#### Storage schema (儲存模式)
在 Uber 應用程式的基本層次上，我們需要以下表：

- **Riders (乘客)**：我們儲存乘客的相關資訊，如 ID、姓名、電子郵件、照片、電話號碼等。

- **Drivers (司機)**：我們儲存司機的相關資訊，如 ID、姓名、電子郵件、照片、電話號碼、車輛名稱、車輛類型等。

- **Driver_location (司機位置)**：我們儲存司機的最後已知位置。

- **Trips (行程)**：我們儲存行程的相關資訊，如行程 ID、乘客 ID、司機 ID、狀態、ETA、車輛位置等。

### Fault tolerance (容錯性)
為了可用性，我們需要擁有資料庫的副本。我們使用主從複製模型。我們有一個主資料庫和幾個輔助資料庫。我們從主資料庫到輔助資料庫同步複製資料。每當我們的主資料庫停機時，我們可以使用輔助資料庫作為主資料庫。

```
Question
我們將如何處理司機緩慢且斷開連接的網路？

Answer
我們可以使用司機的手機作為本地儲存，並在那裡每隔幾秒鐘保存一次行程狀態。所有請求和最後記錄的狀態都存儲在本地磁碟上，這確保即使應用程式重新啟動也能保留它們。假設司機在有幾個請求等待與伺服器同步時退出應用程式。重新啟動時從本地磁碟加載請求和最後已知狀態。當司機重新啟動應用程式時，他們仍處於與以前相同的情況。請求排隊以使伺服器保持最新狀態。
```

### Load balancers (負載平衡器)
我們在客戶端 (司機和乘客) 和應用程式伺服器之間使用負載平衡器，以在伺服器之間均勻分發負載。請求被路由到提供所請求服務的指定伺服器。

### Cache (快取)
一百萬司機需要每四秒發送一次更新的位置。一百萬個對四叉樹服務的請求會影響其工作效率。為此，我們首先將更新的位置儲存在 Redis 中儲存的雜湊表中。最終，這些值每 10-15 秒複製到持久儲存中。
