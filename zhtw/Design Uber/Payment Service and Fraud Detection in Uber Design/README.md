# Payment Service and Fraud Detection in Uber Design (Uber 設計中的支付服務和欺詐檢測)
本課的目標是強調針對惡意活動保護系統的必要性。我們將討論支付背景下的欺詐活動。我們將首先簡要介紹支付系統的工作原理，然後我們將介紹如何保護我們的系統免受惡意活動的侵害。

支付服務處理 Uber 應用程式的支付方面。它包括從乘客那裡收取款項以將其交給司機。隨著行程的完成，它收集行程資訊，計算行程費用，並啟動支付流程。

## Major functionality (主要功能)
Uber 支付平台包括以下功能：

- **New payment options (新的支付選項)**：它為使用者新增了新的支付選項。
- **Authorization (授權)**：它授權交易的付款。
- **Refund (退款)**：它退還之前授權的付款。
- **Charging (收費)**：它將資金從使用者帳戶轉移到 Uber。

```
在支付服務中，授權是驗證支付方式的過程——例如，某張信用卡是否有效。
```

## What to prevent (如何預防)
我們需要預防以下情況以確保支付系統的成功：

- **Lack of payment (缺乏支付)**
- **Duplicate payments (重覆支付)**
- **Incorrect payment (不正確的支付)**
- **Incorrect currency conversion (不正確的貨幣轉換)**
- **Dangling authorization (未解決的授權)**

Uber 支付平台基於複式記賬法。

```
複式記賬，也稱為複式會計，是一種記賬方法，依靠雙面會計分錄來維護財務資訊。對一個帳戶的每項分錄都需要對另一個帳戶進行相應且相反的分錄。來源：維基百科
```

## Design (設計)
讓我們看看 Uber 支付平台的設計，並了解不同組件如何協同工作以完成交易：

[Uber 的支付平台](./payment_platform.jpg)

支付服務中使用的關鍵組件如下：

- **API**：Uber API 用於訪問支付服務。
- **Order store (訂單存儲)**：這存儲所有訂單。訂單收集付款並包含有關不同乘客和司機之間資金流動的資訊。
- **Account store (帳戶存儲)**：這存儲乘客和司機的所有帳戶。
- **Risk engine (風險引擎)**：風險引擎分析從特定乘客收取款項所涉及的不同風險。它檢查乘客的歷史記錄——例如，乘客的評分、乘客帳戶中是否有足夠的資金、任何未決費用、乘客是否頻繁取消行程等。
- **Payment profile service (支付配置文件服務)**：這提供有關支付機制的資訊，例如信用卡和借記卡。
- **User profile service (使用者配置文件服務)**：這提供有關使用者支付的資訊。
- **Payment authorization service (支付授權服務)**：這提供支付認證服務。
- **PSP gateways (PSP 網關)**：這與支付服務提供商連接。

### Workflow (工作流程)
以下步驟顯示了支付服務的工作流程：

1. 當乘客請求乘車時，Uber 應用程式使用 Uber API 請求風險引擎檢查涉及的風險。
2. 風險引擎從使用者配置文件服務獲取使用者資訊並評估涉及的風險。
3. 如果風險很高，則不接受乘客的請求。
4. 如果風險較低，風險引擎會創建一個授權令牌並將其發送到支付配置文件服務 (用於記錄保存)，該服務獲取該令牌並將其發送到支付授權服務。
5. 支付授權服務將該請求發送到 PSP 網關，PSP 網關聯繫服務提供商進行授權。
6. PSP 網關將授權令牌發送回支付授權服務，該服務將令牌發送回 Uber 應用程式，表明行程請求已獲批准。
7. 行程完成後，Uber 應用程式使用 API 將帶有授權資料的支付請求發送到 PSP 網關。
8. PSP 網關聯繫服務提供商並通過 API 將狀態發送回 Uber 應用程式。

Uber 支付服務由一組微服務構成，這些微服務作為流處理架構組合在一起。

Kafka 是一個開源流處理軟體平台。它是支付服務中使用的主要技術。讓我們看看 Kafka 如何幫助處理訂單：

```
流處理是一種計算機程式設計範式，通過限制可以執行的並行計算來簡化並行軟體和硬體。給定一系列資料 (流)，一系列操作 (核心函數) 將應用於流中的每個元素。來源：維基百科
```

[使用 Kafka 的支付服務](./payment_service.jpg)

訂單創建者獲取業務事件——例如，行程結束。訂單創建者創建資金流動資訊和元資料。此訂單創建者將該資訊發佈到 Kafka。Kafka 處理該訂單並將其發送到訂單處理器。然後訂單處理器從 Kafka 獲取該資訊，對其進行處理，並將其作為意圖發送到 Kafka。從那裡，訂單處理器再次處理並聯繫 PSP。然後訂單處理器從 PSP 獲取答案並將其作為結果傳輸到 Kafka。然後結果由訂單編寫者保存。

支付服務使用的 Kafka 關鍵功能如下：

- 它像訊息隊列一樣工作，可以發布和訂閱訊息隊列。
- 它以容錯的方式存儲記錄。
- 它非同步處理支付記錄。

## Fraud detection (欺詐檢測)
欺詐檢測是我們設計的關鍵運營組件。支付欺詐損失按總金額的百分比計算。儘管欺詐活動僅佔總預訂的一小部分，但這些損失對收益有重大的影響。此外，如果惡意行為未能及時被發現和處理，它可能會被進一步利用，從而給企業帶來重大損失。早些時候，我們討論了在行程開始前檢測欺詐的風險引擎。在這裡，我們將重點關注在行程期間或行程結束時發生的欺詐檢測。

欺詐檢測具有挑戰性，因為許多欺詐實例就像檢測零日安全漏洞一樣。因此，我們的系統需要智能來檢測異常，並且還需要以人工主導審計的形式對自動決策進行問責。

Uber 認為是欺詐的活動如下：

```
以下八種欺詐活動列表取自：https://www.uber.com/gb/en/drive/driver-app/fraud-activities/
```

- 司機以不誠實的方式故意增加行程的時間或距離——例如，如果他們選擇比乘客到達目的地所需路線長得多的路線。
- 司機操縱 GPS 資料或使用虛假位置 GPS 應用程式。
- 司機在無意完成行程的情況下確認行程，迫使乘客取消。
- 司機出於欺詐目的創建虛假司機或乘客帳戶。
- 司機在開設帳戶時提供關於自己的不正確或不準確的資訊。
- 司機駕駛未經 Uber 批准的車輛。
- 司機索取欺詐性費用或收費，例如無根據的清潔費。
- 司機故意確認或完成欺詐性行程。

Uber 推出了 RADAR，這是一個人工輔助的 AI 欺詐檢測和緩解解決方案，用於處理討論過的欺詐場景。RADAR 系統通過分析支付系統的活動時間序列來檢測欺詐。然後它為其生成一條規則並阻止其進一步處理。這種主動方法有助於實時檢測看不見的欺詐。此檢測模型還利用人類知識進行持續改進。在這裡，我們將簡要討論 RADAR 的工作原理：

[RADAR 欺詐檢測解決方案](./radar.jpg)

RADAR 識別欺詐企圖的開始並創建一條規則來防止它。欺詐分析師參與下一步。他們審查規則並在需要時批准或拒絕它。然後他們向保護系統發送反饋 (批准或未批准)。欺詐分析師也將反饋發送到欺詐檢測系統以改進檢測。

此外，系統在以下時間維度檢查資料：

- 它在行程完成時檢查行程時間。實時行程監控涉及多個因素。例如，系統可以檢查司機和乘客的位置是否相同。系統還可以監控速度並分析實時交通，以檢查司機是否故意開慢車或是否存在交通擁堵。

- 支付結算時間是指獲取支付處理資料。結算可能需要數天或數週。

我們先前討論了關於大規模防範惡意活動對於企業成功必不可少的基本細節。在擬議的模型中，有人類專家參與，這可能會降低系統的可擴展性。正在研究如何確保 AI 系統做出的決策是公平和合乎道德的。
