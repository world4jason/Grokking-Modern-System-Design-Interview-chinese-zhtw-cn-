# Detailed Design of a Monitoring System (監控系統的詳細設計)
我們將討論監控系統的核心組件，找出我們設計的缺點，並改進設計以滿足我們的需求。

## Storage (存儲)
我們將使用時間序列資料庫將資料本地保存在運行監控服務的伺服器上。然後，我們將把它與一個單獨的存儲節點集成。我們將使用 blob 存儲來存儲我們的指標。

我們需要存儲指標，並知道如果指標達到特定值時該執行什麼操作。例如，如果 CPU 使用率超過 90%，我們會向最終使用者生成警報，以便警報接收者可以採取必要的步驟，例如分配更多資源進行擴展。為此，我們需要另一個包含規則和操作的存儲區域。我們稱之為規則資料庫。一旦違反規則，我們可以採取適當的行動。

在這裡，我們在設計中確定了另外兩個組件——即規則和操作資料庫以及存儲節點 (blob 存儲)。

## Data collector (資料收集器)
我們需要一個監控系統來更新有關我們幾個資料中心的資訊。如果有關我們流程的資訊到達我們，我們就可以保持更新，這可以通過日誌記錄來實現。我們將選擇拉取策略。然後，我們將從應用程式的日誌中提取相關指標。正如我們在日誌設計中所討論的，我們使用了分佈式消息隊列。隊列中的消息具有服務名稱、ID 和日誌的簡短描述。這將幫助我們識別特定服務的指標及其資訊。將相關指標暴露給資料收集器對於監控任何服務都是必要的，以便我們的資料收集器可以從服務中獲取指標並將它們存儲在時間序列資料庫中。

基於拉取方法的監控系統的一個現實世界示例是 DigitalOcean。它監控全球分散的數百萬台機器。

Question
使用基於推送的方法有哪些缺點？

Answer
基於推送的監控工具從應用程式和伺服器收集指標資料並將其發送到中央收集平台。每個微服務都將其指標發送到監控系統，從而導致基礎設施上的流量負載很重。這就是監控可能成為業務運營瓶頸的原因。監控可以接近實時。但是，如果不採取適當的措施，來自所有服務的持續推送請求可能會壓垮基礎設施，從而導致網絡洪水。我們還必須在每個目標上安裝守護進程，以便將指標發送到監控伺服器，這需要額外的工作。
```

### Service discoverer (服務發現者)
資料收集器負責從其監控的服務中獲取指標。這樣，監控系統不需要跟踪服務。相反，它可以使用發現者服務找到它們。我們將保存我們必須監控的服務的相關資訊。我們將使用服務發現解決方案並與多個平台和工具集成，包括 EC2、Kubernetes 和 Consul。這將使我們能夠發現我們必須監控哪些服務。類似的動態發現可用於新委託的硬件。

讓我們將新識別的組件添加到我們現有的設計中。

## Querying service (查詢服務)
我們希望有一個服務來訪問資料庫並獲取相關的查詢結果。我們需要這樣做是因為我們想要查看錯誤，例如特定節點的內存使用值，或者如果指標超過設定的限制，則發送警報。讓我們添加我們需要的兩個組件以及查詢。

### Alert Manager (警報管理器)
警報管理器負責在違反設定規則時發送警報。它可以發送電子郵件、Slack 消息等警報。

### Dashboard (儀表板)
我們可以使用收集的指標來設置儀表板以顯示所需的資訊——例如，本週的請求數。

我們的一體化監控服務適用於主動跟踪系統和服務。它收集和存儲資料，並支持搜索、圖表和警報。

## Pros (優點)
- 我們監控服務的設計確保了運營的順利進行，並關注即將出現問題的跡象。
- 我們的設計通過獲取資料本身來避免使網絡流量過載。
- 監控服務提供更高的可用性。

## Cons (缺點)
- 該系統似乎具有可擴展性，但管理更多伺服器進行監控可能會成為問題。例如，我們有一台專用於運行監控服務的伺服器。它可能是單點故障 (SPOF)。為了應對 SPOF，我們可以為我們的監控系統配備一個故障轉移伺服器。然後，我們還需要保持實際伺服器和故障轉移伺服器之間的一致性。但是，隨著伺服器數量的進一步增加，這樣的設計也將達到可擴展性上限。
- 監控 24/7 收集大量資料，永遠保存可能不可行。我們需要一項政策和機制來定期刪除不需要的資料，以有效地利用資源。

## Improving our design (改進我們的設計)
我們希望改進我們的設計，以便我們的系統可以更好地擴展並決定保留哪些資料和刪除哪些資料。讓我們看看基於推送的方法是如何工作的。在基於推送的方法中，應用程式將其資料推送到監控系統。

[基於推送的監控系統](./push.jpg)

我們使用基於拉取的策略來避免網絡擁塞。這還允許應用程式不必將相關監控資料發送到系統。相反，監控系統獲取或自行拉取資料。為了滿足擴展需求，我們也需要應用基於推送的方法。我們將通過結合基於拉取的策略和基於推送的策略來使用混合方法。

我們將繼續在資料中心內的幾台伺服器上使用基於拉取的策略。我們還將為資料中心內的數百或數千台伺服器分配幾台監控伺服器——比如一台伺服器監控 5,000 台伺服器。我們稱它們為二級監控伺服器。

現在，我們將應用基於推送的策略。二級監控系統將其資料推送到主資料中心伺服器。主資料中心伺服器將其資料推送到負責檢查分佈在全球的所有資料中心的全球監控服務。

我們將使用 blob 存儲來存儲過多的資料，應用 elastic search，並使用可視化工具查看我們的相關統計資料。隨著我們的伺服器或資料中心的增加，我們將添加更多的監控系統。其設計如下。

Question 1
如果本地或全球監控系統宕機怎麼辦？

Answer
我們可以將資料存儲在本地，等待系統恢復運行。但是本地資料存儲是有限制的。因此，我們要麼刪除以前的資料，要麼不存儲新資料。為了做出決定，需要制定相關政策。
```

```
Question 2
如果監控系統使用其本應監控的資料中心中的相同基礎設施，它如何可靠地工作？考慮到資料中心網絡故障可能會破壞監控組件，這一點值得思考。

Answer
監控系統的實際部署需要特別小心。我們可能有內部、監控專用網絡以將其與公共網絡隔離。我們應該使用 blob 存儲和其他服務的單獨實例。
```

擁有監控的外部組件也有幫助，其中外部可能意味著獨立服務提供商的基礎設施。但是，設計這樣的系統很複雜並且更昂貴。
