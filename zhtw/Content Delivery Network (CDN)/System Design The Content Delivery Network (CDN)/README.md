# System Design: The Content Delivery Network (CDN) (系統設計：內容傳遞網路)
## Problem statement (問題陳述)
讓我們從一個問題開始：如果世界各地數百萬使用者使用我們的資料密集型應用程式，而我們的服務部署在單個資料中心來服務使用者的請求，可能會出現什麼問題？

可能會出現以下問題：

- **High latency (高延遲)**：由於與服務資料中心的物理距離，使用者感知的延遲將很高。使用者感知的延遲有許多組成部分，例如傳輸延遲 (可用頻寬的函數)、傳播延遲 (距離的函數)、排隊延遲 (網路擁塞的函數) 和節點處理延遲。因此，長距離的資料傳輸會導致更長的延遲。即時應用程式通常需要低於 200 毫秒 (ms) 的延遲。對於網際網路語音協定 (VoIP)，延遲不應超過 150 毫秒，而影片串流應用程式無法容忍超過幾秒鐘的延遲。

注意：根據 2021 年 12 月 21 日進行的一次讀數，從美國東部 (北維吉尼亞) 到美國西部 (北加利福尼亞) 的平均延遲為 62.9 毫秒。跨大陸——例如，從美國東部 (北維吉尼亞) 到非洲 (開普敦)——為 225.63 毫秒。這是雙向延遲，稱為往返延遲。

- **Data-intensive applications (資料密集型應用程式)**：資料密集型應用程式需要傳輸大量流量。在更長的距離上，這可能是一個問題，因為網路路徑延伸穿過不同類型的 ISP。由於一些較小的路徑訊息傳輸單元 (Path MTU) 鏈路，網路上應用程式的吞吐量可能會降低。同樣，網路路徑的不同部分可能具有不同的擁塞特徵。隨著使用者數量的增加，問題會倍增，因為源伺服器必須單獨向每個使用者提供資料。也就是說，當多個客戶端請求時，主資料中心將需要發送大量冗餘資料。然而，使用串流服務的應用程式本質上既是資料密集型的又是動態的。

路徑 MTU (Path MTU) 是指可以從源遍歷到目的地而無需拆分的最小資料單元。
```

注意：根據一項調查，78% 的美國消費者使用串流服務，這在五年內增加了 25%。
```

- **Scarcity of data center resources (資料中心資源的稀缺性)**：當服務的使用者數量顯著增加時，重要的資料中心資源 (如計算能力和頻寬) 成為限制。同時吸引數百萬使用者的服務需要擴展。即使在單個資料中心實現了擴展，當資料中心因自然災害或與網際網路的連接問題而離線時，它仍然可能遭受單點故障的困擾。

注意：根據一項研究，YouTube、Netflix 和 Amazon Prime 在 2020 年共同產生了 80% 的網際網路流量。大約在 2016 年，CDN 提供者 Akamai 服務了 15% 到 30% 的 Web 流量 (約每秒 30 Terabits)。對於 90% 的網際網路使用者來說，Akamai 只有一個跳躍 (hop) 的距離。因此，我們有充分的理由優化這些資料的傳遞和消耗，而不會使網際網路核心成為瓶頸。

## How will we design a CDN? (我們將如何設計 CDN？)
我們將 CDN 的設計分為六課：

- **Introduction to a CDN (CDN 簡介)**：我們將提供 CDN 的詳盡介紹，並識別功能和非功能需求。
- **Design of a CDN (CDN 設計)**：我們將解釋如何設計 CDN。我們還將簡要描述 API 設計。
- **In-depth Investigation of CDN: Part 1 (深入調查 CDN：第 1 部分)**：本課解釋快取策略和 CDN 架構。此外，我們將討論尋找最近代理伺服器的各種方法。
- **In-depth Investigation of CDN: Part 2 (深入調查 CDN：第 2 部分)**：我們將討論如何在 CDN 中使內容保持一致以及代理伺服器的部署。我們還將詳細介紹自定義和專用 CDN。
- **Evaluation of CDN (CDN 評估)**：本課將提供對我們提出的設計的評估。
- **Quiz on CDN System Design (CDN 系統設計測驗)**：我們將通過測驗加強 CDN 設計的主要概念。
