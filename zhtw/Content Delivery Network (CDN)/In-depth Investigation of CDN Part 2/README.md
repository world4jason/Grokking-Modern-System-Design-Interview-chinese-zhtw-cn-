# In-depth Investigation of CDN: Part 2 (深入調查 CDN：第 2 部分)
在本課中，我們學習如何使用不同的一致性機制來實現內容的一致性。我們還將學習應該在哪裡部署代理伺服器，以及 CDN 即服務 (CDN as a service) 和專用 CDN (specialized CDN) 之間的區別。

## Content consistency in CDN (CDN 中的內容一致性)
代理伺服器中的資料應與源伺服器中的資料一致。如果代理伺服器與源伺服器保持不一致，使用者總是有存取過時資料的風險。根據推或拉模型，可以使用不同的一致性機制來確保資料的一致性。

### Periodic polling (定期輪詢)
使用拉取模型，代理伺服器定期向源伺服器請求更新的資料，並相應地更改快取中的內容。當內容不頻繁更改時，輪詢方法會消耗不必要的頻寬。定期輪詢使用重新整理時間 (Time-to-refresh - TTR) 來調整從源伺服器請求更新資料的時間段。

### Time-to-live (TTL) (存活時間)
由於 TTR，代理伺服器可能會無用地向源伺服器請求更新的資料。可用於減少重新整理訊息頻率的更好方法是存活時間 (TTL) 方法。在此方法中，每個物件都有源伺服器分配給它的 TTL 屬性。TTL 定義了內容的過期時間。代理伺服器向使用者提供相同的資料版本，直到該內容過期。過期後，代理伺服器會檢查源伺服器是否有更新。如果資料已更改，它會從源伺服器獲取更新的資料，然後使用更新的資料回應使用者的請求。否則，它會保留相同的資料以及來自源伺服器的更新過期時間。

### Leases (租約)
使用此技術，源伺服器將租約授予發送給代理伺服器的資料。租約表示源伺服器同意在資料有任何更改時通知代理伺服器的時間間隔。代理伺服器必須在租約到期後發送請求續訂租約的訊息。租約方法有助於減少代理伺服器和源伺服器之間交換的訊息數量。此外，租約持續時間可以根據觀察到的代理伺服器負載動態優化。此技術稱為自適應租約 (adaptive lease)。

在下一節中，我們將討論將 CDN 代理伺服器放置在何處以有效地傳輸資料。

## Deployment (部署)
在安裝 CDN 設施之前，我們必須清楚以下問題的答案：

- 安裝代理伺服器以最大程度利用 CDN 技術的最佳位置在哪裡？
- 我們應該安裝多少個 CDN 代理伺服器？

### Placement of CDN proxy servers (CDN 代理伺服器的放置)
CDN 代理伺服器必須放置在具有良好連接性的網路位置。請參閱以下選項：
- **On-premises (本地/內部部署)** 代表可以放置在主要 IXP 附近的較小資料中心。
- **Off-premises (場外/外部部署)** 代表將 CDN 代理伺服器放置在 ISP 的網路中。

如今，將大部分電影資料保存在 ISP 內部的 CDN 基礎設施中可能是可行的。儘管如此，對於像 YouTube 這樣的服務來說，資料太大且不斷擴展，因此很難決定我們應該在使用者附近放置什麼。Google 使用分割 TCP (split TCP) 通過保持從 IXP 級基礎設施到其主要資料中心的巨大 TCP 視窗的持久連接來減少使用者感知的延遲。客戶端的 TCP 請求在 IXP 級基礎設施終止，然後在已建立的低延遲 TCP 連接上轉發。

這樣做大大減少了客戶端感知的延遲，這是因為避免了與遠處主機的 TCP 連接的初始三向握手和慢啟動階段 (如果客戶端想要去 Google 的主要資料中心)。到 IXP 的往返延遲通常非常低。因此，該級別的三向握手和慢啟動可以忽略不計。預測推送 (Predictive push) 是一個重要的研究領域，用於決定將什麼推送到客戶附近。

我們可以使用測量來促進代理伺服器放置的決策。一種這樣的工具是 ProxyTeller，用於決定將代理伺服器放置在何處以及需要多少代理伺服器才能實現高效能。ProxyTeller 使用命中率、網路頻寬和客戶端回應時間 (延遲) 作為效能參數來決定代理伺服器的放置。其他貪婪、隨機和熱點演算法也用於代理伺服器放置。

## CDN as a service (CDN 即服務)
大多數公司不建立自己的 CDN。相反，他們使用 CDN 提供者 (如 Akamai、Cloudflare、Fastly 等) 的服務來傳遞其內容。同樣，像 AWS 這樣的參與者使任何人都可以使用全球 CDN 設施。

公司與 CDN 服務提供者簽訂合約並將其內容傳遞給 CDN，從而允許 CDN 將內容分發給終端使用者。公共 CDN 引發了內容提供者的以下擔憂：

- 如果公共 CDN 宕機，內容提供者什麼也做不了。

- 如果公共 CDN 在某些網站流量來自的地區或國家沒有任何代理伺服器，那麼這些特定客戶就倒霉了。在這種情況下，內容提供者必須從其他 CDN 提供者購買 CDN 服務或部署和使用自己的私有 CDN。

- CDN 提供者的某些網域或 IP 地址可能會在某些國家被封鎖或限制，因為它們可能正在傳遞在這些國家被禁止的內容。

注意：有些公司建立自己的 CDN，而不是使用 CDN 提供者的服務。例如，Netflix 擁有自己專門構建的 CDN，稱為 Open Connect。

## Specialized CDN (專用 CDN)
我們已經討論過許多公司使用 CDN 即服務，但有些情況下公司會建立自己的 CDN。許多原因促成了這一決定。一是商業 CDN 服務的成本。專用 CDN 由僅為其自己公司服務內容的存取點 (PoP) 組成。這些 PoP 可以是快取伺服器、反向代理或應用程式傳遞控制器。雖然專用 CDN 在首次設定時成本很高，但成本最終會隨著時間的推移而降低。從本質上講，這是一個購買與構建 (buy versus build) 的決定。

專用 CDN 的 PoP 由許多代理伺服器組成，可服務數 PB 的內容。私有 CDN 可以與公共 CDN 共存使用。如果私有 CDN 的容量不足或發生故障導致容量減少，則使用公共 CDN 作為備份。Netflix 的 Open Connect Appliance (OCA) 是專門用於影片傳遞的 CDN 的一個例子。

Netflix 的 OCA 伺服器不儲存使用者資料。相反，它們執行以下任務：

- 它們向駐留在 AWS (Amazon Web Services) 中的 Open Connect 控制平面報告其狀態——健康狀況、學習到的路由以及快取內容的詳細資訊。
- 它們服務使用者請求的快取內容。

所有位於 IXP 或嵌入 ISP 網路中的已部署 OCA 都由 Open Connect 營運團隊監控。

### Why Netflix built its CDN (為什麼 Netflix 建立其 CDN)
隨著 Netflix 變得越來越受歡迎，它決定建立和管理自己的 CDN，原因如下：

- 由於客戶對 Netflix 影片串流媒體需求的快速增長，CDN 服務提供者正在努力擴展其基礎設施。

- 隨著串流媒體影片數量的增加，使用 CDN 服務的費用也隨之增加。

- 影片串流媒體是 Netflix 的主要業務和主要收入來源。因此，保護平台上所有影片的資料至關重要。Netflix 的 OCA 以更好的方式管理潛在的資料洩露風險。

- 為了向客戶提供最佳的串流媒體傳遞，Netflix 需要最大化其對使用者影片播放器、使用者與 Netflix 伺服器之間網路的控制。

- Netflix 的 OCA 可以使用自定義 HTTP 模組和 TCP 連接演算法來快速檢測網路問題並排除其 CDN 網路中的任何問題。

- Netflix 希望長時間保留熱門內容。在使用公共 CDN 運營時，這並不完全可能，因為保留和維護它會產生高昂的成本。

注意：Netflix 使用 OCA 能夠實現接近 95% 的命中率。
