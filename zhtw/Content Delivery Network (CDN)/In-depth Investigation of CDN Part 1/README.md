# In-depth Investigation of CDN: Part 1 (深入調查 CDN：第 1 部分)
在本課中，我們將詳細介紹之前課程中提到的某些概念，例如 CDN 模型和多層/分層 CDN 架構。我們還將介紹一些新概念，包括動態內容快取優化以及在 CDN 中發現附近代理伺服器的各種技術。

## Content caching strategies in CDN (CDN 中的內容快取策略)
識別要快取的內容對於傳遞最新且熱門的 Web 內容非常重要。為了確保及時更新，使用兩種 CDN 分類從源伺服器獲取內容。

### Push CDN (推送 CDN)
在推送 CDN 模型中，內容會自動從源伺服器發送到 CDN 代理伺服器。向 CDN 代理伺服器傳遞內容是內容提供者的責任。推送 CDN 適用於靜態內容傳遞，其中源伺服器決定使用 CDN 向使用者傳遞哪些內容。內容會根據內容的受歡迎程度推送到各個位置的代理伺服器。如果內容變化迅速，推送模型可能難以跟上，並且會執行多餘的內容推送。

[將內容推送到 PoP](./push.jpg)

### Pull CDN (拉取 CDN)
當使用者請求時，CDN 會從源伺服器提取不可用的資料。代理伺服器將檔案保留一段指定的時間，如果不再請求這些檔案，則將其從快取中刪除，以平衡容量和成本。

當使用者在拉取 CDN 模型中請求 Web 內容時，CDN 本身負責從源伺服器拉取請求的內容並將其服務給使用者。因此，這種類型的 CDN 更適合服務動態內容。

[從源伺服器到 CDN PoP 的內容拉取](./pull.jpg)

如上所述，推送 CDN 主要用於服務靜態內容。由於靜態內容服務的用戶範圍比動態內容更廣，時間也更長，因此推送 CDN 方案比拉取 CDN 維護更多的副本，從而提高了可用性。另一方面，拉取 CDN 對於頻繁變化的內容和高流量負載更受青睞。低儲存消耗是拉取 CDN 的主要好處之一。

注意：大多數內容提供者同時使用拉取和推送 CDN 快取方法，以獲得兩者的好處。
```

## Dynamic content caching optimization (動態內容快取優化)
由於動態內容經常變化，因此最好對其進行最佳快取。本節處理頻繁變化內容的優化。

某些動態內容的建立需要執行腳本，這些腳本可以在代理伺服器上執行，而不是在源伺服器上執行。可以使用各種參數生成動態資料，如果在代理伺服器上執行，這可能是有益的。例如，我們可以根據使用者位置、某個位置的一天中的時間、特定於某個位置的第三方 API (例如，天氣 API) 等生成動態內容。因此，在代理伺服器而不是源伺服器上運行腳本是最佳的。

為了減少源伺服器和代理伺服器之間的通訊以及代理伺服器的儲存需求，使用壓縮技術也很有用。例如，Cloudflare 使用 Railgun 壓縮動態內容。

另一種流行的動態資料壓縮方法是 Edge Side Includes (ESI) 標記語言。通常，Web 頁面的一小部分會在特定時間內發生變化。這意味著在每次小更改時獲取完整的 Web 頁面都包含大量冗餘資料。為了解決此效能損失，ESI 指定了內容更改的位置，以便可以快取 Web 頁面的其餘內容。它在 CDN 邊緣伺服器或客戶端瀏覽器組裝動態內容。ESI 尚未由全球資訊網協會 (W3C) 標準化，但許多 CDN 提供者使用它。

注意：基於 HTTP 的動態自適應流 (Dynamic Adaptive Streaming over HTTP - DASH) 使用帶有不同解析度影片 URI 的清單檔案，以便客戶端可以根據當時的網路和終端節點條件獲取任何合適的內容。Netflix 在 URL 中使用帶有 Byte-range 的專有 DASH 版本，以進一步優化內容請求和傳遞。
```

## Multi-tier CDN architecture (多層 CDN 架構)
內容提供者通過 CDN 將內容發送給大量客戶端。同時將資料分發到所有 CDN 代理伺服器的任務具有挑戰性，並且會顯著增加源伺服器的負擔。CDN 遵循樹狀結構來簡化源伺服器的資料分發過程。邊緣代理伺服器擁有屬於同一層級的一些對等伺服器。這組伺服器從樹中的父節點接收資料，父節點最終從源伺服器接收資料。資料通過樹中的不同路徑從源伺服器複製到代理伺服器。

資料分發的樹狀結構允許我們通過向樹中新增更多伺服器節點來為不斷增加的使用者擴展我們的系統。它還減少了源伺服器進行資料分發的負擔。CDN 通常具有一層或兩層代理伺服器 (快取)。下圖顯示了兩層代理伺服器：

[CDN 代理伺服器之間的資料分發](./distribution.jpg)

每當新的代理伺服器進入 CDN 的樹時，它就會請求控制核心 (control core)，控制核心維護 CDN 中所有代理伺服器的資訊，並提供初始內容和設定資料。

控制核心是管理 PoP 內代理伺服器的一組伺服器。
```

研究表明，許多內容具有長尾分佈。這意味著，在某個時刻，只有少數內容非常受歡迎，然後我們有一長串不太受歡迎的內容。在這裡，可以使用多層快取來處理長尾內容。

[許多種類的資料呈現長尾現象](./statistics.jpg)

問 (Question)
如果子代理伺服器或父代理伺服器發生故障，或者源伺服器發生故障會發生什麼？

答 (Answer)
每個 PoP 包含一組 CDN 代理伺服器。當任何子代理伺服器因任何故障而停止工作時，DNS 可以將客戶端路由到不同的子級代理伺服器。每個子代理伺服器都知道許多上層父伺服器，如果一個發生故障，它可以轉向另一個。源伺服器是一組具有熱備份的伺服器，內容位於複製儲存中。如果其中任何源伺服器發生故障，其他伺服器將承擔負載。
```

既然我們已經看到了將內容從源伺服器分發到 CDN 的所有代理伺服器的方法，我們還應該了解使用者如何使用這些代理伺服器更有效地獲取資料。我們將在本課的後續部分討論當客戶端發出請求時如何選擇最近的代理伺服器以及 CDN 的位置。

## Find the nearest proxy server to fetch the data (尋找最近的代理伺服器以獲取資料)
使用者從最近的代理伺服器獲取資料至關重要，因為 CDN 旨在通過將資料帶到離使用者更近的地方來減少使用者感知到的延遲。然而，問題仍然在於世界各地的使用者如何從最近的代理伺服器請求資料。本節的目標是回答這個問題。

### Important factors that affect the proximity of the proxy server (影響代理伺服器鄰近度的重要因素)
有兩個與尋找離使用者最近的代理伺服器相關的重要因素：

- **使用者和代理伺服器之間的網路距離**至關重要。這取決於以下兩件事：
    - 第一是網路路徑的長度。
    - 第二是沿網路路徑的容量 (頻寬) 限制。

具有最高容量 (頻寬) 的最短網路路徑是有問題的使用者最近的代理伺服器。此路徑幫助使用者更快地下載內容。

- **請求負載 (Requests load)** 指的是代理伺服器在任何時間點處理的負載。如果一組代理伺服器過載，請求路由系統應該將請求轉發到負載較少的位置。此操作平衡了代理伺服器的負載，從而減少了回應延遲。

讓我們看看可用於將使用者路由到最近代理伺服器的技術。

### DNS redirection (DNS 重新導向)
在典型的 DNS 解析中，我們使用 DNS 系統針對人類可讀的名稱獲取 IP。然而，DNS 也可以向客戶端返回另一個 URI (而不是 IP)。這種機制稱為 DNS 重新導向 (DNS redirect) 或 DNS 重分發 (DNS redistribution)。

內容提供者可以使用 DNS 重新導向將客戶端發送到特定的 CDN。例如，如果客戶端嘗試解析其中包含單詞“video”的名稱，則權威 DNS 伺服器提供另一個 URL (例如，cdn.xyz.com)。客戶端執行另一個 DNS 解析，CDN 的權威 DNS 提供適當 CDN 代理伺服器的 IP 地址以獲取所需的內容。

根據使用者的位置，DNS 的回應可能會有所不同。讓我們看看下面的幻燈片，了解 DNS 重新導向是如何運作的：

[DNS 重分發](./redistribution)

注意：最近的代理伺服器不一定意味著地理位置上最近的伺服器。可能是，但這不僅僅是地理位置的問題。其他因素，如網路距離、頻寬和該路線上已經存在的流量負載也很重要。
```

DNS 重新導向方法有兩個步驟：

1. 在第一步中，它將客戶端映射到適當的網路位置。
2. 在第二步中，它將負載分發到該位置的代理伺服器上，以平衡代理伺服器之間的負載 (有關此內容的更多詳細資訊，請參閱 DNS 和負載平衡器構建塊)。

DNS 重新導向考慮了這兩個重要因素——網路距離和請求負載，這減少了對代理伺服器的延遲。

為了將客戶端從叢集中的一台機器轉移到另一台機器，第二步的 DNS 回覆具有較短的 TTL，以便客戶端在短時間後重複解析。在硬體故障和網路擁塞的情況下，DNS 通過將請求路由到其他活動伺服器來繼續傳遞內容。它通過負載平衡流量、使用智慧故障轉移並維護多個資料中心的伺服器來做到這一點，從而實現良好的可靠性和效能。

由於代理伺服器的負載隨時間變化，內容提供者需要在 DNS 中進行適當的更改以使 DNS 重新導向有效。許多 CDN 提供者 (如 Akamai) 在其路由系統中使用 DNS 重新導向。

### Anycast (任播)
任播 (Anycast) 是一種路由方法，其中位於多個位置的所有邊緣伺服器共享同一個單一 IP 地址。它使用邊界閘道協定 (BGP) 根據網際網路的自然網路流路由客戶端。CDN 提供者可以使用任播機制，以便將客戶端引導至最近的代理伺服器以獲取內容。

BGP 是一種網路級協定，由網際網路邊緣路由器用於共享路由和可達性資訊，以便網路上的每個節點 (即使是獨立的) 都能知道其最近網路鄰居的狀態。
```

### Client multiplexing (客戶端多工)
客戶端多工涉及向客戶端發送候選伺服器列表。然後客戶端從列表中選擇一個伺服器發送請求。這種方法效率低，因為客戶端缺乏整體資訊來選擇最適合其請求的伺服器。這可能會導致將請求發送到已經負載的伺服器並經歷更高的存取延遲。

### HTTP redirection (HTTP 重新導向)
HTTP 重新導向是所有方法中最簡單的。通過此方案，客戶端從源伺服器請求內容。源伺服器使用 HTTP 協定回應，通過內容的 URL 重新導向使用者。
