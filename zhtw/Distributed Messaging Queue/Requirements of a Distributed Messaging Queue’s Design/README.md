# Requirements of a Distributed Messaging Queue’s Design (分佈式消息隊列設計的需求)
## Requirements (需求)
在分佈式消息隊列中，資料駐留在多台機器上。我們的目標是設計一個滿足以下功能和非功能需求的分佈式消息隊列。

### Functional requirements (功能需求)
- 以下是客戶端應能夠執行的操作：

- **Queue creation (隊列創建)**：客戶端應能夠創建隊列並設置一些參數——例如，隊列名稱、隊列大小和最大消息大小。

- **Send message (發送消息)**：生產者實體應能夠將消息發送到為它們準備的隊列。

- **Receive message (接收消息)**：消費者實體應能夠從各自的隊列接收消息。

- **Delete message (刪除消息)**：消費者進程應能夠在成功處理消息後從隊列中刪除消息。

- **Queue deletion (隊列刪除)**：客戶端應能夠刪除特定隊列。

```
隊列大小是隊列可以包含的最大消息數。例如，亞馬遜的標準隊列大小是無限的。但是，對於傳輸中的消息，大小限制為 120,000。

一般來說，大多數流行的服務，如亞馬遜簡單隊列服務 (SQS) 和微軟消息隊列 (MSMQ)，分別允許最大大小為 256KB 和 4MB。

我們如何發送大於預定義大小的消息？

有多種方法可用於發送大於指定允許大小的消息。例如，一種方法是在發送方將消息分成小塊，並在接收方將其組合。但是，這種方法會在發送方和接收方都會產生額外的複雜性。

亞馬遜 SQS 提供了擴展庫，使用者可以通過調用多個 API (包括 AmazonSQSExtendedClient、ExtendedClientConfiguration 等) 發送包含對 Amazon S3 中消息負載引用的消息。同樣，微軟 MSMQ 提供了一個 MQSendLargeMessage API，可以作為 XML 文檔發送大於 4MB 的消息。

因此，我們將忽略此討論，假設我們的系統支持亞馬遜或微軟遵循的策略之一。
```

## Non-functional requirements (非功能需求)
我們對分佈式消息隊列的設計應遵守以下非功能需求：

- **Durability (持久性)**：系統接收的資料應該是持久的，不應丟失。生產者和消費者可以獨立失敗，具有資料持久性的隊列對於使整個系統工作至關重要，因為其它實體都依賴於該隊列。

- **Scalability (可擴展性)**：系統需要具有可擴展性，並能夠處理增加的負載、隊列、生產者、消費者和消息數量。同樣，當負載減少時，系統應該能夠相應地縮減資源。

- **Availability (可用性)**：系統應具有高可用性以接收和發送消息。即使在其一個或多個組件發生故障後，它也應繼續不間斷地運行。

- **Performance (性能)**：系統應提供高吞吐量和低延遲。

## Single-server messaging queue (單伺服器消息隊列)
在我們開始繪製分佈式消息隊列設計的旅程之前，我們應該回顧一下如何在單個伺服器中使用隊列，其中生產者和消費者進程也在同一個節點上。生產者或消費者可以通過獲取鎖定機制來訪問單伺服器隊列，以避免資料不一致。隊列被認為是一個關鍵部分，一次只有一個實體 (生產者或消費者) 可以訪問資料。

然而，有幾個方面限制了我們在當今的分佈式系統範式中使用單伺服器消息隊列。例如，在發生硬體或網絡故障時，協作進程、生產者和消費者無法使用它。此外，隨著鎖爭用的增加，性能會受到重大打擊。此外，它既不可擴展也不持久。

```
這種隊列也稱為有界隊列，因為它在系統中的大小是固定的。
```

## Building blocks we will use (我們將使用的構建模塊)
分佈式消息隊列的設計利用以下構建模塊：

[用於設計分佈式消息隊列的構建模塊](./bb.jpg)

- **Database(s) (資料庫)**：將需要存儲隊列和使用者的元資料。
- **Caches (快取)**：對於保存經常訪問的資料很重要，無論是與使用者有關的資料還是隊列元資料。
- **Load balancers (負載平衡器)**：用於將傳入請求引導到存儲元資料的伺服器。

在我們關於消息隊列的討論中，我們重點關注了它們的功能和非功能需求。在繼續設計分佈式消息隊列的過程之前，我們有必要討論一些可能影響設計的關鍵注意事項和挑戰。
