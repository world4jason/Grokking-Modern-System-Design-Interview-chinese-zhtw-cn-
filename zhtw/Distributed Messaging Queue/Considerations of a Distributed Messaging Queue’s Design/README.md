# Considerations of a Distributed Messaging Queue’s Design (分佈式消息隊列設計的注意事項)
在我們開始設計分佈式消息隊列的旅程之前，讓我們討論一些可能顯著影響設計的主要因素。這些包括消息的順序、排序對性能的影響以及對隊列的並發訪問的管理。我們在下面詳細討論這些因素中的每一個。

## Ordering of messages (消息的排序)
消息隊列用於從生產者那裡接收消息。消費者按照自己的節奏消費這些消息。有些操作至關重要，因為它們需要由隊列中的消息驅動的任務執行的嚴格順序。例如，在通過 Messenger 應用程式與朋友聊天時，消息應按順序發送；否則，這種交流至少可以說是令人困惑的。同樣，使用者從不同使用者那裡收到的電子郵件可能不需要嚴格的排序。因此，在某些情況下，隊列中傳入消息的嚴格順序至關重要，而許多用例可以容忍一些重新排序。

讓我們討論以下兩類隊列中的消息排序：

- **Best-effort ordering (盡力而為的排序)**
- **Strict ordering (嚴格排序)**

```
在隊列中，消息的順序與傳入消息隱式相關。一旦將消息放入隊列，在這些消息的消費和處理中將遵循相同的順序。

對於將消息放入同一隊列的並發生產者，直到生產者提供順序資訊 (例如，時間戳或序列號)，順序才被明確定義。在沒有任何順序資訊的情況下，隊列按照消息到達服務的順序將消息放入隊列。

對於從同一隊列獲取消息的並發消費者，排序可能再次成為一個複雜的問題。雖然隊列可以按照它們進入隊列的相同順序一個接一個地移交消息，但兩個幾乎同時處理兩條消息的消費者可能需要特定於應用程式的排序機制。隊列可以通過在從隊列中分發消息時標記消息的排序資訊、序列號或時間戳來提供幫助。
```

### Best-effort ordering (盡力而為的排序)
通過盡力而為的排序方法，系統將消息按接收順序放入指定隊列。

例如，如下圖所示，生產者按圖示的相同順序發送四條消息 A、B、C 和 D。由於網絡擁塞或其他一些問題，消息 B 在消息 D 之後收到。因此，接收端的消息順序為 A、C、D 和 B。因此，在這種方法中，消息將按接收順序放入隊列，而不是在客戶端生成的順序。

[盡力而為的排序：消息按接收順序而不是發送順序放入隊列](./ordering.jpg)

### Strict ordering (嚴格排序)
嚴格排序技術更嚴格地保留消息的順序。通過這種方法，消息按生成的順序放入隊列。

在將消息按正確順序放入隊列之前，擁有一個識別消息在客戶端生成順序的機制至關重要。通常，使用唯一標識符或時間戳來標記生成時的消息。

```
Question
問題
誰負責提供序列號？

Answer
答案
系統向客戶端提供基本的庫或 API，以便為客戶端生成的消息提供序列號。
```

可以使用以下三種方法之一對傳入消息進行排序：

1. **Monotonically increasing numbers (單調遞增數字)**：對傳入消息進行排序的一種方法是在伺服器端為消息分配單調遞增的數字。當第一條消息到達時，系統會為其分配一個數字，例如 1。然後將數字 2 分配給第二條消息，依此類推。

   然而，這種方法存在潛在的缺點。首先，當收到突發請求時，它會充當影響系統性能的瓶頸，因為系統必須按指定順序為消息分配 ID，而其他消息則等待輪流。

   其次，它仍然無法解決當消息在客戶端較早生成的消息之前收到時出現的問題。因此，它不能保證會為客戶端生成的消息生成正確的順序。

2. **Causality-based sorting at the server side (伺服器端的基於因果關係的排序)**：鑑於使用單調遞增數字的缺點，另一種可用於傳入消息的時間戳和排序的方法是基於因果關係的排序。在這種方法中，消息根據在客戶端生成的的時間戳進行排序，並相應地放入隊列中。這種方法的主要缺點是對於多個客戶端會話，服務無法根據掛鐘時間確定順序。

3. **Using time stamps based on synchronized clocks (使用基於同步時鐘的時間戳)**：為了解決上述兩種方法出現的潛在問題，我們可以使用另一種適當的方法為消息分配基於同步時鐘的時間戳。在這種方法中，通過同步時鐘提供給每條消息的時間戳 (ID) 是唯一的，並且處於消息生成的正確序列中。我們可以將唯一進程標識符與時間戳一起標記，以使整體消息標識符唯一，並解決當兩個並發會話在完全相同的時間請求時間戳時的情況。此外，通過這種方法，伺服器可以根據時間戳輕鬆識別延遲的消息並等待延遲的消息。

正如我們在定序器構建模塊一節中所討論的，我們可以獲得既作為序列號又作為全球同步掛鐘時間戳的序列號。使用這種方法，我們的服務也可以跨客戶端會話對消息進行全局排序。

總之，在上述三種方法中，為傳入消息提供唯一 ID 或時間戳的最合適機制涉及使用同步時鐘。

#### Sorting (排序)
一旦在伺服器端收到消息，我們需要根據它們的時間戳對它們進行排序。因此，我們為此使用適當的在線排序演算法。

```
在線排序意味著我們需要在新資料不斷進入時保持某些資料排序。
```

```
Question
問題
假設發送較早的消息由於網絡延遲而到達較晚。處理這種情況的正確方法是什麼？

Answer
答案
在這種情況下，簡單的解決方案是對隊列重新排序。由此可能出現兩種情況。首先，重新排序將消息按正確順序排列。其次，我們已經將更新的消息分發給了消費者。

如果舊消息在我們已經分發了更新的消息時到達，我們將其放入特殊隊列中，客戶端將處理這種情況。如果是盡力而為的隊列，我們可以只將此類消息放在隊列的頭部。
```

## Effect on performance (對性能的影響)
主要是，隊列是為先進先出 (FIFO) 操作設計的。先進先出操作表明進入隊列的第一條消息總是首先分發。然而，在分佈式系統中維持這種嚴格的順序並不容易。由於消息 A 是在消息 B 之前生成的，因此消息 A 是否會在消息 B 之前被消費仍然不確定。使用單調遞增的消息標識符或帶有因果關係的標識符在將消息放入隊列時提供高吞吐量。儘管需要在線排序以提供嚴格順序，但在消息準備好提取之前需要一些時間。為了最小化由在線排序引起的延遲，我們使用時間窗口方法。

同樣，對於接收端的嚴格排序，我們需要序列化所有請求以逐個發送消息。如果不需要這樣做，我們在接收端會有更好的吞吐量和更低的延遲。

由於上述原因，許多分佈式消息隊列解決方案要麼不保證嚴格順序，要麼在吞吐量方面存在限制。正如我們之前所看到的，隊列必須執行許多額外的驗證和協調操作來維持順序。

```
時間窗口：我們必須對特定時間範圍內收到的消息進行排序，然後將它們放入相關隊列 (最舊的消息將首先放入隊列)。
```

### Managing concurrency (管理並發)
並發隊列訪問需要適當的管理。並發可能發生在以下階段：

- When multiple messages arrive at the same time. (當多條消息同時到達時。)
- When multiple consumers request concurrently for a message. (當多個消費者同時請求消息時。)

第一個解決方案是使用鎖定機制。當進程或線程請求消息時，它應該獲取用於從隊列中放置或消費消息的鎖。然而，正如前面所討論的，這種方法有幾個缺點。它既不可擴展也不高效。

另一種解決方案是在隊列的兩端使用系統緩衝區序列化請求，以便傳入的消息按順序放置，並且消費者進程也按到達順序接收消息。這是一個更可行的解決方案，因為它可以幫助我們避免競爭條件的發生。

應用程式可能會使用帶有專用生產者和消費者的多個隊列來控制每個隊列的排序成本，儘管這是以更複雜的應用程式邏輯為代價的。
