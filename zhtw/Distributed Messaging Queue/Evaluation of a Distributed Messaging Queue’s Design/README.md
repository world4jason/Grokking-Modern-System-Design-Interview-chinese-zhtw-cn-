# Evaluation of a Distributed Messaging Queue’s Design (分佈式消息隊列設計的評估)
我們完成了分佈式消息隊列的設計過程。現在，讓我們分析設計是否滿足分佈式消息隊列的功能和非功能需求。

## Functional requirements (功能需求)
- **Queue creation and deletion (隊列創建和刪除)**：當前端收到隊列請求時，在經過一些必要的檢查後，將根據客戶端提供的所有必要詳細資訊創建隊列。相應的集群管理器將伺服器分配給新創建的隊列，並通過元資料服務更新元資料存儲和快取中的資訊。

同樣，當客戶端不再需要隊列時，隊列將被刪除。負責的集群管理器釋放隊列佔用的空間，並因此從所有元資料存儲和快取中刪除資料。

```
Question
問題
在消費者嘗試最大處理次數後，我們如何處理無法處理 (這裡指消費) 的消息？

Answer
答案
可以提供一種特殊類型的隊列，稱為死信隊列，以處理在消費者進行最大處理嘗試次數後未消費的消息。這種類型的隊列還用於保存由於以下因素而無法成功處理的消息：

- The messages intended for a queue that doesn’t exist anymore. (發送到不再存在的隊列的消息。)
- The queue length limit is exceeded, although this would rarely occur with our current design. (超過隊列長度限制，儘管這在我們當前的設計中很少發生。)
- The message expires due to per-message time to live (TTL). (消息因每條消息的生存時間 (TTL) 而過期。)

死信隊列對於確定故障原因和識別系統中的故障也很重要。
```

- **Send and receive messages (發送和接收消息)**：一旦創建了特定隊列，生產者就可以將消息傳遞給它們。在後端，接收消息根據時間戳進行排序以保持其順序並放入隊列中。同樣，消費者可以從指定隊列檢索消息。

當收到生產者為特定隊列發送的消息時，前端會根據複製模型識別隊列所在的主主機或集群。然後將請求轉發到相應的實體並放入隊列中。

- **Message deletion (消息刪除)**：主要使用兩個選項從隊列中刪除消息。

  - 第一個選項是在消息被消費後不刪除它。但是，在這種情況下，消費者負責跟蹤已消費的內容。為此，我們需要維護隊列中消息的順序並跟蹤隊列中的消息。當滿足過期條件時，作業可以刪除消息。Apache Kafka 主要使用這種想法，其中多個進程可以消費一條消息。

  - 第二種方法在消息被消費後也不會刪除它。但是，通過一個屬性 (例如 visibility_timeout)，它在一段時間內不可見。這樣，其他消費者就無法獲取已經被消費的消息。然後消費者通過 API 調用刪除消息。


在這兩種情況下，消費者檢索到的消息僅由消費者刪除。這背後的原因是如果消費者因某種故障無法處理消息，則提供高持久性。在這種情況下，在沒有刪除調用的情況下，消費者可以在回來時再次檢索消息。

此外，這種方法還提供了至少一次交付語義。例如，當工作人員無法處理消息時，另一個工作人員可以在隊列中可見後檢索該消息。

```
至少一次交付語義：在這種類型的交付語義中，消息可以交付多次。大多數分佈式系統實現這種類型的交付語義，因為它更容易實現。潛在的假設是應用程式將處理可能的冗餘交付和處理 (通常，重複項不會損害應用程式，因為處理是冪等的)。
```

## Non-functional requirements (非功能需求)
- **Durability (持久性)**：為了實現持久性，隊列的元資料在不同節點上進行複製。同樣，當收到消息時，它會在駐留在不同節點上的隊列中進行複製。因此，如果節點發生故障，可以使用其他節點來傳遞或檢索消息。

- **Scalability (可擴展性)**：我們的設計組件，如前端伺服器、元資料伺服器、快取、後端集群等，都是水平可擴展的。我們可以增加或減少它們的容量以滿足我們的需求。可擴展性可以分為兩個維度：

 - **Increase in the number of messages (消息數量的增加)**：當消息數量達到特定限制 (例如 80%) 時，指定的隊列將被擴展。同樣，當消息數量低於特定閾值時，隊列將縮小。

 - **Increase in the number of queues (隊列數量的增加)**：隨著隊列數量的增加，對更多伺服器的需求也會增加，在這種情況下，集群管理器負責添加額外的伺服器。我們委託節點，以便在不同隊列之間實現性能隔離。一個隊列上的負載增加不應影響其他隊列。

- **Availability (可用性)**：我們的資料組件、元資料和實際消息在資料中心內部或外部進行適當複製，並且負載平衡器將流量路由到故障節點周圍。這些機制共同確保我們的系統在故障下仍可用於服務。

- **Performance (性能)**：為了獲得更好的性能，我們使用快取、資料複製和分區，從而減少了資料讀寫時間。此外，在必要時可以使用盡力而為的排序策略來增加吞吐量並降低延遲。在嚴格排序的情況下，我們還建議使用基於時間窗口的排序來潛在減少延遲。

## Conclusion (結論)
我們討論了在分佈式設置中設計 FIFO 隊列的許多細微之處。我們看到在嚴格的消息生產、消息提取順序以及可實現的吞吐量和延遲之間存在權衡。寬鬆的排序為我們提供了更高的吞吐量和更低的延遲。要求嚴格排序迫使系統做額外的工作來強制執行掛鐘或基於因果關係的排序。我們使用具有適當複製和分區的不同資料存儲來隨資料擴展。這個設計練習強調了一個在基於單操作系統的系統中很容易實現的結構，即生產者-消費者隊列，在分佈式設置中變得更加困難。
