# Design of a Rate Limiter (速率限制器的設計)

## High-level design (高層設計)
速率限制器可以部署為與 Web 伺服器交互的單獨服務，如下圖所示。收到請求後，速率限制器會建議是否應將請求轉發到伺服器。速率限制器由每個傳入請求應遵循的規則組成。這些規則定義了每個操作的節流限制。讓我們看看 Lyft 的速率限制器規則，它已經開源了其速率限制組件。

```yaml
domain: messaging
descriptors:
   -key: message_type
    value: marketing
    rate_limit:
               unit: day
               request_per_unit: 5
                            
                            
                            Rate-limiting rules from Lyft (Lyft 的速率限制規則)
```

[高層設計](./design)

在上面的速率限制規則中，單位設置為天，request_per_unit 設置為 5。這些參數定義了系統每天允許 5 條營銷消息。

## Detailed design (詳細設計)
上面給出的高層設計沒有回答以下問題：

- **Where are the rules stored? (規則存儲在哪裡？)**
- **How do we handle requests that are rate limited? (我們如何處理受速率限制的請求？)**

在本節中，我們將首先將高級架構擴展為其他幾個基本組件。我們還將詳細解釋每個組件，如下圖所示。

[速率限制器根據節流規則接受或拒絕請求](./detailed_design.jpg)

讓我們討論速率限制器詳細設計中存在的每個組件。

- **Rule database (規則資料庫)**：這是資料庫，由服務所有者定義的規則組成。每個規則指定特定客戶端在單位時間內允許的請求數量。

- **Rules retriever (規則檢索器)**：這是一個後台進程，定期檢查資料庫中規則的任何修改。如果對現有規則進行了任何修改，則更新規則緩存。

- **Throttle rules cache (節流規則緩存)**：緩存由從規則資料庫檢索到的規則組成。緩存服務速率限制器請求的速度比持久存儲快。結果，它提高了系統的性能。因此，當速率限制器收到針對 ID (鍵) 的請求時，它會根據緩存中的規則檢查 ID。

- **Decision-maker (決策者)**：此組件負責根據緩存中的規則做出決策。該組件基於下一課中討論的速率限制算法之一工作。

- **Client identifier builder (客戶端標識符構建器)**：此組件為從客戶端收到的請求生成唯一 ID。這可以是遠程 IP 地址、登錄 ID 或其他幾個屬性的組合，因此這裡不能使用定序器。此 ID 被視為在鍵值資料庫中存儲使用者資料的鍵。因此，將此鍵傳遞給決策者以進行進一步的服務決策。

如果超過預定義的限制，API 將返回 HTTP 響應代碼 429 Too Many Requests，並對請求應用以下策略之一：

- 丟棄請求並向客戶端返回特定響應，例如"請求過多"或"服務不可用"。
- 如果某些請求由於系統過載而受到速率限制，我們可以將這些請求保留在隊列中以供稍後處理。

### Request processing (請求處理)
收到請求後，客戶端標識符構建器識別請求並將其轉發給決策者。決策者確定請求所需的服務，然後根據允許的請求數量以及服務所有者提供的規則檢查緩存。如果請求不超過計數限制，則將其轉發給負責服務請求的請求處理器。

決策者根據節流算法做出決定。節流可以是硬的、軟的或彈性的。基於軟節流或彈性節流，允許請求超過定義的限制。這些請求要麼被服務，要麼保留在隊列中，並在資源可用時稍後服務。同樣，如果使用硬節流，則拒絕請求，並將響應錯誤發送回客戶端。

問題 (Question)
如果發生故障，速率限制器無法執行節流任務。在這種情況下，應該接受還是拒絕請求？

答案 (Answer)
在這種情況下，擬議的系統應遵守非功能需求，包括可用性和容錯性。因此，如果發生故障，速率限制器將無法執行。但是，默認決定是不對任何請求進行節流。原因是我們在不同的服務級別會有許多速率限制器。即使沒有其他速率限制器，負載平衡器也會在一定程度上執行此任務，如前所述。
```

### Race condition (競爭條件)
在高並發請求模式的情況下，存在競爭條件的可能性。當遵循"先獲取後設置"方法時會發生這種情況，其中檢索當前計數器，遞增，然後推回資料庫。在遵循這種方法時，可能會通過一些額外的請求，這可能會使遞增的計數器無效。這允許客戶端發送非常高速率的請求，從而繞過速率限制控制。為了避免此問題，可以使用鎖定機制，其中一個進程可以一次更新計數器，而其他進程等待鎖釋放。由於這種方法會導致潛在的瓶頸，因此會顯著降低性能並且無法很好地擴展。

另一種可以使用的方法是"先設置後獲取"方法，其中以非常高性能的方式遞增值，避免了鎖定方法。如果競爭最少，這種方法有效。但是，人們可能會使用其他方法，其中允許的配額分為多個地方並分擔負載，或者使用分片計數器來擴展方法。

```
注意：我們可以在高並發流量下使用分片計數器進行速率限制。通過增加分片數量，我們減少了寫入爭用。由於我們必須從所有分片收集計數器，因此我們的讀取可能會變慢。
```

### A rate limiter should not be on the client's critical path (速率限制器不應位於客戶端的關鍵路徑上)
讓我們假設一個實時場景，其中數百萬個請求訪問前端伺服器。每個請求都將檢索、更新並將計數推回相應的緩存。在所有這些操作之後，請求被發送以進行服務。如果有大量請求，這種方法可能會導致延遲。為了避免客戶端關鍵路徑中的大量計算，我們應該將工作分為離線和在線部分。

最初，當收到客戶端的請求時，系統只會檢查各個計數。如果小於最大限制，系統將允許客戶端的請求。在第二階段，系統離線更新相應的計數和緩存。對於少數請求，這不會對性能產生任何影響，但是對於數百萬個請求，這種方法會顯著提高性能。

讓我們通過一個例子來理解在線和離線更新方法。在下面的一組插圖中，當收到請求時，其 ID 被轉發到速率限制器，速率限制器將通過從緩存中檢索資料來檢查條件 if(request(ID).Count <= Max. Limit)。為簡單起見，假設其中一個請求 ID 為 101，即 request(ID) = 101。下表顯示了每個客戶端發出的請求數以及客戶端單位時間內可以發出的最大請求數。

```
Request ID     Maximum Limit    Count
100            5                 4
101            5                 3
```

如果條件為真，速率限制器將首先向前端伺服器響應允許信號。相應的計數和其他相關資訊在接下來的步驟中離線更新。速率限制器將更新的資料寫回緩存。遵循這種方法可以減少延遲並避免傳入請求可能引起的爭用。

## Conclusion (結論)
在本課中，我們討論了分佈式系統中速率限制器的設計。讓我們分析一下我們在上一課中承諾的非功能需求。

- **Availability (可用性)**：如果速率限制器發生故障，將有多個速率限制器可用於處理傳入的請求。因此，消除了單點故障。

- **Low latency (低延遲)**：我們的系統從緩存而不是資料庫中檢索和更新每個傳入請求的資料。首先，如果傳入請求不超過速率限制，則轉發它們，然後更新緩存和資料庫。

- **Scalability (可擴展性)**：可以根據定義限制內的傳入請求數量增加或減少速率限制器的數量。

現在，鑑於上述討論，我們的系統提供了高可用性、低延遲和可擴展性。
