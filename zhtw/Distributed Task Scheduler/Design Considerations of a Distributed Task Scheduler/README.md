# Design Considerations of a Distributed Task Scheduler (分佈式任務調度器的設計注意事項)
## Queueing (隊列)
分佈式隊列是調度器使用的一個主要構建模組。最簡單的調度方法是按先到先得的原則將任務推入隊列。如果集群 (雲) 中有 10,000 個節點 (資源)，則任務調度器會快速從隊列中提取任務並將其調度到節點上。但是，如果所有資源當前都很忙，那麼任務將需要在隊列中等待，小任務可能需要等待更長時間。

這種調度機制會影響系統的可靠性、可用性和任務的優先級。有些情況下我們希望緊急執行任務——例如，通知使用者其帳戶從無法識別的設備訪問的任務。因此，我們不能僅依靠先到先得來調度任務。相反，我們對任務進行分類並設置適當的優先級。我們的任務有以下三類：

- 不能延遲的任務。
- 可以延遲的任務。
- 需要週期性執行的任務 (例如，每 5 分鐘、每小時或每天)。

[基於任務類別的多個隊列](./multiqueues.jpg)

我們的系統確保非緊急隊列中的任務不會被餓死。一旦某個任務的延遲限制即將達到，它就會被移至緊急任務隊列，以便獲得服務。我們稍後將在本課中了解任務調度器如何實現優先級。

讓我們探討一些有助於調度器有效利用資源並為使用者提供可靠服務的參數。

## Execution cap (執行上限)
有些任務執行時間很長，會佔用資源並阻塞其他任務。執行上限是調度任務時需要考慮的重要參數。如果我們將資源完全分配給單個任務並等待該任務完成，則某些任務可能因為任務腳本中不讓其完成執行的錯誤而不會停止。我們讓客戶端為其任務設置執行上限。在指定時間後，我們應該停止任務執行，釋放資源，並將其分配給隊列中的下一個任務。如果任務執行因執行上限限制而停止，我們的系統會將這些實例通知相應的客戶端。客戶端需要針對此類情況採取適當的補救措施。

如果客戶端未設置執行上限，調度器將使用其默認上限作為殺死任務的最大允許時間。假設任務實際上需要更長時間——例如，如果我們正在訓練機器學習模型。在這種情況下，調度器可能需要多次暫停和恢復任務以適應其他任務。對於必須等待兩天才能使用資源兩秒鐘的短任務來說，這是不公平的。

雲提供商不能讓基本 (免費) 帳戶的任務無限期執行，因為使用其資源會向提供商收取一定費用。為了處理此類情況，會通知客戶端最大使用限制，以便他們可以處理長時間的任務執行。例如，客戶端可以設計他們的任務，以便在一段時間後進行檢查點並從該狀態加載以恢復進度，以防由於使用限制而從客戶端獲取資源。

```
Question
如果一個長任務執行了 90%，但在完成之前，執行該任務的機器發生故障怎麼辦？

Answer
任務調度器將在其他機器上重新執行該任務。任務需要是冪等的 (將在本課稍後討論)，或者它們應該能夠從以前的檢查點恢復其狀態。保存狀態後，我們可以在任何其他機器上恢復該任務的執行。這使我們的系統具有容錯能力並節省了我們的資源。
```

## Prioritization (優先級)
有些任務需要緊急執行。例如，在 Facebook 等社交應用程式中，使用者可以在緊急情況下 (例如地震) 標記自己安全。執行此活動的任務應及時執行，否則此功能對 Facebook 使用者毫無用處。向客戶發送電子郵件通知其帳戶被扣除了特定金額是另一個需要緊急執行的任務示例。

為了對任務進行優先級排序，任務調度器為每個任務維護一個延遲容忍度參數，並在接近其延遲容忍度時執行任務。延遲容忍度是任務執行可以延遲的最大時間量。延遲容忍時間最短的任務首先執行。通過使用延遲容忍度參數，我們可以推遲具有較長延遲容忍度值的任務，以便在高峰時段為緊急任務騰出空間。

```
Question
我們如何確定延遲容忍度的值？

Answer
由於各種應用程式中有不同類別的任務，應用程式所有者或客戶端可以根據任務類別自行設置或自動化這些值。例如，在 Facebook 等社交媒體應用程式中，我們可以生成動態消息、建議好友、允許使用者在災難後標記自己安全、發送有關直播活動的通知等等。在列出的任務中，優先任務應該是在地震期間標記人員安全並發送有關直播活動的通知。客戶端可以將這些任務的延遲容忍度值收緊到毫秒或幾秒，而像建議好友這樣的任務可以延遲幾天。

任務調度系統本身可以根據任務類別及其嚴重程度設置延遲容忍度值。

不同優先級有不同的成本 (例如，高優先級任務通常成本較高)，以便客戶可以仔細對任務進行分類。
```

## Resource capacity optimization (資源容量優化)
有時資源接近過載閾值 (例如，利用率高於 80%)。這稱為高峰時間。同一資源在非高峰時間可能處於空閒狀態。因此，我們必須考慮如何在非高峰時間更好地利用資源，以及如何在高峰時間保持資源可用。

有些任務不需要緊急執行。例如，在 Facebook 等社交應用程式中，建議好友並不是緊急任務。我們可以為此類任務建立一個單獨的隊列，並在非高峰時間執行它們。如果我們一直有比可用資源更多的工作要做，我們可能會遇到容量問題，為了解決這個問題，我們應該調試更多資源。雲提供商需要有一個目標資源需求比。當需求開始增加時，該比率將趨向於 0。如果該比率隨時間開始變化，提供商可能會決定調試更多或更少的資源。

## Task idempotency (任務冪等性)
如果任務執行成功，但由於某種原因機器未能發送確認，調度器將再次調度任務。任務再次執行，我們最終得到錯誤的結果，這意味著任務是非冪等的。下圖顯示了一個非冪等的例子：

[非冪等](./nonidempotency)

我們不希望在再次執行任務時改變最終結果。這在轉賬時的金融應用程式中至關重要。我們要求任務是冪等的。冪等任務無論執行多少次都會產生相同的結果。冪等任務的執行如下圖所示：

[冪等](./idempotent)

讓我們將上傳視頻到資料庫的任務設為冪等操作。如果上傳者沒有收到確認，我們不希望視頻在資料庫中重複。冪等性確保視頻不會重複。此屬性由開發人員在實現中添加，他們通過某種方式 (例如名稱) 識別視頻並覆蓋舊視頻。這樣，無論有人上傳多少次，最終結果都是一樣的。冪等性使我們能夠簡單地重新執行失敗的任務。

```
Question
我們應該如何處理由於任務負載中的無限循環而永遠無法完成的任務執行？

Answer
我們需要標記並殺死此類任務。因此，為此目的，我們可以設置時間限制。如果花費的時間超過指定的執行上限值，我們可以殺死任務。但是區分錯誤任務和長任務具有挑戰性。我們可以在應用程式級別處理它，客戶端通過在不同時間保存狀態來處理長任務。如果任務調度器殺死該任務 (假設該任務包含無限循環)，客戶端也可以從該狀態恢復。
```

## Schedule and execute untrusted tasks (調度和執行不受信任的任務)
在繼續之前，讓我們問自己一個問題：什麼是不受信任的任務，我們應該如何管理它們？

```
不受信任的任務是指任務腳本中可能存在某些惡意指令的任務，這些指令可能會影響其他任務的執行。受影響的任務可能是其他租戶的任務。不受信任的任務也可能損害操作系統或執行它們的資源。
```

程式有潛在的錯誤，並且可能有惡意意圖。在使用任務調度器時，我們應該注意不要讓一個任務對其他任務產生負面影響。如果我們提供基礎設施即服務，安全性是一個重要組成部分。這是因為租戶通過在共享環境中執行惡意代碼來損害彼此的任務變得更加容易。執行惡意代碼也會損壞我們的基礎設施。因此，我們需要牢記以下注意事項：

- 使用適當的身份驗證和資源授權。
- 考慮使用 docker 或虛擬機進行代碼沙盒化。
- 通過監控任務的資源利用率並限制 (或終止) 行為不良的任務，在任務之間使用性能隔離。

```
Question
當同一個任務多次失敗時會發生什麼？

Answer
我們可以使用死信隊列 (dead-letter queue) 功能來隔離重複失敗的任務。
```
