# Evaluation of a Distributed Task Scheduler's Design (評估分佈式任務調度器的設計)
## Availability (可用性)
我們設計中的第一個組件是速率限制器，它被適當複製並確保可用性。任務提交由多個節點完成。如果提交任務的節點發生故障，其他節點將取代它的位置。我們推送任務的隊列本質上也是分佈式的，確保了可用性。我們總是有可用的資源，因為我們會持續監控是否需要添加或刪除資源。設計中的每個組件都是分佈式的，使整個系統可用。

## Durability (持久性)
我們將任務存儲在持久性分佈式資料庫中，並在執行時間附近將任務推入隊列。一旦提交任務，它就會一直在資料庫中，直到執行為止。

## Scalability (可擴展性)
我們的任務調度器提供了可擴展性，因為任務提交器在我們的設計中是分佈式的。我們可以向集群添加更多節點以提交不斷增加的任務。然後將任務保存到分佈式關係資料庫中，這也是可擴展的。來自 RDB 的任務隨後被推送到分佈式隊列，該隊列可以隨著任務數量的增加而擴展。我們可以為不同類型的任務添加更多隊列。我們還可以根據資源與需求的比例添加更多資源。

## Fault tolerance (容錯性)
任務第一次發送執行時不會從隊列中刪除。如果執行失敗，我們會重試允許的最大嘗試次數。如果任務包含無限循環，我們會在指定時間後殺死任務並通知使用者。

## Bounded waiting time (有限等待時間)
我們不讓使用者無限期等待。我們對最大等待時間有限制。如果達到限制並且由於某種原因我們無法調度任務，我們會通知使用者並要求他們重試。

## Conclusion (結論)
我們討論了操作系統級任務調度器和資料中心級任務調度器之間的區別。我們解釋了資料中心級任務調度需要分佈式解決方案，因為有多個租戶和分散的資源。我們了解到隊列是任務調度器的主要構建模組。我們還使用了分佈式隊列，我們可以隨著任務數量的增加而擴展，以利用越來越多的資源。

本課幫助我們評估了 FIFO 隊列的問題。據觀察，任務調度器的主要工作是設置任務的優先級，我們為此使用了延遲容忍度參數。我們討論了任務調度器如何確定延遲容忍度值，並使用不同的分佈式資料庫來存儲任務詳細資訊。我們通過根據存儲在圖資料庫中的 DAG 運行任務，確保按順序執行依賴任務。根據任務數量 (或需求)，我們添加或刪除資源以優化容量。最後，我們使用了監控服務，在需要添加或刪除資源時提醒管理員。
