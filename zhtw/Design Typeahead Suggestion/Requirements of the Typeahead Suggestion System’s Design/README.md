# Requirements of the Typeahead Suggestion System’s Design (預輸入建議系統的設計需求)

## Requirements (需求)
在本課中，我們將研究設計預輸入建議系統所需的需求和估算資源。我們提出的設計應滿足以下需求。

### Functional requirements (功能需求)
系統應根據使用者在搜尋框中輸入的文字向使用者建議前 N 個 (比如說前十個) 頻繁且相關的術語。

### Non-functional requirements (非功能需求)
- **Low latency (低延遲)**：系統應在使用者輸入後實時顯示所有建議的查詢。延遲不應超過 200 毫秒。一項研究表明，兩次擊鍵之間的平均時間為 160 毫秒。因此，我們的建議時間預算應大於 160 毫秒，以提供實時響應。這是因為如果使用者輸入速度很快，他們已經知道要搜尋什麼，可能不需要建議。同時，我們的系統響應應大於 160 毫秒。但是，它不應該太高，因為在那種情況下，建議可能已經過時且不太有用。

- **Fault tolerance (容錯性)**：儘管一個或多個組件發生故障，系統應足夠可靠以提供建議。

- **Scalability (可擴展性)**：系統應支持隨著時間推移不斷增加的使用者數量。

## Resource estimation (資源估算)
如前所述，預輸入功能用於增強輸入查詢時的使用者體驗。我們需要設計一個在規模上類似於 Google 搜尋的系統。Google 每天收到超過 35 億次搜尋。設計這樣一個龐大的系統是一項具有挑戰性的任務，需要不同的資源。讓我們估算擬議系統的儲存和頻寬需求。

### Storage estimation (儲存估算)
假設在每天 35 億次查詢中，有 20 億次查詢是唯一的並且需要儲存。讓我們還假設每個查詢平均由 15 個字元組成，每個字元佔用 2 個位元組的儲存空間。根據此公式，我們將需要以下內容：

2 billion x 15 x 2 = 60GB 來儲存一天中進行的所有查詢。

每年所需的儲存空間：

60GB/day x 365 = 21.9TB/year

[預輸入建議系統的儲存需求](./storage.jpg)

### Bandwidth estimation (頻寬估算)
每天有 35 億次查詢到達我們的系統。假設使用者輸入的每個查詢平均長度為 15 個字元。

記住這一點，每天的字元讀取請求總數如下：

15 x 3.5 billion = 52.5 characters per day (每天 525 億個字元)。

每秒總讀取請求數：52.5B/86400 ≈ 0.607M characters/sec (每秒 60.7 萬個字元)。86,400 是每天的秒數。

由於每個字元佔用 2 個位元組，我們的系統需要的頻寬如下：

0.607M x 2 x 8 = 9.7Mb/sec (9.7 兆位/秒)。

9.7Mb/sec 是最大長度為 15 個字元的查詢的傳入頻寬需求。我們的系統會在使用者輸入每個字元後建議前十個長度與查詢長度大致相同的查詢。因此，傳出頻寬需求將變為以下內容：15 x 10 x 9.7Mb/sec = 1.46Gb/sec (1.46 吉位/秒)。

[預輸入建議系統所需的總頻寬](./bandwidth.jpg)

### Number of servers estimation (伺服器數量估算)
我們的系統將同時收到 607,000 個請求。因此，我們需要安裝許多伺服器以避免單個伺服器負擔過重。假設單個伺服器每秒可以處理 8,000 個查詢。因此，我們需要大約 76 台伺服器來處理 607,000 個查詢。

```
系統將在使用者輸入每個字元後建議查詢。因此，針對每秒 607,000 個字元，我們的系統每秒接收 607,000 或 60.7 萬個請求。
```

607K/8000 ≈ 76 servers (76 台伺服器)

在這裡，我們僅指應用程式伺服器的數量。為簡單起見，我們忽略了快取和資料庫伺服器的數量。實際數量高於 76，因為我們還需要冗餘伺服器來實現可用性。

## Building blocks we will use (我們將使用的構建塊)
預輸入建議系統的設計包括課程前幾章討論的以下構建塊：

[預輸入建議系統設計所需的構建塊](./bb.jpg)

- **Databases (資料庫)** 需要保存與查詢前綴相關的資料。
- **Load balancers (負載平衡器)** 需要在許多活動伺服器之間傳播傳入查詢。
- **Caches (快取)** 用於保存前 N 個建議以進行快速檢索。
