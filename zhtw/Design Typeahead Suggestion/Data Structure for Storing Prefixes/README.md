# Data Structure for Storing Prefixes (儲存前綴的資料結構)

## The trie data structure (Trie 資料結構)
在我們繼續討論預輸入建議系統的詳細設計之前，我們必須選擇一種高效的資料結構來儲存前綴。前綴是使用者輸入的一組字元。我們試圖解決的問題是，我們有許多字串，我們需要以允許使用者使用任何前綴搜尋它們的方式儲存這些字串。我們的服務建議與提供的前綴匹配的下一個單詞。假設我們的資料庫包含詞組 UNITED, UNIQUE, UNIVERSAL 和 UNIVERSITY。當使用者輸入“UNIV”時，我們的系統應該建議“UNIVERSAL”和“UNIVERSITY”。

應該有一種方法可以有效地儲存我們的資料並幫助我們進行快速搜尋，因為我們必須以最小的延遲處理大量請求。我們不能為此依賴資料庫，因為與從 RAM 讀取建議相比，從資料庫提供建議需要更長的時間。因此，我們需要在高效的資料結構中將我們的索引儲存在記憶體中。但是，為了持久性和可用性，此資料儲存在資料庫中。

```
回想一下封底計算一章，從 RAM 順序讀取 1MB 資料需要 9 微秒，而從 SSD 等持久儲存讀取需要 200 微秒。
```

Trie (發音為“try”) 是最適合我們需求的資料結構之一。Trie 是一種用於儲存詞組的樹狀資料結構，每個樹節點按順序儲存詞組中的一個字元。如果我們需要在 trie 中儲存 UNITED, UNIQUE, UNIVERSAL 和 UNIVERSITY，它看起來像這樣：

[UNITED, UNIQUE, UNIVERSAL 和 UNIVERSITY 的 trie](./trie1.jpg)

如果使用者輸入“UNIV”，我們的服務可以遍歷 trie 到達節點 V，以找到所有以該前綴開頭的術語——例如 UNIVERSAL, UNIVERSITY 等。

Trie 可以將僅存在單個分支的節點合併為一個，從而減少樹的深度。這也減少了遍歷時間，從而提高了效率。例如，上述 trie 的空間和時間效率模型如下：

## Track the top searches (追蹤熱門搜尋)
由於我們的系統會跟蹤熱門搜尋並返回熱門建議，因此我們將每個術語的搜尋次數儲存在 trie 節點中。假設使用者搜尋 UNITED 15 次，UNIQUE 20 次，UNIVERSAL 21 次，UNIVERSITY 25 次。為了向使用者提供熱門建議，這些計數存儲在這些術語終止的每個節點中。結果 trie 如下所示：

[顯示 UNITED, UNIQUE, UNIVERSAL 和 UNIVERSITY 搜尋頻率的 trie](./freq.jpg)

如果使用者輸入“UNI”，系統開始遍歷 UNI 根節點下的樹。在比較源自根節點的所有術語後，系統提供所有可能單詞的建議。由於單詞 UNIVERSITY 的頻率很高，它出現在頂部。同樣，單詞 UNITED 的頻率相對較低，因此它最後出現。如果使用者從建議列表中選擇 UNIQUE，則針對 UNIQUE 的數字增加到 21。

```
Question
我們通過合併具有單個分支的節點並減少級別數來減少遍歷 trie 的時間。還有其他方法可以最大限度地減少 trie 遍歷時間嗎？

Answer
減少 trie 遍歷時間的一一種方法是預先計算並保存節點中每個前綴的前十個 (或我們選擇的任何數量) 建議。這意味著系統無需在每次使用者在搜尋框中輸入“UNIVERS”時遍歷 trie，而是預先計算、排序並存儲前綴 UNIVERS 的解決方案——即 UNIVERSITY, UNIVERSAL 等——在攜帶前綴 UNIVERS 的節點內。但是，這種方法需要額外的空間來保存預計算的結果。
```

```
預計算：系統不是每次都遍歷樹，而是只遍歷樹一次，並將建議儲存在每個節點中，我們稱之為預計算建議。
```

## Trie partitioning (Trie 分區)
我們的目標是設計一個像 Google 這樣的系統，我們可以用它來每秒處理數十億次查詢。一台伺服器不足以處理如此大量的請求。除此之外，將所有前綴儲存在單個 trie 中對於系統的可用性、可擴展性和持久性來說並不是一個可行的選擇。一個好的解決方案是將 trie 拆分為多個 trie，以獲得更好的使用者體驗。

假設 trie 被分成兩部分，每部分都有一個副本用於持久性目的。所有以“A”到“M”開頭的前綴都儲存在 Server/01 上，副本儲存在 Server/02 上。同樣，所有以“N”到“Z”開頭的前綴都儲存在 Server/03 上，副本儲存在 Server/04 上。應該注意的是，這種簡單的技術並不總是能平均平衡負載，因為某些前綴的單詞更多，而另一些則更少。我們使用這種簡單的技術來理解分區。

我們可以將 trie 拆分成任意多個部分，以將負載分配到不同的伺服器上並實現所需的效能。

                Partitioned Trie (分區 Trie)
Prefixes (前綴)       Primary (主)        Secondary (輔)

A to M               Server/01            Server/02

N to Z               Server/03            Server/04
```

```
Question
前綴與其主輔儲存之間的映射將儲存在哪裡？誰將管理和引導對這些伺服器的請求？

Answer
在分散式系統中，可以使用由多個伺服器組成的多個集群來提供特定服務，我們使用像 ZooKeeper 這樣的集群管理器來儲存集群之間的映射。
```

### Process a query after partitioning (分區後處理查詢)
當使用者輸入查詢時，它會到達負載平衡器並轉發到應用程式伺服器之一。應用程式伺服器根據使用者輸入的前綴搜尋適當的 trie。例如，如果使用者輸入以“U”開頭的內容，它會訪問 Server/03 或 Server/04，因為兩者都儲存了以“U”開頭的前綴的 trie。


## Update the trie (更新 Trie)
每天數十億次的搜尋給我們帶來每秒數十萬次的查詢。因此，為每個查詢更新 trie 的過程非常耗費資源且耗時，並且可能會妨礙我們的讀取請求。這個問題可以通過在特定間隔後離線更新 trie 來解決。為了離線更新 trie，我們將查詢及其頻率記錄在雜湊表中，並定期聚合資料。在特定時間後，使用聚合資訊更新 trie。trie 更新後，所有以前的條目都從雜湊表中刪除。

         Prefixes and Their Frequencies Updated Periodically (定期更新的前綴及其頻率)
Prefix (前綴)       Time Interval (One Hour) (時間間隔 (一小時))          Frequency (頻率)

UNIVERSITY          1st hour (第 1 小時)                                  25

UNIVERSITY          2nd hour (第 2 小時)                                  60

UNIVERSITY          3rd hour (第 3 小時)                                  100
我們可以設置一個 MapReduce (MR) 作業來定期處理所有日誌資料，比如說每 15 分鐘一次。這些 MR 服務計算前 15 分鐘內所有搜尋短語的頻率，並將結果轉儲到像 Cassandra 這樣的資料庫中的雜湊表中。之後，我們可以進一步使用新資料更新 trie。我們可以用所有新單詞及其頻率更新 trie 的當前副本。我們應該離線執行此操作，因為我們的首要任務是向使用者提供建議，而不是讓他們等待。

```
MapReduce 是一個大數據處理引擎。
```

主要是，我們可以使用以下兩種方法更新 trie。

- 我們可以在每台伺服器上複製 trie 以離線更新它。之後，我們可以開始使用它進行建議並丟棄舊的。
- 另一種方法是有 trie 的一個主副本和幾個輔助副本。當主副本用於回答查詢時，我們可以更新輔助副本。一旦升級完成，我們也可以將輔助副本作為我們的主副本。然後我們可以升級我們以前的主副本，這樣它也能夠為流量提供服務。

```
Question
如果前綴頻率隨著時間的推移不斷增加，存儲它們的相應整數可能會溢出。我們如何管理這個問題？

Answer
我們可以通過將頻率映射到一個範圍 (比如說在 0 到 1,000 之間) 來歸一化頻率。或者，我們可以假設任何達到該閾值的前綴都處於排名的頂部，從而在達到特定閾值後停止任何進一步的新增。
```
