# Detailed Design of WhatsApp (WhatsApp 的詳細設計)
## Detailed design (詳細設計)
上一課討論的高層設計沒有回答以下問題：

- 如何在客戶端和伺服器之間創建通訊通道？
- 如何擴展高層設計以支援數十億使用者？
- 如何儲存使用者的資料？
- 如何識別訊息傳遞給哪個接收者？
為了回答所有這些問題，讓我們深入研究高層設計並詳細探討每個組件。讓我們從使用者如何與聊天伺服器建立連接開始。

### Connection with a WebSocket server (與 WebSocket 伺服器連接)
在 WhatsApp 中，每個活動設備都通過 WebSocket 協議連接到 WebSocket 伺服器。WebSocket 伺服器與所有活動 (在線) 使用者保持連接打開。由於一台伺服器不足以處理數十億台設備，因此應該有足夠的伺服器來處理數十億使用者。每個伺服器的職責是為每個在線使用者提供一個端口。伺服器、端口和使用者之間的映射儲存在位於資料儲存集群之上的 WebSocket 管理器中。在這種情況下，那是 Redis。

```
Question
為什麼在客戶端-伺服器通訊中首選 WebSocket 而不是 HTTP(S) 協議？

Answer
HTTP(S) 不會為伺服器保持連接打開以向客戶端發送頻繁資料。使用 HTTP(S) 協議，客戶端不斷請求伺服器的更新，通常稱為輪詢，這會佔用大量資源並導致延遲。WebSocket 在客戶端和伺服器之間保持持久連接。每當資料可用時，此協議立即將資料傳輸到客戶端。它提供雙向連接，用作從伺服器向客戶端發送非同步更新的通用解決方案。
```

### Send or receive messages (發送或接收訊息)
WebSocket 管理器負責維護活動使用者與分配給使用者的端口之間的映射。每當使用者連接到另一個 WebSocket 伺服器時，此資訊將在資料儲存中更新。

WebSocket 伺服器還與另一個稱為訊息服務的服務通訊。訊息服務是 Mnesia 資料庫集群之上的訊息存儲庫。訊息服務公開 API 以通過各種過濾器 (例如使用者 ID、訊息 ID 等) 接收訊息。

Mnesia database cluster (Mnesia 資料庫集群)

如前所述，WhatsApp 會短時間儲存訊息。因此，我們需要一個能夠儲存不斷增加的資料並應支援頻繁刪除操作的資料庫。為此，WhatsApp 使用名為 Mnesia 的基於 Erlang 的分散式 DBMS。該 DBMS 提供以下好處。

- Real-time key-value lookup (實時鍵值查找)
- High fault tolerance (高容錯性)
- Dynamic reconfiguration (動態重新配置)
- Complex objects (複雜對象)

```
[WebSocket 與 Mnesia 資料庫集群之上的訊息服務通訊]

現在，假設使用者 A 想向使用者 B 發送訊息。如上圖所示，兩個使用者連接到不同的 WebSocket 伺服器。系統執行以下步驟將訊息從使用者 A 發送到使用者 B：

1. 使用者 A 與其連接的相應 WebSocket 伺服器通訊。

2. 與使用者 A 關聯的 WebSocket 伺服器通過 WebSocket 管理器識別使用者 B 連接到的 WebSocket。如果使用者 B 在線，WebSocket 管理器會回應使用者 A 的 WebSocket 伺服器，表明使用者 B 已與其 WebSocket 伺服器連接。

3. 同時，WebSocket 伺服器將訊息發送到訊息服務，並將其儲存在 Mnesia 資料庫中，在該資料庫中按先進先出的順序處理。一旦這些訊息傳遞給接收者，它們就會從資料庫中刪除。

4. 現在，使用者 A 的 WebSocket 伺服器擁有使用者 B 與其自己的 WebSocket 伺服器連接的資訊。使用者 A 和使用者 B 之間的通訊通過他們的 WebSocket 伺服器開始。

5. 如果使用者 B 離線，訊息將保留在 Mnesia 資料庫中。每當他們上線時，所有發給使用者 B 的訊息都會通過推送通知傳遞。否則，這些訊息將在 30 天后永久刪除。

兩個使用者 (發送者和接收者) 都與 WebSocket 管理器通訊以找到對方的 WebSocket 伺服器。考慮兩個使用者之間可能存在持續對話的情況。這樣，可以對 WebSocket 管理器進行多次調用。為了最小化延遲並減少對 WebSocket 管理器的這些調用次數，每個 WebSocket 伺服器都會快取以下資訊：

- 如果兩個使用者都連接到同一台伺服器，則避免調用 WebSocket 管理器。

- 它快取有關哪個使用者連接到哪個 WebSocket 伺服器的最近對話資訊。

```
Question
如果使用者斷開連接並與另一台伺服器連接，快取中的資料將過時。考慮到這一點，WebSocket 伺服器應該快取資訊多長時間？

Answer
當使用者由於連接中的某些故障而斷開連接並重新連接到不同的 WebSocket 伺服器時，資訊將在 WebSocket 管理器中更新。WebSocket 管理器反過來使 WebSocket 伺服器使用的快取中的資料無效，並將更新的資料發送到相應的快取。因此，快取中的資訊將保留在那裡，直到它收到來自 WebSocket 管理器的無效訊號。
```


### Send or receive media files (發送或接收媒體文件)
到目前為止，我們已經討論了文本訊息的通訊。但是當使用者發送媒體文件時會發生什麼？通常，WebSocket 伺服器是輕量級的，不支援繁重的邏輯，例如處理媒體文件的發送和接收。我們有另一個稱為資產服務的服務，負責發送和接收媒體文件。

此外，發送媒體文件包括以下步驟：

1. 媒體文件在設備端進行壓縮和加密。

2. 壓縮和加密的文件發送到資產服務以將文件存儲在 blob 儲存中。資產服務分配一個與發送者通訊的 ID。資產服務還為每個文件維護一個雜湊，以避免 blob 儲存上的內容重覆。例如，如果使用者想要上傳 blob 儲存中已存在的圖像，則不會上傳該圖像。相反，相同的 ID 會轉發給接收者。

3. 資產服務通過訊息服務將媒體文件的 ID 發送給接收者。接收者使用 ID 從 blob 儲存下載媒體文件。

4. 如果資產服務收到大量針對某些特定內容的請求，則內容將加載到 CDN 上。

### Support for group messages (支援群組訊息)
WebSocket 伺服器不跟蹤群組，因為它們只跟蹤活動使用者。但是，在一個群組中，有些使用者可能在線，有些可能離線。對於群組訊息，以下三個主要組件負責將訊息傳遞給群組中的每個使用者：

- Group message handler (群組訊息處理器)
- Group message service (群組訊息服務)
假設使用者 A 想向具有某個唯一 ID (例如 Group/A) 的群組發送訊息。以下步驟解釋了發送到群組的訊息流：

1. 由於使用者 A 連接到 WebSocket 伺服器，它向訊息服務發送一條針對 Group/A 的訊息。

2. 訊息服務將訊息連同有關群組的其他特定資訊發送到 Kafka。訊息保存在那裡以供進一步處理。在 Kafka 術語中，群組可以是一個主題，發送者和接收者可以分別是生產者和消費者。

3. 現在，輪到群組服務負責了。群組服務將每個群組中使用者的所有資訊保存在系統中。它擁有關於每個群組的所有資訊，包括使用者 ID、群組 ID、狀態、群組圖標、使用者數量等。此服務位於 MySQL 資料庫集群之上，具有多個地理分佈的輔助副本。還存在一個 Redis 快取伺服器來快取來自 MySQL 伺服器的資料。地理分佈的副本和 Redis 快取都有助於減少延遲。

4. 群組訊息處理器與群組服務通訊以檢索 Group/A 使用者的資料。

5. 在最後一步中，群組訊息處理器遵循與 WebSocket 伺服器相同的過程，並將訊息傳遞給每個使用者。

End-to-end encryption (端對端加密)
與群組訊息服務類似，還有另一個稱為使用者服務的服務，用於跟蹤每個使用者。它包含與使用者相關的資料，例如姓名、個人資料圖片、狀態等。此服務位於 MySQL 資料庫之上，並利用快取存儲頻繁使用的資料。

在註冊時，WhatsApp 客戶端生成許多公私鑰對，包括用於身份的密鑰對、簽名的預密鑰和一批一次性預密鑰。這些密鑰用於不同目的。公鑰與使用者標識符一起存儲在與使用者服務關聯的資料庫中。每當發送者想要與接收者建立連接時，它也會向伺服器請求與接收者 ID 關聯的密鑰。私鑰僅存儲在客戶端的終端設備上。

One-to-one communication (一對一通訊)
為了安全通訊，發送者和接收者雙方的 WhatsApp 客戶端彼此建立成對加密會話。使用以下步驟創建會話：

發送者請求接收者設備的公開身份密鑰、簽名預密鑰和單個公開一次性預密鑰。一次性預密鑰僅使用一次。

WhatsApp 伺服器返回請求的接收者公鑰。

發送者生成一個臨時 Curve25519 密鑰對。

發送者使用自己的身份密鑰、臨時密鑰對和接收者的公鑰創建主密鑰。

發送者使用基於 HMAC 的密鑰派生函數 (HKDF) 從主密鑰創建另外兩個密鑰，稱為根密鑰和鏈密鑰。發送者在建立成對加密會話後開始向接收者發送訊息。接收者根據第一條接收訊息標頭中存在的資訊創建相同的會話。

建立會話後，根據根密鑰和鏈密鑰生成一個 80 位元組的訊息密鑰。訊息密鑰用於訊息的加密和認證。

Group communication (群組通訊)
WhatsApp 群組中的通訊由上一節關於一對一通訊中討論的相同過程處理。使用的發送者密鑰由信令訊息協議生成，並使用成對加密會話與群組每個成員的設備共享。發送到群組的訊息使用發送者密鑰加密。

群組中的通訊由 Kafka 指導，其中群組中的每個使用者訂閱相關主題 (具有關聯訊息隊列的群組)。然後以扇出訊息模式傳遞訊息，其中訊息從單個發送者傳遞給多個接收者。

Simultaneous maintenance of WhatsApp sessions on multiple devices (在多個設備上同時維護 WhatsApp 會話)
WhatsApp 上的每個設備都由設備身份密鑰標識。如果使用者使用多個設備 (一個主設備和幾個其他配套設備)，每個設備身份密鑰都會存儲在 WhatsApp 伺服器上的使用者帳戶中。當 WhatsApp 伺服器收到使用者的訊息時，它會多次將訊息傳輸到與使用者帳戶關聯的每個設備。

同樣，使用者使用的每個設備都有自己的一組加密密鑰。如果一個配套設備的一組密鑰被洩露，攻擊者將無法看到與其他設備通訊的訊息。
```
