# How the Domain Name System Works (域名系統如何工作)
通過本課，我們將回答以下問題：

```
如何使用各種類型的 DNS 名稱伺服器形成 DNS 層次結構？

如何在互聯網的不同級別執行緩存以減輕 DNS 基礎設施的查詢負擔？

DNS 基礎設施的分佈式特性如何有助於其健壯性？
```
讓我們開始吧。

## DNS hierarchy (DNS 層次結構)
如前所述，DNS 不是單個接受請求並響應使用者查詢的伺服器。這是一個在不同層次結構中具有名稱伺服器的完整基礎設施。

```
名稱伺服器可以響應使用者的 DNS 查詢
```

DNS 層次結構中主要有四種類型的伺服器：

```
DNS 解析器：解析器啟動查詢序列並將請求轉發到其他 DNS 名稱伺服器。通常，DNS 解析器位於使用者網絡的前提下。但是，正如我們稍後將看到的，DNS 解析器還可以通過緩存技術滿足使用者的 DNS 查詢。這些伺服器也可以稱為本地或默認伺服器。

根級名稱伺服器：這些伺服器接收來自本地伺服器的請求。根名稱伺服器維護基於頂級域名的名稱伺服器，例如 .com、.edu、.us 等。例如，當使用者請求 educative.io 的 IP 地址時，根級名稱伺服器將返回包含 .io 域 IP 地址的頂級域名 (TLD) 伺服器列表。

頂級域名 (TLD) 名稱伺服器：這些伺服器保存權威名稱伺服器的 IP 地址。查詢方將獲得屬於該組織權威伺服器的 IP 地址列表。

權威名稱伺服器：這些是組織的 DNS 名稱伺服器，提供 Web 或應用程式伺服器的 IP 地址。
```

[用於解析域名/主機名的 DNS 層次結構](./arch.jpg)

```
Question
DNS 名稱是如何處理的？例如，educative.io 是從左到右還是從右到左處理？

Answer
與 UNIX 文件從左到右處理不同，DNS 名稱是從右到左處理的。在 educative.io 的情況下，解析器將首先解析 .io 部分，然後是 educative，依此類推。

然而，從視覺上看，DNS 層次結構可以看作是一棵樹。
```

### Iterative versus recursive query resolution (迭代與遞歸查詢解析)

執行 DNS 查詢有兩種方法：

```
迭代：本地伺服器向根伺服器、TLD 伺服器和權威伺服器請求 IP 地址。

遞歸：最終使用者請求本地伺服器。本地伺服器進一步請求根 DNS 名稱伺服器。根名稱伺服器將請求轉發到其他名稱伺服器。
```

在下圖 (左) 中，從本地/ISP 伺服器的角度來看，DNS 查詢解析是迭代的：

```
注意：通常，首選迭代查詢以減少 DNS 基礎設施上的查詢負擔。
```


## Caching (緩存)
緩存是指頻繁請求的資源記錄的臨時存儲。記錄是 DNS 資料庫中的資料單元，顯示名稱到值的綁定。緩存減少了使用者的響應時間並減少了網絡流量。當我們在不同層次結構中使用緩存時，它可以減輕 DNS 基礎設施的大量查詢負擔。緩存可以在瀏覽器、操作系統、使用者網絡內的本地名稱伺服器或 ISP 的 DNS 解析器中實現。

## DNS as a distributed system (DNS 作為分佈式系統)
雖然 DNS 層次結構促進了我們今天所知的分佈式互聯網，但它本身就是一個分佈式系統。DNS 的分佈式特性具有以下優點：

```
它避免成為單點故障 (SPOF)。

它實現了低查詢延遲，因此使用者可以從附近的伺服器獲得響應。

它在維護和更新或升級期間獲得了更高程度的靈活性。例如，如果一個 DNS 伺服器關閉或負擔過重，另一個 DNS 伺服器可以響應使用者查詢。
```
有 13 個邏輯根名稱伺服器 (以字母 A 到 M 命名)，其許多實例遍布全球。這些伺服器由 12 個不同的組織管理。

現在讓我們回顧一下 DNS 如何實現可擴展性、可靠性和一致性。


### Highly scalable (高度可擴展)
由於其分佈式特性，DNS 是一個高度可擴展的系統。大約有 1,000 個複製的 13 個根級伺服器實例戰略性地位於世界各地，以處理使用者查詢。工作勞動力分配給 TLD 和根伺服器來處理查詢，最後由組織自己管理的權威伺服器使整個系統工作。如上面的 DNS 層次結構樹所示，不同的服務處理樹的不同部分，從而實現系統的可擴展性和可管理性。

### Reliable (可靠)
DNS 成為可靠系統的三個主要原因：

```
緩存：緩存是在瀏覽器、操作系統和本地名稱伺服器中完成的，ISP DNS 解析器也維護著經常訪問的服務的豐富緩存。即使某些 DNS 伺服器暫時關閉，也可以提供緩存記錄以使 DNS 成為可靠的系統。

伺服器複製：DNS 擁有每個邏輯伺服器的複製副本，系統地分佈在全球各地，以低延遲滿足使用者請求。冗餘伺服器提高了整個系統的可靠性。

協議：儘管許多客戶端通過去可靠的使用者資料報協議 (UDP) 使用 DNS，但 UDP 也有其優點。UDP 快得多，因此提高了 DNS 性能。此外，互聯網服務的可靠性自問世以來已有所提高，因此 UDP 通常優於 TCP。如果 DNS 解析器沒有收到對前一個請求的回覆，它可以重新發送 UDP 請求。此請求-響應僅需要一次往返，與需要在資料交換前進行三次握手的 TCP 相比，延遲更短。
```

```
Question
如果網絡擁塞會發生什麼？DNS 應該繼續使用 UDP 嗎？

Answer
通常，DNS 使用 UDP。但是，當 DNS 消息大小超過 512 字節的原始資料包大小時，它可以使用 TCP。這是因為大尺寸資料包在擁塞的網絡中更容易損壞。DNS 始終使用 TCP 進行區域傳輸。

由於隱私原因，一些客戶端更喜歡通過 TCP 使用 DNS 以採用傳輸層安全性。
```

### Consistent (一致性)
DNS 使用各種協議在層次結構中的複製伺服器之間更新和傳輸資訊。DNS 犧牲強一致性來實現高性能，因為與寫入相比，從 DNS 資料庫讀取資料的頻率更高。但是，DNS 提供最終一致性並懶惰地更新複製伺服器上的記錄。通常，在互聯網上的 DNS 伺服器上更新記錄可能需要幾秒鐘到三天時間。在不同 DNS 集群之間傳播資訊所需的時間取決於 DNS 基礎設施、更新的大小以及正在更新 DNS 樹的哪個部分。

一致性也會因為緩存而受到影響。由於權威伺服器位於組織內部，因此如果組織發生伺服器故障，可能會在權威伺服器上更新某些資源記錄。因此，默認/本地和 ISP 伺服器上的緩存記錄可能已過時。為了緩解此問題，每個緩存記錄都有一個過期時間，稱為生存時間 (TTL)。

```
TTL 是指查詢方可以緩存記錄的時間量。TTL 值以秒為單位報告。
```

```
Question
為了保持高可用性，TTL 值應該大還是小？

Answer
為了保持高可用性，TTL 值應該很小。這是因為如果有任何伺服器或集群發生故障，組織可以立即更新資源記錄。使用者僅在 TTL 未過期的時間內會遇到不可用情況。但是，如果 TTL 很大，組織將更新其資源記錄，而使用者將繼續 ping 很久以前崩潰的過時伺服器。渴望高可用性的公司將 TTL 值保持在低至 120 秒。因此，即使發生故障，最大停機時間也只有幾分鐘。
```

## Test it out (測試)
讓我們運行幾個命令。點擊終端以執行以下命令。在終端中複製以下命令以運行它們。研究命令的輸出：
```

dig www.google.com
```

### The nslookup output (nslookup 輸出)
非權威回答，顧名思義，是由非 Google 權威伺服器的伺服器提供的回答。它不在 Google 維護的權威名稱伺服器列表中。那麼，答案從哪裡來？答案由配置為回覆我們 DNS 查詢的二手、三手和四手名稱伺服器提供——例如，我們的大學或辦公室 DNS 解析器、我們的 ISP 名稱伺服器、我們 ISP 的 ISP 名稱伺服器等。簡而言之，它可以被視為 Google 權威名稱伺服器響應的緩存版本。如果我們嘗試多個域名，我們會意識到我們大多數時候都會收到緩存響應。

如果我們多次運行相同的命令，我們將收到相同的 IP 地址列表，但每次的順序都不同。原因是 DNS 間接地執行負載平衡。這是一個重要的術語，我們將在接下來的課程中熟悉它。

### The dig output (dig 輸出)
查詢時間：4 毫秒表示從 DNS 伺服器獲得響應所需的時間。由於各種原因，這些數字在我們的情況下可能有所不同。

ANSWER SECTION 中的 300 值表示緩存在 DNS 解析器中維護的秒數。這意味著 Google 的 ADNS 保持 5 分鐘 (300秒/60) 的 TTL 值。

```
注意：我們邀請您測試不同服務的 TTL 和查詢時間以加強您的理解。您可以使用上面的終端進行此操作。
```

```
Question
如果我們需要 DNS 告訴我們要到達哪個 IP 才能訪問網站或服務，我們如何知道 DNS 解析器的 IP 地址？(這看起來像是一個先有雞還是先有蛋的問題！)

Answer
最終使用者的操作系統具有包含 DNS 解析器 IP 地址的配置文件 (在 Linux 中為 /etc/resolv.conf)，這些解析器反過來為它們獲取所有資訊。(通常，DHCP 提供默認的 DNS 解析器 IP 地址以及其他配置。) 終端系統請求 DNS 解析任何 DNS 查詢。DNS 解析器安裝了特殊軟件以通過 DNS 基礎設施解析查詢。根伺服器的 IP 地址在特殊軟件中。通常，Berkeley Internet Name Domain (BIND) 軟件用於 DNS 解析器。InterNIC 維護著 13 個根伺服器的更新列表。
```
因此，我們通過向每個解析器播種根 DNS 伺服器 (其 IP 很少更改) 的先驗知識來打破先有雞還是先有蛋的問題。
