# Advanced Details of Load Balancers (負載平衡器的高級細節)
本課將重點介紹本地負載平衡器中使用的一些著名算法。我們還將了解負載平衡器如何連接以形成層次結構，在不同層級的 LB 之間共享工作。

## Algorithms of load balancers (負載平衡器的算法)
負載平衡器根據算法分發客戶端請求。下面給出了一些著名的算法：

```
循環調度：在此算法中，每個請求都以重複的順序方式轉發到池中的伺服器。

加權循環：如果某些伺服器具有更高的服務客戶端請求的能力，那麼首選使用加權循環算法。在加權循環算法中，每個節點都分配有一個權重。LB 根據節點的權重轉發客戶端的請求。權重越高，分配的數量越多。

最少連接：在某些情況下，即使所有伺服器都具有相同的服務客戶端的能力，某些伺服器上的負載不均勻仍然是可能的。例如，某些客戶端的請求可能需要更長的時間才能服務。或者某些客戶端可能在同一連接上有後續請求。在這種情況下，我們可以使用最少連接等算法，其中新到達的請求被分配給現有連接較少的伺服器。在這種情況下，LB 保持現有連接的數量和映射的狀態。我們將在本課後面詳細討論狀態維護。

最少響應時間：在對性能敏感的服務中，需要最少響應時間等算法。該算法確保請求具有最少響應時間的伺服器來為客戶端提供服務。

IP 哈希：某些應用程式根據使用者的 IP 地址向其提供不同級別的服務。在這種情況下，執行 IP 地址哈希以將使用者的請求分配給伺服器。

URL 哈希：有可能應用程式中的某些服務僅由特定伺服器提供。在這種情況下，請求 URL 服務的客戶端被分配給特定的集群或一組伺服器。URL 哈希算法用於這些場景。
```

還有其他算法，如隨機或加權最少連接算法。

### Static versus dynamic algorithms (靜態與動態算法)
算法可以是靜態的或動態的，具體取決於機器的狀態。讓我們分別看看每個類別：

```
靜態算法不考慮伺服器的變化狀態。因此，任務分配是根據有關伺服器配置的現有知識執行的。當然，這些算法並不複雜，它們在所有請求到達的單個路由器或商用機器中實現。

動態算法是考慮伺服器當前或最近狀態的算法。動態算法通過與伺服器通信來維護狀態，這增加了通信開銷。狀態維護使算法的設計更加複雜。
```

動態算法需要不同的負載平衡伺服器相互通信以交換資訊。因此，動態算法可以是模塊化的，因為沒有單個實體會做出決策。雖然這增加了動態算法的複雜性，但它能改善轉發決策。最後，動態算法監控伺服器的健康狀況，並且只將請求轉發給活動伺服器。

```
注意：在實踐中，動態算法提供更好的結果，因為它們維護服務主機的狀態，因此值得付出努力和復雜性。
```

### Stateful versus stateless LBs (有狀態與無狀態 LB)
雖然需要靜態和動態算法來考慮託管伺服器的健康狀況，但維護狀態以保存不同客戶端與託管伺服器的會話資訊。

如果會話資訊未保存在較低層 (分佈式緩存或資料庫)，則使用負載平衡器來保存會話資訊。下面，我們描述了通過 LB 處理會話維護的兩種方法：

Stateful (有狀態)
Stateless (無狀態)
```

#### Stateful load balancing (有狀態負載平衡)
顧名思義，有狀態負載平衡涉及維護在客戶端和託管伺服器之間建立的會話狀態。有狀態 LB 將狀態資訊納入其算法以執行負載平衡。

本質上，有狀態 LB 保留將傳入客戶端映射到託管伺服器的資料結構。有狀態 LB 增加了複雜性並限制了可擴展性，因為所有客戶端的會話資訊都在所有負載平衡器中維護。也就是說，負載平衡器彼此共享其狀態資訊以做出轉發決策。

[有狀態負載平衡](./stateful.jpg)

#### Stateless load balancing (無狀態負載平衡)
無狀態負載平衡不維護任何狀態，因此速度更快且重量更輕。無狀態 LB 使用一致性哈希來做出轉發決策。但是，如果基礎設施發生變化 (例如，新的應用程式伺服器加入)，無狀態 LB 可能不如有狀態 LB 有彈性，因為僅靠一致性哈希不足以將請求路由到正確的應用程式伺服器。因此，除了與一致性哈希一起，可能仍然需要本地狀態。

[使用哈希桶將請求映射到終端伺服器的無狀態負載平衡器](./hash.jpg)

因此，跨不同負載平衡器維護的狀態被視為有狀態負載平衡。而負載平衡器內部維護以供內部使用的狀態被假定為無狀態負載平衡。

## Types of load balancers (負載平衡器的類型)
根據需求，負載平衡可以在開放系統互連 (OSI) 層的網絡/傳輸層和應用層執行。

```
第 4 層負載平衡器：第 4 層是指基於 TCP 和 UDP 等傳輸協議執行的負載平衡。這些類型的 LB 維護與客戶端的連接/會話，並確保相同的 (TCP/UDP) 通信最終被轉發到相同的後端伺服器。儘管 TLS 終止在第 7 層 LB 上執行，但某些第 4 層 LB 也支持它。

第 7 層負載平衡器：第 7 層負載平衡器基於應用層協議的資料。可以根據 HTTP 標頭、URL、cookie 和其他特定於應用程式的資料 (例如使用者 ID) 做出應用程式感知的轉發決策。除了執行 TLS 終止外，這些 LB 還可以承擔限制使用者速率、HTTP 路由和標頭重寫等責任。
```

```
注意：第 7 層負載平衡器在檢查方面很聰明。但是，第 4 層負載平衡器在處理方面更快。例如，Google為其雲平台開發了一種名為 Maglev 的高性能分佈式負載平衡器。
```

## Load balancer deployment (負載平衡器部署)
我們討論了在不同 OSI 層執行負載平衡的權衡。然而，實際上，單層 LB 對於大型資料中心來說是不夠的。事實上，多層負載平衡器協調以做出明智的轉發決策。傳統資料中心可能具有三層 LB，如下所示：

[典型資料中心的三層負載平衡器](./3tiers.jpg)

### Tier-0 and tier-1 LBs (第 0 層和第 1 層 LB)
如果 DNS 可以被視為第 0 層負載平衡器，那麼等價多路徑 (ECMP) 路由器就是第 1 層 LB。從 ECMP 的名稱可以明顯看出，該層根據 IP 或其他一些算法 (如循環或加權循環) 分配傳入流量。第 1 層 LB 將在通往更高等級負載平衡器的不同路徑之間平衡負載。

ECMP 路由器在更高級別 LB 的水平可擴展性中起著至關重要的作用。

### Tier-2 LBs (第 2 層 LB)
第二層 LB 包括第 4 層負載平衡器。第 2 層 LB 確保對於任何連接，所有傳入的數據包都被轉發到相同的第 3 層 LB。為了實現這一目標，可以使用像一致性哈希這樣的技術。但在基礎設施發生任何變化的情況下，一致性哈希可能還不夠。因此，我們必須維護本地或全球狀態，正如我們將在本課接下來的部分中看到的那樣。

第 2 層負載平衡器可以被視為第 1 層和第 3 層 LB 之間的粘合劑。如果不包括第 2 層 LB，在故障或 LB 動態擴展的情況下可能會導致錯誤的轉發決策。

### Tier-3 LBs (第 3 層 LB)
第 7 層 LB 在第 3 層提供服務。由於這些 LB 與後端伺服器直接接觸，因此它們在 HTTP 級別執行伺服器的健康監控。該層通過在健康後端伺服器集中均勻分發請求來實現可擴展性，並通過直接監控伺服器的健康狀況來提供高可用性。該層還通過處理 TCP 擁塞控制協議、路徑 MTU (最大傳輸單元) 的發現、客戶端和後端伺服器之間的應用協議差異等低級別細節來減輕終端伺服器的負擔。這個想法是將計算和資料服務留給應用程式伺服器，並有效地利用負載平衡商用機器執行瑣碎的任務。在某些情況下，第 7 層 LB 與服務主機處於同一級別。

```
TCP 利用擁塞窗口來估計連接中正在傳輸的數據包數量，以避免網絡擁塞。兩個著名的 TCP 擁塞協議是 Tahoe 和 Reno。
```

```
路徑 MTU 是源可以在網絡上發送的最大數據包大小，超過該大小將發生數據包分片。此數字等於網絡路徑上的最小 MTU。
```

```
總而言之，第 1 層在負載平衡器本身之間平衡負載。第 2 層在出現故障的情況下實現從第 1 層到第 3 層的平滑過渡，而第 3 層在後端伺服器之間進行實際的負載平衡。每一層都執行其他任務以減輕終端伺服器的負擔。
```

## Implementation of load balancers (負載平衡器的實現)
根據傳入請求的數量、組織和特定於應用程式的需求，可以實施不同種類的負載平衡器：

### Hardware load balancers (硬件負載平衡器)
負載平衡器在 20 世紀 90 年代作為硬件設備引入。硬件負載平衡器作為獨立設備工作，而且相當昂貴。儘管如此，它們具有性能優勢，並且能夠處理大量並發使用者。基於硬件的解決方案的配置是有問題的，因為它需要額外的人力資源。因此，即使對於負擔得起的大型企業來說，它們也不是首選解決方案。硬件負載平衡器可能存在可用性問題，因為在發生故障時需要額外的硬件來進行故障轉移。最後，硬件 LB 可能具有更高的維護/運營成本和兼容性問題，使其靈活性降低。更不用說硬件 LB 也有供應商鎖定。

### Software load balancers (軟件負載平衡器)
由於其靈活性、可編程性和成本效益，軟件負載平衡器正變得越來越流行。這完全是可能的，因為它們是在商用硬件上實現的。隨著需求的增長，軟件 LB 可以很好地擴展。可用性對於軟件 LB 來說不是問題，因為在商用硬件上實施影子負載平衡器所需的額外成本很小。此外，軟件 LB 可以提供預測分析，有助於為未來的流量模式做準備。

### Cloud load balancers (雲負載平衡器)
隨著雲計算領域的出現，引入了負載平衡即服務 (LBaaS)。這是雲擁有者提供負載平衡服務的地方。使用者根據其使用情況或與雲提供商的服務級別協議 (SLA) 付費。基於雲的 LB 不一定取代本地內部部署負載平衡設施，但它們可以在不同區域之間執行全球流量管理。此類負載平衡器的主要優點包括易於使用、管理、計量成本、使用方面的靈活性、審計和監控服務以改善業務決策。下面給出了一個基於雲的 LB 如何提供 GSLB 的示例：
```

## Conclusion (結論)
LB 從最初以硬件形式出現以來，已經走過了漫長的道路，成為雲中提供的服務。它們是任何企業級服務的關鍵組成部分。託管伺服器的水平可擴展性總是需要一個良好的負載平衡層，能夠提供負載平衡、會話維護、TLS 卸載、服務發現等。
