# Prerequisites of a Monitoring System (監控系統的先決條件)
## Monitoring: metrics and alerting (監控：指標和警報)
一個好的監控系統需要明確定義測量什麼以及使用什麼單位 (指標)。監控系統還需要定義所有指標的閾值，並且能夠在值超出可接受範圍時通知適當的利益相關者 (警報)。了解我們的基礎設施和系統的狀態可確保服務穩定性。如果支持團隊可以訪問有關部署的健康狀況和性能的資訊，他們就可以更快速、更自信地響應問題。收集測量值、顯示資料並在出現問題時發出警告的監控系統對支持團隊很有幫助。

為了進一步了解指標、警報及其與監控的聯繫，我們將回顧它們的重要性、潛在的好處以及我們可能想要跟踪的資料。

```
Question
處理 IT 基礎設施故障的傳統方法有哪些？

Answer
處理 IT 基礎設施故障的兩種傳統方法是被動和主動方法。

在被動方法中，是在故障發生後採取糾正措施。在這種方法中，即使 DevOps 採取快速行動查找錯誤原因並及時處理故障，也會導致停機。因此，被動方法會導致系統停機，這對於持續運行的應用程式通常是不可取的。

在主動方法中，是在故障發生之前採取主動措施。因此，它可以防止停機和相關損失。主動方法致力於預測系統故障，以便採取糾正措施來避免故障。這種方法通過防止停機提供了更好的可靠性。

在現代服務中，完全避免問題是不可能的。在巨大的資料中心和網絡部署中，總會有一些東西發生故障。目標是及早發現即將發生的問題，並以服務故障對最終使用者不可見的方式設計系統。
```

## Metrics (指標)
指標客觀地定義了我們應該測量什麼以及什麼單位是合適的。指標值提供了對任何時間點系統的洞察。例如，Web 伺服器每秒處理一定量流量的能力或其加入 Web 伺服器池的能力是與組件的特定用途或活動相關的高級資料的示例。另一個例子可以是根據吞吐量 (每秒兆位) 和延遲 (往返時間) 來衡量網絡性能。我們需要在性能損失最小的情況下收集指標值。我們可以使用使用者感知的延遲或計算資源量來衡量這種損失。

跟踪作業系統使用的物理資源數量的數值可能是一個很好的起點。如果我們有監控系統，我們無需做太多額外工作即可獲取有關處理器負載、CPU 統計資訊 (如快取命中和未命中)、作業系統和進程的 RAM 使用情況、頁面錯誤、磁碟空間、磁碟讀寫延遲、交換空間使用情況等的資料。許多 Web 伺服器、資料庫伺服器和其他軟體提供的指標有助於我們確定一切是否運行順利。

我們使用 top 命令查看 Linux 進程。運行此命令將打開運行系統的交互式視圖，其中包含系統摘要和進程或線程列表。默認視圖具有以下內容：

- 在頂部，我們可以看到機器已開機多長時間、登錄了多少使用者以及過去幾分鐘機器的平均負載。

- 在下一行，我們可以看到機器上運行的任務的狀態 (運行、睡眠或停止)。

- 接下來，我們有 CPU 消耗值。

- 最後，我們有一個物理內存的概覽，其中有多少是空閒的、已用的、緩衝的或可用的。

現在，讓我們採取以下步驟來查看 CPU 使用率的變化：

### Populate the metrics (填充指標)
為了全球監控和警報的目的，指標在邏輯上應該是集中的。獲取指標對監控系統至關重要。根據使用者的偏好，指標可以被推送到監控系統，也可以被拉取到監控系統中。

在這裡，我們現在面臨一個基本的設計挑戰：我們是利用推 (push) 還是拉 (pull)？伺服器應該主動發送指標值，還是只暴露一個端點並被動等待查詢？

在拉取策略中，每個受監控的伺服器只需要將指標存儲在內存中並將其發送到暴露的端點。暴露的端點允許監控應用程式自行獲取指標。發送過多資料或發送資料過於頻繁的伺服器不會使監控系統過載。監控系統將按照自己的時間表拉取資料。

但在其他情況下，推送可能是有益的，例如當防火牆阻止監控系統直接訪問伺服器時。監控系統有能力調整有關要收集的資料以及伺服器和交換機應推送資料的時間間隔的全局配置。

推和拉的術語可能會令人困惑。每當我們討論推或拉策略時，我們都會從監控系統的角度來考慮。也就是說，要麼系統從應用程式中拉取指標值，要麼指標被推送到監控系統。為了避免混淆，我們將堅持監控系統的觀點。

```
Question
日誌記錄是在軟體系統中保留事件記錄的行為。它如何幫助監控？

Answer
在日誌記錄中，應用程式伺服器將資訊記錄到文件中。這些資訊可以是 CPU 使用率、應用程式相關資訊以及我們認為在遇到問題時回溯或調試文件所需的其他相關屬性。我們可以根據日誌中記錄的值填充我們的指標。

日誌和指標都有助於監控服務。但這並不總是正確的，因為處理日誌資訊需要時間。在實時情況下，我們需要迅速採取行動以儘早發現問題。因此，日誌記錄也是指標的輸入之一。日誌記錄只是收集資訊的一種機制，監控系統可以使用它來收集必要的資訊。

日誌記錄還可以幫助將資料暫時保存在伺服器上，以吸收任何瞬間的資料峰值或解耦資料生成和監控系統。
```

### Persist the data (持久化資料)
弄清楚如何存儲來自受監控伺服器的指標很重要。一個集中的內存指標存儲庫可能就足夠了。然而，對於一個有數百萬事物需要監控的大型資料中心來說，將有大量的資料需要存儲，而時序資料庫可以在這方面提供幫助。

時序資料庫有助於保持持久性，這是一個重要因素。如果在監控系統中沒有事件的歷史視圖，它就不是很有用。具有時間戳值的樣本按時間順序存儲。因此，整個指標的時間線可以以時間序列的形式顯示。

```
時間序列資料是連續的，時序資料庫 (TSDB) 允許存儲與時間戳關聯的資料。使用 TSDB 是存儲和檢索大量帶時間戳資料的有效方法。
```

### Application metrics (應用程式指標)
我們可能需要添加代碼或 API 來為其他組件 (尤其是我們自己的應用程式) 公開我們關心的指標。我們在應用程式中嵌入日誌記錄或監控代碼 (稱為代碼插樁)，以收集感興趣的資訊。

整體查看指標可以揭示我們的系統性能如何以及它們的健康狀況如何。監控系統利用這些輸入來生成我們環境的綜合視圖，自動響應變化 (例如，如果應用程式流量增加，則調試更多 EC2 實例)，並在必要時向人類發出警告。指標是系統測量值，允許分析歷史趨勢、相關性和性能、消耗或錯誤率的變化。

## Alerting (警報)
警報是監控系統的一部分，它響應指標值的變化並採取行動。警報定義有兩個組成部分：基於指標的條件或閾值，以及當值超出允許範圍時採取的行動。
