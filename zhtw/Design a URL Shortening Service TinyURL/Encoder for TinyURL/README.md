# Encoder for TinyURL (TinyURL 的編碼器)

## Introduction (介紹)
我們已經詳細討論了短網址生成器 (SUG) 的整體設計，但有兩個方面需要更多澄清：

1. 編碼器如何提高短網址的可讀性？
2. 短網址生成中的定序器和 base-58 編碼器有什麼關係？

### Why to use encoding (為什麼使用編碼)
我們的定序器生成一個 base-10 的 64 位 ID，它可以轉換為 base-64 短網址。Base-64 是字母數字字符串生成中最常見的編碼。然而，在堅持使用 base-64 來解決這個設計問題時存在一些固有問題：生成的短網址可能會因為相似字符而出現可讀性問題。字符如 O (大寫 o) 和 0 (零)，I (大寫 I) 和 l (小寫 L) 可能會混淆，而像 + 和 / 這樣的字符應該避免，以防止與其他系統相關的編碼衝突。

因此，我們刪除這六個字符並使用 base-58 代替 base-64 (包括 A-Z, a-z, 0-9，但不包括容易混淆的字符以及 + 和 /) 以增強可讀性。讓我們看看我們的 base-58 定義。

## Converting base-10 to base-58 (將 base-10 轉換為 base-58)
由於我們正在將 base-10 數字 ID 轉換為 base-58 字母數字 ID，解釋轉換過程將有助於掌握底層機制以及 SUG 的整體範圍。為了實現上述功能，我們使用取模函數。

**Process (過程)**：我們不斷將 base-10 數字除以 58，並記下每一步的餘數。當沒有餘數時我們停止。然後我們將字符索引分配給餘數，從將最新的餘數分配給最左邊的位置，將最舊的餘數分配給最右邊的位置。

**Example (示例)**：讓我們假設選定的唯一 ID 是 2468135791013。以下步驟向我們展示了餘數計算：

Base-10 = 2468135791013

2468135791013 % 58=17

42554065362 % 58=6

733690782 % 58=4

12649841 % 58=41

218100 % 58=20

3760 % 58=48

64 % 58=6

1 % 58=1

現在，我們需要按照從最新到最舊的順序寫下餘數。

Base-58 = [1] [6] [48] [20] [41] [4] [6] [17]

使用上表，我們可以將相關字符與上面寫的餘數寫在一起。

Base-58 = 27qMi57J

```
注意：根據我們的定序器設計，base-10 數字 ID 和 base-64 字母數字 ID 都有 64 位。
```

## Converting base-58 to base-10 (將 base-58 轉換為 base-10)
解碼過程與編碼過程同等重要，因為正如設計課程中所解釋的那樣，我們在生自定義短網址時使用了特定解碼器。

**Process (過程)**：將 base-58 數字轉換為 base-10 數字的過程也很簡單。我們只需要將每個字符索引 (上表中的值列) 乘以該位置所持有的 58 的數量，然後將所有單個乘法結果相加。

**Example (示例)**：讓我們對上面的示例進行逆向工程，看看解碼是如何工作的。

Base-58: 27qMi57J

  2_{58} = 1 x 58^{7} = 2207984167552

  7_{58} = 6 x 58^{6} = 228412155264

  q_{58} = 48 x 58^{5} = 31505124864

  M_{58} = 20 x 58^{4} = 226329920

  i_{58} = 41 \times 58^{3} = 7999592

  5_{58} = 4 \times 58^{2} = 13456

  7_{58} = 6 \times 58^{1} = 348

  J_{58} = 17 \times 58^{0} = 17


Base-10 = 17 + 348 + 13456 + 7999592 + 226329920 + 31505124864 + 228412155264 + 2207984167552

Base-10 = 2468135791013.

這與上一個示例中的 base-10 唯一 ID 相同。

## The scope of the short URL generator (短網址生成器的範圍)
短網址生成器是我們網址縮短服務的支柱。此短網址生成器的輸出取決於設計強加的限制，如下所示：

- 生成的短網址應包含字母數字字符。
- 任何字符都不應相似。
- 生成的短網址的最小默認長度應為六個字符。
這些限制定義了我們短網址生成器的範圍。我們可以定義範圍，如下所示：

- **Starting range (起始範圍)**：我們的定序器可以生成一個範圍從 1 到 (2^{64}-1) 的 64 位二進制數。為了滿足短網址最小長度的要求，我們可以選擇從至少 10 位數字開始的定序器 ID，即 10 億。
- **Ending point (結束點)**：映射到短網址生成器輸出的定序器 ID 的最大位數取決於 64 位的最大利用率，即 64 位中的最大 base-10 數字。我們可以通過計算這兩點來估算任何基數中的總位數：
1. 在 base-n 中表示一個數字所需的位數。這由 log_2{n} 給出。
2. 位數 = 可用總位數 / 表示一個數字的位數

讓我們從數學上看看上述針對 base-10 和 base-58 的計算：

    - 表示一個十進制數字所需的位數 = log_2{10} = 3.13
  - 64 位數字 ID 中的十進制數字總數 = 64 / 3.13= 20

    - 表示一個十進制數字所需的位數 = log_2{58}=5.85
    - 64 位數字 ID 中的 base-58 數字總數 = 64 / 5.85=11

```
最大位數：上述計算表明，定序器生成的 ID 中的最大位數將為 20，因此，編碼的短網址中的最大字符數將為 11。
```

## The sequencer's lifetime (定序器的壽命)
我們的定序器可以為我們提供唯一 ID 的年數取決於兩個因素：

- 定序器中可用的總數 = 2^{64} - 10^{9} (從上面討論的 10 億開始)
- 每年請求數 = 每月 2 億 × 12 = 24 億 (如需求中假設)

因此，考慮到上述兩個因素，我們可以計算定序器的預期壽命。

定序器的壽命 = 可用總數 / 每年請求 ={2^{64}-10^{9}} / {24 億} = 7,686,143,363.63 年

```
            定序器的預期壽命
Number of requests per month (每月請求數)	200 Million (2 億)
Number of requests per year (每年請求數)	  2.4 Billion (24 億)
Lifetime of sequencer (定序器壽命)	        7,686,143,363.63 years (年)
因此，我們的服務可以在範圍耗盡之前運行很長時間。
