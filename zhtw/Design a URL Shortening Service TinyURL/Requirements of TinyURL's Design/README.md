# Requirements of TinyURL's Design (TinyURL 設計的需求)
## Requirements for URL Shortening Design (網址縮短設計需求)
讓我們看看我們將要設計的服務的功能和非功能需求：

### Functional requirements (功能需求)
- **Short URL generation (短網址生成)**：我們的服務應該能夠為給定的網址生成唯一的短別名。
- **Redirection (重定向)**：給定一個短鏈接，我們的系統應該能夠將使用者重定向到原始網址。
- **Custom short links (自定義短鏈接)**：使用者應該能夠使用我們的系統為其網址生成自定義短鏈接。
- **Deletion (刪除)**：給定權限，使用者應該能夠刪除我們系統生成的短鏈接。
- **Update (更新)**：給定適當的權限，使用者應該能夠更新與短鏈接關聯的長網址。
- **Expiry time (過期時間)**：短鏈接必須有默認的過期時間，但使用者應該能夠根據自己的需求設置過期時間。

```
Question
問題
作為設計選擇，我們不重用過期的短網址。既然我們不重用它們，為什麼需要從我們的系統中刪除它們？

Answer
答案
到目前為止，我們將默認過期時間保持在五年。如果我們放寬這一限制並開始永遠保存記錄，我們的資料存儲的搜尋索引將無限增長，並且從中查詢的時間會增加明顯的延遲。
```

### Non-functional requirements (非功能需求)
- **Availability (可用性)**：我們的系統應該高度可用，因為即使是一小部分的停機時間也會導致網址重定向失敗。由於我們系統的域名在網址中，我們無法利用停機時間，我們的設計必須灌輸容錯條件。
- **Scalability (可擴展性)**：我們的系統應該隨著需求的增加而水平擴展。
- **Readability (可讀性)**：我們系統生成的短鏈接應該易於閱讀、區分和輸入。
- **Latency (延遲)**：系統應以低延遲執行，為使用者提供流暢的體驗。
- **Unpredictability (不可預測性)**：從安全角度來看，我們系統生成的短鏈接應該是高度不可預測的。這確保了下一個短網址不會被串行生成，從而消除了有人猜測我們系統已經生成或將要生成的所有短網址的可能性。

```
Question
問題
為什麼生成不可預測的短網址對我們的系統是強制性的？

Hide Answer
隱藏答案
以下兩個問題凸顯了生成非串行、不可預測的短網址的必要性：

1. 攻擊者可以訪問短網址總數的系統級訊息，從而為他們提供一個定義的範圍來規劃他們的攻擊。這類內部訊息不應在系統外可用。

2. 我們的使用者可能已經使用我們的服務為秘密網址生成短網址。有了上面的訊息，攻擊者可以嘗試列出所有短網址，訪問它們並獲得有關相關長網址的見解，從而危及私人網址的保密性。這將損害使用者資料的隱私，使我們的系統安全性降低。

因此，隨機分配唯一 ID 會剝奪攻擊者對此類系統見解的了解，這些見解是枚舉和破壞使用者私人資料所必需的。
```

## Resource estimation (資源估算)
最好在開始時進行現實的估算。例如，我們可能需要根據設計修改在未來更改它們。讓我們做一些假設來完成我們的估算。

**Assumptions (假設)**

- 我們假設縮短與重定向的請求比率為 1:100。
- 每個月有 2 億個新的網址縮短請求。
- 一個網址縮短條目需要 500 字節的資料庫存儲空間。
- 除非明確刪除，否則每個條目最多有五年的過期時間。
- 有 1 億日活躍使用者 (DAU)。

### Storage estimation (儲存估算)
由於條目保存期為 5 年，每月共有 2 億個條目，因此總條目數約為 120 億。
```
2 億/月 × 12 個月/年 × 5 年 = 120 億個網址縮短請求
由於每個條目為 500 字節，總儲存估算為 6 TB：
```
120 億 × 500 字節 = 6 TB
```

### Query rate estimation (查詢率估算)
基於上述估算，我們可以預期每個月有 200 億次重定向請求。
```
2 億 × 100 = 200 億
我們可以以此為基準擴展我們系統的每秒查詢數 (QPS) 計算。假設平均每月天數為 30.42，一個月中的秒數為：
```
30.42 天 × 24 小時 × 60 分鐘 × 60 秒 = 2628288 秒
考慮到上述計算，每秒新的網址縮短請求將為：
```
2 億 / 2628288 秒 = 76 個網址/秒
以 1:100 的縮短與重定向比率，每秒網址重定向率將為：
```
100 × 76 個網址/秒 = 7.6 K 個網址/秒
### Bandwidth estimation (頻寬估算)
**Shortening requests (縮短請求)**：預期到達率為每秒 76 個新網址。總傳入資料將為每秒 304 Kbps：
```
76 × 500 字節 × 8 位 = 304 Kbps
**Redirection requests (重定向請求)**：由於預期速率為每秒 20K 個網址重定向，總傳出資料將為 30.4 Mbps：
```
7.6 K × 500 字節 × 8 位 = 30.4 Mbps

### Memory estimation (記憶體估算)
如果我們想快取一些頻繁訪問的網址重定向請求，我們需要記憶體估算。讓我們假設傳入請求的分佈為 80-20。20% 的重定向請求產生 80% 的流量。

由於每秒重定向請求為 7.6 K，因此一天的總請求數為 6.6 億。
```
7.6 K × 3600 秒 × 24 小時 = 6.6 億
由於我們只考慮快取這些每日重定向請求的 20%，因此總記憶體需求估算為 66 GB。
```
0.2 × 6.6 億 × 500 字節 = 66 GB
```

### Number of servers estimation (伺服器數量估算)
我們採用粗略估算中討論的相同近似值來計算所需的伺服器數量：日活躍使用者數和伺服器的每日使用者處理限制是描述所需伺服器總數的兩個主要因素。根據近似值，我們需要將日活躍使用者 (DAU) 除以 8000 來計算近似的伺服器數量。
```
伺服器數量 = DAU/8000 = 1 億/8000 = 12500 台伺服器

## Building blocks we will use (我們將使用的構建塊)
估算完成後，我們可以確定設計中的關鍵構建塊。列表如下：

[高層設計中的構建塊](./bb.jpg)

- **Database(s) (資料庫)**：將需要存儲長網址和相應短網址的映射。
- **Sequencer (定序器)**：將提供唯一 ID，作為每個短網址生成的起點。
- **Load balancers (負載平衡器)**：各層的負載平衡器將確保請求在可用伺服器之間平滑分配。
- **Caches (快取)**：將用於存儲最頻繁的短網址相關請求。
- **Rate limiters (速率限制器)**：將用於避免系統被利用。

除了這些構建塊之外，我們還需要以下附加組件來實現所需的服務：

- **Servers (伺服器)**：在運行應用程式邏輯的同時處理和導航服務請求。
- **A Base-58 encoder (Base-58 編碼器)**：將定序器的數字輸出轉換為更易讀和可用的字母數字形式。
