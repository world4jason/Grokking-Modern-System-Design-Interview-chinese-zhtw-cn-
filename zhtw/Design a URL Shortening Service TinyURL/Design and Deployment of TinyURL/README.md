# Design and Deployment of TinyURL (TinyURL 的設計和部署)
## System APIs (系統 API)
為了公開我們服務的功能，我們可以使用 REST API 來實現以下功能：

- Shortening a URL (縮短網址)
- Redirecting a short URL (重定向短網址)
- Deleting a short URL (刪除短網址)

[系統 API 設計概述](./api.jpg)

### Shortening a URL (縮短網址)
我們可以使用以下定義創建新的短網址：
```
shortURL(api_dev_key, original_url, custom_alias=None, expiry_date=None)
```

上面的 API 調用具有以下參數：

Parameter (參數)       Description (描述)

api_dev_key            註冊使用者帳戶的唯一標識符。這在跟踪使用者活動方面很有用，並允許系統相應地控制相關服務。

original_url           需要縮短的原始長網址。

custom_alias           使用者定義為自定義短網址的可選鍵。

expiry_date            縮短網址的可選過期日期。
成功插入會向使用者返回縮短的網址。否則，系統會向使用者返回適當的錯誤代碼。

### Redirecting a short URL (重定向短網址)
要重定向短網址，REST API 的定義將是：
```
redirectURL(api_dev_key, url_key)
具有以下參數：
Parameter (參數)     Description (描述)

api_dev_key          註冊使用者帳戶的唯一標識符。

url_key              我們需要從資料庫中獲取長網址的縮短網址。
成功的重定向會將使用者引導到與 url_key 關聯的原始網址。

### Deleting a short URL (刪除短網址)
同樣，要刪除短網址，REST API 的定義將是：
```
deleteURL(api_dev_key, url_key)
相關參數將是：
Parameter (參數)      Description (描述)

api_dev_key           註冊使用者帳戶的唯一標識符。

url_key               我們需要從資料庫中獲取長網址的縮短網址。
成功刪除會返回一條系統消息，URL Removed (網址已刪除)，傳達從系統中成功刪除網址的訊息。

## Design (設計)
讓我們討論我們的網址縮短服務所需的主要設計組件。我們的設計取決於每個部分的功能，並逐步將它們組合起來以實現功能需求中提到的不同工作流程。

### Components (組件)
我們將解釋系統中不同組件的內部機制，以及它們作為整個系統一部分的用法。我們還將重點介紹為實現整體功能而為每個組件所做的設計選擇。

**Database (資料庫)**：對於像網址縮短這樣的服務，不需要存儲大量資料。但是，存儲必須是水平可擴展的。我們需要存儲的資料類型包括：

- 使用者詳細資訊。
- 網址映射，即映射到短網址的長網址。
我們的服務不需要使用者註冊即可生成短網址，因此我們可以跳過將某些資料添加到我們的資料庫中。此外，存儲的記錄除了鏈接創建網址的使用者詳細資訊外，彼此之間沒有關係，因此我們不需要結構化存儲來保存記錄。考慮到上述原因以及我們的系統將是讀取密集型的事實，NoSQL 是存儲資料的合適選擇。特別是，MongoDB 是一個不錯的選擇，原因如下：

1. 它使用領導者-追隨者協議，使得使用副本進行大量讀取成為可能。
2. MongoDB 確保並發寫入操作中的原子性，並通過返回記錄重複問題的重複鍵錯誤來避免衝突。

```
Question
問題
為什麼像 Cassandra 或 Riak 這樣的 NoSQL 資料庫不是代替 MongoDB 的好選擇？

Answer
答案
由於我們的服務更多是讀取密集型而不是寫入密集型，因此 MongoDB 最適合我們的用例，原因如下：

像 Cassandra、Riak 和 DynamoDB 這樣的 NoSQL 資料庫在讀取階段需要讀取修復，因此提供的讀取性能低於寫入性能。

它們是無領導者的 NoSQL 資料庫，在並發寫入時提供較弱的原子性。作為單一領導者資料庫，MongoDB 提供了更高的讀取吞吐量，因為我們可以從領導者副本或追隨者副本中讀取。寫入操作必須經過領導者副本。它確保了我們的系統在讀取密集型任務中的可用性，即使在領導者死亡的情況下也是如此。

由於 Cassandra 本質上比 MongoDB 更能保證可用性，因此選擇 MongoDB 而不是 Cassandra 可能會使我們的系統看起來可用性較低。然而，與短網址生成和首次使用之間經過的時間相比，領導者選舉演算法所花費的時間可以忽略不計，因此它不會妨礙我們系統的可用性。
```


**Short URL generator (短網址生成器)**：我們的短網址生成器將包含一個構建塊和一個附加組件：

- 用於生成唯一 ID 的定序器
- 用於增強短網址可讀性的 Base-58 編碼器
我們在構建塊部分構建了一個定序器來生成 64 位唯一數字 ID。但是，我們建議的設計需要 base-58 的 64 位字母數字短網址。要將數字 (base-10) ID 轉換為字母數字 (base-58) ID，我們需要一個 base-10 到 base-58 的編碼器。我們將在下一課中探討這些決定背後的理由以及 base-58 編碼器的內部工作原理。

**Other building blocks (其他構建塊)**：除了上面提到的元素外，我們還將整合其他構建塊，如負載平衡器、快取和速率限制器。

- **Load balancing (負載平衡)**：除了本地負載平衡外，我們還可以使用全局伺服器負載平衡 (GSLB) 來提高可用性。由於我們在生成短網址和隨後訪問它之間有足夠的時間，我們可以安全地假設我們的 DB 在地理上是一致的，並且在全球範圍內分發請求不會引起任何問題。
- **Cache (快取)**：對於我們特定的讀取密集型設計問題，Memcached 是快取解決方案的最佳選擇。我們需要一個簡單、水平可擴展且對資料結構要求最低的快取系統。此外，我們將有一個特定於資料中心的快取層來處理本地請求。擁有全局快取層會導致更高的延遲。
- **Rate limiter (速率限制器)**：限制每個使用者的配額對於向我們的系統添加安全層是可取的。我們可以通過通過其唯一的 api_dev_key 唯一標識使用者並應用討論的速率限制演算法之一來實現這一點 (參見構建塊中的速率限制器)。考慮到我們系統的簡單性和需求，固定窗口計數器演算法可以達到目的，因為我們可以為特定時間範圍內的每個 api_dev_key 分配一定數量的縮短和重定向操作。

Question 1
問題 1
如果重定向請求可以轉到地理位置相隔的資料中心，我們將如何維護唯一映射？我們的設計是否假設我們的 DB 在地理上是一致的？

Answer
答案
我們最初假設我們的資料中心是全球一致的。讓我們換個角度看問題，考慮相反的情況：我們需要根據資料中心過濾重定向請求。

解決方案：實現此功能的一種簡單方法是在短網址中引入唯一字符。這個特殊字符將作為確切資料中心的指示器。

例如：假設需要重定向的短網址是 service.com/x/short123/，其中 x 表示包含此記錄的資料中心。

在此解決方案中，如果短網址轉到錯誤的資料中心，它可以被重定向到正確的資料中心。但是，如果特定短網址無法訪問特定資料中心 (並且該網址尚未緩存)，則重定向將失敗。
```

Question 3
問題 3
當我們向短網址生成器請求新的短網址時，發生衝突的概率是多少？

Answer
答案
我們向定序器請求唯一 ID，根據我們定序器設計的定義，ID 永遠不會重複。然後我們對這些 ID 進行編碼，這也確保了沒有重複。因此，常規的短網址生成過程確保記錄中沒有重複。

現在讓我們考慮自定義短網址的情況。由於使用者提供短網址，因此可能存在重複。我們可以通過考慮包含短網址記錄的資料庫的大小來輕鬆計算此衝突的概率。

假設資料庫中已經生成了 n 個短網址。使用者提供的自定義短網址與現有短網址相似的概率可以由 1/n 給出。

## Workflow (工作流程)

讓我們深入分析系統以及各個部分如何組合在一起以提供整體功能。

考慮到功能需求，上述抽象設計的工作流程如下。

1. **Shortening (縮短)**：每個新的短鏈接計算請求都由應用伺服器轉發到短網址生成器 (SUG)。成功生成短鏈接後，系統將一份副本發送回使用者，並將記錄存儲在資料庫中以供將來使用。

```
Question 1
問題 1
我們的系統如何避免重複的短網址生成？

答案
- 為已經存在的長網址計算短網址是多餘的，系統將長網址發送到資料庫伺服器以檢查其在系統中的存在。系統將首先檢查快取中的相應條目，然後查詢資料庫。

- 如果相應長網址的短網址已經存在，資料庫將保存的短網址返回給應用伺服器，應用伺服器將請求的短網址重新路由給使用者。

- 如果請求的短網址在系統中不可用，應用伺服器請求 SUG 為請求的長網址計算短網址。計算完成後，SUG 將請求的短網址的一份副本發送回應用伺服器，並將另一份副本發送回資料庫伺服器。
```

問題 2
我們如何確保兩個對短網址的並發請求不會覆蓋？

Answer
答案
處理網址縮短請求的並發性至關重要，我們通過以下方式實現：

在 MongoDB 中，所有寫入請求都經過單個領導者，因此排除了由於通過單個領導者序列化請求而導致競爭條件的可能性。

Question
問題
成功分配自定義短網址後，系統如何修改其記錄？

Answer
答案
由於自定義短網址是可用 base-10 唯一 ID 的 base-58 編碼，將該唯一 ID 標記為不可用於將來使用對於系統的完整性是必要的。

在後端，系統訪問具有該特定 base-58 短網址的 base-10 等效唯一 ID 的伺服器。它將該 ID 標記為範圍內不可用，從而消除了將相同 ID 重新分配給任何其他請求的機會。
```

[轉換](./bases.jpg)

這種技術也有助於可用性。生成短網址的節點將不再需要在內存中維護已使用和未使用的唯一 ID 列表。相反，為每個列表維護一個資料庫。為了獲得良好的性能，此資料庫可以是 NoSQL。

上面的部分解釋了自定義短網址關聯的後處理。一些進一步的細節包括以下內容：

1. 一旦我們生成了 ID，我們就將它們放入未使用的列表中。一旦我們使用未使用列表中的 ID，我們就將其放入已使用列表中。這消除了重複關聯的可能性。
2. 由於編碼保證了 base-10 和 base-58 之間的唯一映射，因此不會有兩個長網址具有相同的短網址。
