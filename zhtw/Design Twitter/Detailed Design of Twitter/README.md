# Detailed Design of Twitter (Twitter 的詳細設計)
## Storage system (儲存系統)
儲存是每個實時系統中的核心組件之一。雖然我們有關於儲存系統的詳細章節，但在這裡，我們將特別關注 Twitter 使用的儲存系統。Twitter 為不同的服務使用各種儲存模型，以充分利用每種模型。我們將討論每種儲存模型，看看 Twitter 如何從各種資料庫、平台和工具轉向其他資料庫、平台和工具，以及 Twitter 如何從所有這些中受益。

本課的內容主要受到 Twitter 技術部落格的影響，儘管分析是我們的。

```
儲存模型表示資料儲存的基本物理方面。
```

- **Google Cloud**：在 Twitter 中，HDFS (Hadoop Distributed File System) 由數萬台伺服器組成，託管超過 300PB 的資料。HDFS 中的資料儲存主要通過 LZO (資料壓縮演算法) 進行壓縮，因為 LZO 在 Hadoop 中工作效率很高。這些資料包括日誌 (客戶端事件、推文事件和時間線事件)、MySQL 和 Manhattan (稍後討論) 備份、廣告定位和分析、使用者參與度預測、社交圖譜分析等等。2018 年，Twitter 決定將資料從 Hadoop 集群轉移到 Google Cloud，以更好地分析和管理資料。這種轉變被稱為“部分雲端策略” (partly cloudy strategy)。最初，他們遷移了 Ad-hoc 集群 (偶爾分析) 和冷儲存集群 (較少訪問和較少使用的資料)，而實時和生產 Hadoop 集群仍然存在。大數據儲存在 BigQuery (Google 雲端服務) 中，這是一個完全託管且高度可擴展的無伺服器資料倉庫。Twitter 使用 Presto (分散式 SQL 查詢引擎) 訪問來自 Google Cloud (BigQuery、Ad-hoc 集群、Google 雲端儲存等) 的資料。

- **Manhattan**：在 Twitter 上，使用者迅速增長，需要一個可擴展的解決方案來增加吞吐量。2010 年左右，Twitter 使用 Cassandra (一種分散式寬列儲存) 來替換 MySQL，但由於 Cassandra 儲存的一些缺點，未能完全替換它。2014 年 4 月，Twitter 推出了自己的通用實時分散式鍵值儲存，稱為 Manhattan，並棄用了 Cassandra。Manhattan 儲存推文、Twitter 帳戶、直接訊息等的後端。Twitter 根據用例運行多個集群，例如用於非通用或唯讀的較小集群，以及用於繁重讀/寫流量 (數百萬 QPS) 的較大集群。最初，Manhattan 還提供了 MetricsDB 現在提供的時間序列 (查看、按讚等) 計數器服務。Manhattan 使用 RocksDB 作為儲存引擎，負責儲存和檢索特定節點內的資料。

[Twitter 的資料移動到 Manhattan 資料庫](./manhattandb.jpg)

- **Blobstore**：2012 年左右，Twitter 建立了 Blobstore 儲存系統來儲存附在推文上的照片。現在，它還儲存影片、二進位檔案和其他對象。在指定時間段後，伺服器將記憶體中的資料作為持久儲存檢查點到 Blobstore。我們有一個關於 Blob 儲存的詳細章節，可以幫助您了解它是什麼以及它是如何工作的。

- **SQL-based databases (基於 SQL 的資料庫)**：Twitter 使用 MySQL 和 PostgreSQL，在這些地方它需要強一致性、廣告交易和管理廣告活動。Twitter 還使用 Vertica 查詢常用的聚合資料集和 Tableau 儀表板。大約在 2012 年，Twitter 還在 MySQL 之上構建了 Gizzard 框架用於分片，這是通過分區和複製完成的。我們在資料庫章節中詳細討論了關聯式儲存。

- **Kafka and Cloud dataflow (Kafka 和 Cloud dataflow)**：Twitter 每天評估大約 4000 億個實時事件並生成 PB 級的資料。為此，它在本地使用 Kafka 處置事件，並使用 Google Dataflow 作業在 Google Cloud 上處理重複資料刪除和實時聚合。聚合後，結果儲存在 BigQuery (資料倉庫) 中進行臨時分析，以及服務系統到 Bigtable (NoSQL 資料庫) 中。Twitter 使用事件處理器將 Kafka 主題轉換為 Cloud Pub-sub 主題，這有助於避免資料丟失並提供更高的可擴展性。有關這方面的深入探討，請參閱 Pub-sub 章節。

[數十億請求的實時處理](./realtime.jpg)

- **FlockDB**：關係是指使用者的追蹤者、使用者關注的人、使用者必須接收其通知的人等等。Twitter 以圖形的形式儲存這種關係。Twitter 使用 FlockDB，這是一個針對巨大鄰接表、快速讀寫等以及圖遍歷操作進行調整的圖資料庫。我們有一章關於資料庫和動態消息，詳細討論了圖形儲存。

- **Apache Lucene**：Twitter 構建了一個搜尋服務，索引大約一萬億條記錄，並在 100 毫秒內響應請求。大約在 2019 年，Twitter 的搜尋引擎索引延遲 (索引新推文的時間) 大約為 15 秒。Twitter 使用 Apache Lucene 進行實時搜尋，它使用倒排索引。Twitter 將實時索引 (過去一周的最近推文) 儲存在 RAM 中，以實現低延遲和快速更新。完整索引比實時索引大一百倍。但是，Twitter 對完整索引執行批處理。請參閱分散式搜尋章節以深入了解索引的工作原理。

```
倒排索引是一種類似於雜湊表的資料結構，它將系統從單詞引導到文件或資料庫表。
```

[處理搜尋請求](./processing.jpg)

基於“一刀切”方法的解決方案很少有效。實時應用程式始終專注於為工作提供正確的工具，這需要了解所有可能的用例。最後，凡事都有利弊，應以現實感加以應用。


## Cache (快取)
眾所周知，快取有助於減少延遲並增加吞吐量。快取主要用於儲存 (繁重的讀取流量)、計算 (實時流處理和機器學習) 和瞬態資料 (速率限制器)。Twitter 一直被用作多租戶 (應用程式的多個實例具有共享環境) Twitter Memcached (Twemcache) 和 Redis (Nighthawk) 集群進行快取。由於現有快取系統 (Twemcache 和 Nighthawk) 中的一些問題，例如意外的效能、除錯困難和其他操作麻煩，Twitter 已開始使用 Pelikan 快取。此快取提供高吞吐量和低延遲。Pelikan 使用多種類型的後端伺服器，例如 Twitter Twemcache 伺服器的 peliken_twemcache 替代品、Twitter Memcached/Redis 伺服器的 peliken_slimcache 替代品等等。為了深入探討，我們有一個關於記憶體中快取的詳細章節。讓我們看看下圖，它代表了應用程式伺服器與分散式 Pelikan 快取的關係。

[分散式 Pelikan 快取](./cache.jpg)

```
注意：Pelikan 還推出了另一個名為 Segcache 的後端伺服器，它對於小對象來說極具可擴展性且記憶體效率高。通常，在大規模應用程式的快取中，小對象的中位數大小在 200 到 300 字節之間。大多數解決方案 (Memcache 和 Redis) 每個對象都有很大的元資料大小 (56 字節)。這意味著元資料佔用了超過三分之一的記憶體。Pelikan 將每個對象的元資料大小減少到 38 字節。Segcache 還獲得了 NSDI 社區獎，截至 2021 年仍被用作實驗伺服器。
```

## Observability (可觀測性)
實時應用程式使用數千台提供多種服務的伺服器。監控資源及其在系統內部或外部的通訊是複雜的。我們可以使用各種工具來監控服務的運行狀況，例如為多個問題提供警報和支持。我們的警報系統會通知由設定指標觸發的損壞或降級的服務。我們還可以使用動態配置庫，在不重新啟動服務的情況下為多個服務部署及更新配置。該庫利用 Zookeeper (稍後討論) 進行配置作為事實來源。Twitter 使用 LonLens 服務，該服務提供服務日誌的可視化和分析。後來，它被中央日誌系統 Splunk Enterprise 取代。

在大型實時應用程式中追蹤數十億個請求具有挑戰性。Twitter 使用 Zipkin (一種分散式追蹤系統) 來追蹤多個服務的每個請求 (花費時間和請求計數)。Zipkin 選擇所有請求的一部分並附加輕量級追蹤標識符。這種採樣也減少了追蹤開銷。Zipkin 通過 Scribe (實時日誌資料聚合) 伺服器接收資料，並將其儲存在具有少量索引的鍵值儲存中。

[可觀測性](./observability.jpg)

大多數實時應用程式使用 Zookeeper 來儲存關鍵資料。它還可以提供多種服務，例如分佈系統中的分散式鎖定和領導者選舉。Twitter 使用 Zookeeper 來儲存服務註冊表、Manhattan 集群的拓撲資訊、元資料等等。Twitter 還將其用於各種系統上的領導者選舉。

## Real-world complex problems (現實世界的複雜問題)
Twitter 擁有數百萬個帳戶，有些帳戶 (公眾人物) 擁有數百萬追蹤者。當這些帳戶發布推文時，相應帳戶的數百萬追蹤者會在短時間內與他們的推文互動。當系統處理這些推文上的數十億次互動 (例如查看和按讚) 時，問題就變大了。這個問題也被稱為 heavy hitter (重度擊球手) 問題。為此，我們需要數百萬個計數器來計算推文上的各種操作。

此外，針對特定推文的每個特定操作的單個計數器是不夠的。在單個計數器中處理針對特定推文的數百萬增量或減量請求具有挑戰性。因此，我們需要多個分散式計數器來管理針對名人推文的各種互動的爆發寫入請求 (增量或減量)。每個計數器都有幾個在不同計算單元上工作的分片。這些分散式計數器稱為分片計數器。這些計數器還有助於解決另一個名為 Top-k 問題的實時問題。讓我們討論一個 Twitter 的 Top-k 問題的例子：趨勢和時間線。

Trends (趨勢)：Twitter 在本地和全球顯示 Top-k 趨勢 (標籤或關鍵字)。在這裡，“本地”是指主題或標籤在請求使用者活躍的確切位置內使用的情況。或者，“全球”是指特定標籤在世界範圍內使用的情況。某些地區的使用者可能不會在推文中使用特定標籤，但在其趨勢時間線中獲得此標籤。具有最大頻率 (計數) 的標籤在本地和全球都成為趨勢。此外，Twitter 在趨勢下顯示指定區域的各種推廣趨勢 (稱為“付費趨勢”)。下面的幻燈片代表了隨時間推移被選為 Top-k 趨勢的滑動窗口中的標籤。

[趨勢](./topK)

Timeline (時間線)：Twitter 顯示兩種類型的時間線：首頁和使用者時間線。在這裡，我們將討論顯示關注帳戶發布的推文流的首頁時間線。在時間線中顯示 Top-k 推文的決定包括關注帳戶的推文以及關注帳戶按讚或轉發的推文。首頁時間線中還顯示另一類推廣推文。

分片計數器有效地解決了討論的問題。我們還可以將指定計數器的分片放置在使用者附近，以減少延遲並像 CDN 一樣提高整體效能。我們可以獲得的另一個好處是當使用者與推文互動 (按讚或查看) 時對使用者的頻繁響應。管理相應計數器各個分片的最近伺服器正在以較短的重新整理間隔不斷更新按讚或查看計數。但是，我們應該注意，近乎實時的計數將在具有較長重新整理間隔的推文上更新。原因是應用程式伺服器等待放置在不同區域的各種伺服器提交的多個計數。我們有一個關於分片計數器的詳細章節，解釋它如何在實時應用程式中工作。

## The complete design overview (完整的設計概述)

本節將討論當最終使用者生成多個請求時後端系統中發生的情況。步驟如下：

- 首先，最終使用者從本地 DNS 獲取最近負載平衡器的地址。

- 負載平衡器根據請求的服務將最終使用者的請求路由到適當的伺服器。在這裡，我們將討論推文、時間線和搜尋服務。

  - **Tweet service (推文服務)**：當最終使用者執行任何操作，例如發布推文或按讚其他推文時，負載平衡器將這些請求轉發到處理推文服務的伺服器。考慮一個使用者使用 /postTweet API 在 Twitter 上發布推文的例子。伺服器 (推文服務) 接收請求並執行多個操作。它識別推文中的附件 (圖像、影片) 並將其儲存在 Blobstore 中。推文中的文字、使用者資訊和所有元資料儲存在不同的資料庫 (Manhattan, MySQL, Postgresql, Vertica) 中。同時，在 Apache Kafka 中實現實時處理，例如從實時流和客戶端日誌中提取推文、使用者互動資料和許多其他指標。

隨後，資料通過事件處理器移動到雲端 pub-sub。接下來，資料通過 Cloud Dataflow 傳輸到 BigQuery 進行重複資料刪除和聚合。最後，資料儲存在 Google Cloud Bigtable 中，它是完全託管的、易於擴展的和排序鍵。

  - **Timeline service (時間線服務)**：假設使用者使用 /viewHome_timeline API 發送首頁時間線請求。在這種情況下，請求將轉發到包含靜態資料的最近 CDN。如果未找到請求的資料，則將其發送到提供時間線服務的伺服器。此服務從不同的資料庫或儲存中獲取資料並返回 Top-k 推文。此服務從不同的分片計數器收集推文的各種互動計數，以決定 Top-k 推文。以類似的方式，我們將獲得附加在時間線請求響應中的 Top-k 趨勢。

  - **Search service (搜尋服務)**：當使用者在 Twitter 上的搜尋欄中輸入任何關鍵字時，搜尋請求將使用 /searchTweet API 轉發到相應的伺服器。它首先在 Apache Lucene 的 RAM 中查找以獲取實時推文 (最近發布的推文)。然後，此伺服器在索引伺服器中查找並查找包含請求關鍵字的所有推文。接下來，它考慮多個因素 (例如時間或位置) 對發現的推文進行排名。最後，它返回頂級推文。

- 我們可以使用執行請求採樣的 Zipkin 追蹤系統。此外，我們可以使用 Zookeeper 維護不同的資料，包括配置資訊、分散式同步、命名註冊表等。
