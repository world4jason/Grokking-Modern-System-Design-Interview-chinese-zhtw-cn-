# Requirements of Twitter’s Design (Twitter 的設計需求)

## Requirements (需求)
讓我們了解以下功能和非功能需求：

### Functional requirements (功能需求)
以下是 Twitter 的功能需求：

- **Post Tweets (發布推文)**：註冊使用者可以在 Twitter 上發布一條或多條推文。

- **Delete Tweets (刪除推文)**：註冊使用者可以在 Twitter 上刪除一條或多條推文。

- **Like or dislike Tweets (按讚或按不喜歡推文)**：註冊使用者可以在 Twitter 上按讚或按不喜歡公開和自己的推文。

- **Reply to Tweets (回覆推文)**：註冊使用者可以在 Twitter 上回覆公開推文。

- **Search Tweets (搜尋推文)**：註冊使用者可以通過在 Twitter 搜尋欄中輸入關鍵字、主題標籤或使用者名稱來搜尋推文。

- **View user or home timeline (查看使用者或首頁時間線)**：註冊使用者可以查看使用者的時間線，其中包含他們自己的推文。他們還可以在 Twitter 上查看包含追蹤者推文的首頁時間線。

- **Follow or unfollow the account (關注或取消關注帳戶)**：註冊使用者可以在 Twitter 上關注或取消關注其他使用者。

- **Retweet a Tweet (轉發推文)**：註冊使用者可以在 Twitter 上轉發其他使用者的公開推文。

### Non-functional requirements (非功能需求)
- **Availability (可用性)**：許多人和組織使用 Twitter 傳達時效性資訊 (服務中斷訊息)。因此，我們的服務必須具有高可用性並具有良好的正常運行時間百分比。

- **Latency (延遲)**：在首頁時間線中顯示最近熱門推文的延遲可能會有點高。但是，近乎實時的服務，例如將推文分發給追蹤者，必須具有低延遲。

- **Scalability (可擴展性)**：Twitter 上的工作負載是讀取密集型的，我們有許多讀者和相對較少的作者，這最終需要計算資源的可擴展性。一些估計表明 Twitter 的寫入與讀取比率為 1:1000。雖然推文限制為 280 個字元，影片剪輯預設限制為 140 秒，但我們需要高儲存容量來儲存和交付公眾人物發布給數百萬追蹤者的推文。

- **Reliability (可靠性)**：所有推文都保留在 Twitter 上。這意味著 Twitter 永遠不會刪除其內容。因此，應該有一個有前途的策略來防止上傳內容的丟失或損壞。

- **Consistency (一致性)**：美國東海岸的使用者可能不會立即獲得美國西海岸使用者按讚或轉發的推文的狀態 (按讚、回覆等) 更新。但是，美國西海岸的使用者需要立即獲得關於他的按讚或回覆的狀態更新。需要一種有效的技術向使用者 (按讚某人貼文的人) 提供快速反饋，然後向同一區域的其他指定使用者提供反饋，最後向與該推文連結的所有全球使用者提供反饋。

## Building blocks we will use (我們將使用的構建塊)
Twitter 的設計利用了我們在最初章節中討論的以下構建塊。

[Twitter 設計中使用的構建塊](./bb.jpg)

- **DNS** 是將人性化的 Twitter 域名映射到機器可讀的 IP 地址的服務。
- **Load balancers (負載平衡器)** 在各個服務之間分配讀/寫請求。
- **Sequencers (定序器)** 生成推文的唯一 ID。
- **Databases (資料庫)** 儲存推文和使用者的元資料。
- **Blob stores (Blob 儲存)** 儲存附在推文上的圖像和影片剪輯。
- **Key-value stores (鍵值儲存)** 用於多種目的，例如索引、識別要更新其值的指定計數器、識別特定使用者的推文等等。
- **Pub-sub (發布-訂閱)** 用於實時處理，例如消除冗餘資料、組織資料等等。
- **Sharded counters (分片計數器)** 幫助處理擁有多個追蹤者的帳戶的多個功能 (例如查看、按讚、轉發等) 的計數。
- **Cache (快取)** 用於將最常請求和最新的資料儲存在 RAM 中，以便為使用者提供快速響應。
- **CDN** 幫助最終使用者以低延遲訪問資料。
- **Monitoring (監控)** 分析所有傳出和傳入流量，識別儲存系統中的冗餘，找出故障節點等等。
