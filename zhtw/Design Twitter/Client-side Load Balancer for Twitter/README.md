# Client-side Load Balancer for Twitter (Twitter 的客戶端負載平衡器)
## Introduction (介紹)
在上一課中，我們構思了使用專用負載平衡器設計 Twitter。雖然這種方法有效，並且我們已在其他設計中使用了它，但它可能不是 Twitter 的最佳選擇。這是因為 Twitter 大規模提供各種服務，使用大量實例，對於此類系統而言，專用負載平衡器並非合適的選擇。為了更好地理解這個概念，讓我們了解 Twitter 的設計歷史。

### Twitter’s design history (Twitter 的設計歷史)
Twitter 的初始設計包括一個帶有 MySQL 資料庫的單體 (Ruby on Rails) 應用程式。隨著 Twitter 的擴展，服務數量增加，MySQL 資料庫被分片。像這樣的單體應用程式設計是一場災難，原因如下：

- 大量開發人員在同一個程式碼庫上工作，這使得更新單個服務變得困難。
- 一項服務的升級過程可能會導致另一項服務崩潰。
- 硬體成本增加，因為一台機器執行多項服務。
- 從故障中恢復既耗時又複雜。
隨著 Twitter 的發展方式，唯一的出路是許多微服務，其中每項服務都可以通過數百或數千個實例提供服務。

### Client-side load balancing (客戶端負載平衡)
在客戶端負載平衡技術中，具有大量實例的任何兩個服務之間沒有專用的中間負載平衡基礎設施。請求服務的一組節點的節點具有內置的負載平衡器。我們將請求節點或服務稱為客戶端。客戶端可以使用各種技術來選擇合適的實例來請求服務。下圖描繪了客戶端負載平衡的概念。每個新到達的服務或實例都會在服務註冊表中註冊自己，以便其他服務知道它的存在。

[客戶端負載平衡的工作原理](./clients.jpg)

在上圖中，服務 A 必須選擇服務 B 中負擔相對較輕的實例。因此，它將利用其中的負載平衡器組件來選擇最合適的服務 B 實例。使用相同的客戶端負載平衡方法，服務 B 將與其他服務對話。很明顯，當服務 A 調用服務 B 時，它是客戶端，而當服務 B 與服務 C 和 D 對話時，它是客戶端。因此，將沒有執行負載平衡的中央實體。相反，每個節點都會執行自己的負載平衡。

**Advantages (優點)**：使用客戶端負載平衡具有以下好處。

- 執行負載平衡所需的硬體基礎設施/層更少。
- 由於沒有中間跳躍，網路延遲將減少。
- 客戶端負載平衡器消除了頻寬瓶頸。另一方面，在專用負載平衡層中，所有請求都經過一台機器，如果流量成倍增加，該機器可能會阻塞。
- 整個系統中的故障點更少。
- 最終使用者隊列不會等待特定服務的資源 (伺服器)，因為許多負載平衡器正在路由流量。最終，這提高了體驗質量 (QoE)。
許多現實世界的應用程式 (如 Twitter, Yelp, Netflix 等) 都使用客戶端負載平衡。我們將在下一節中討論 Twitter 使用的客戶端負載平衡技術。

## Client-side load balancing in Twitter (Twitter 中的客戶端負載平衡)
Twitter 使用稱為 deterministic aperture (確定性孔徑) 的客戶端負載平衡器，它是稱為 Finagle 的更大 RPC 框架的一部分。Finagle 是一個與協議無關的、開源的、非同步的 RPC 庫。

注意：考慮以下問題。Twitter 的客戶端負載平衡器基於什麼進行平衡？也就是說，使用什麼參數在不同伺服器之間公平地平衡負載？
Twitter 主要使用兩種分發來衡量負載平衡器的有效性：

1. **The distribution of requests (OSI layer 7)** (請求的分發 (OSI 第 7 層))
2. **The distribution of sessions (OSI layer 5)** (會話的分發 (OSI 第 5 層))
雖然請求是關鍵指標，但會話是實現公平分發的重要屬性。因此，我們將開發公平分發請求和會話的技術。讓我們首先從簡單的 Power of Two Random Choices (P2C) 技術進行請求分發開始。

### Request distribution using P2C (使用 P2C 進行請求分發)
用於請求分發的 P2C 技術只要會話分布均勻，就可以提供均勻的請求分發。在 P2C 中，系統針對每個請求隨機選擇兩個唯一的實例 (伺服器)，並選擇負載最少的一個。讓我們看下面的插圖來了解 P2C。

[兩個隨機選擇的力量](./power.jpg)

P2C 基於一個簡單的想法，即兩個隨機選擇的節點之間的比較提供了比隨機選擇好幾倍的負載分發。

```
參見 M. Mitzenmacher 的“隨機負載平衡中兩種選擇的力量”。
```

既然我們已經建立了如何公平地分發請求，讓我們探索不同的會話分發技術。

### Session distribution (會話分發)
**Solution 1 (解決方案 1)**：我們將從 Mesh topology (網狀拓撲) 開始討論。使用這種方法，每個客戶端 (負載平衡器) 都會與服務的所有給定實例啟動會話。下圖代表了網狀拓撲的概念。

顯然，這種方法是公平的，因為會話是均勻分發的。然而，會話的均勻分發代價非常高，尤其是當擴展到數千台伺服器時。除此之外，一些不健康或陳舊的會話可能會導致故障。

**Solution 2 (解決方案 2)**：為了解決解決方案 1 的可擴展性問題，Twitter 提出了另一種稱為 random aperture (隨機孔徑) 的解決方案。該技術隨機選擇伺服器的子集來建立會話。

[隨機孔徑](./random_aperture.jpg)

當然，隨機選擇會減少已建立會話的數量，如上圖所示。但是，問題是，隨機選擇多少台伺服器？這不是一個容易回答的問題，答案因客戶端的請求併發性而異。

為了回答上面的問題，Twitter 在隨機孔徑內安裝了一個反饋控制器，該控制器根據客戶端的負載決定子集大小。結果，我們能夠減少會話負載並確保可擴展性。然而，這個解決方案並不公平。我們可以在上面的插圖中看到不平衡，使得伺服器 4 沒有會話，而伺服器 0 有三個會話。

這種不平衡會產生諸如伺服器空閒、少數伺服器負載高等問題。因此，我們需要一個既公平又可擴展的解決方案。

**Solution 3 (解決方案 3)**：我們從解決方案 2 中了解到，我們可以通過子集化會話建立的數量來進行擴展。但是，我們未能公平地進行會話分發。為了解決這個問題，Twitter 提出了一個 deterministic aperture (確定性孔徑) 解決方案。這種方法的主要好處是：

- 客戶端和伺服器之間幾乎不需要協調即可收斂到一個解決方案。
- 如果由於任何原因客戶端或伺服器實例的數量發生任何變化，干擾最小。
對於此解決方案，我們將客戶端和伺服器表示在一個等距間隔的環中，其中環上的每個對象代表標有數字的節點或伺服器。下圖顯示了 Twitter 所說的離散環坐標 (即環上的特定點)。

[環坐標](./ring.jpg)

現在，我們組成客戶端和伺服器環來推導它們之間的關係。我們還定義了孔徑大小為 3。每個客戶端將與環中的三台伺服器建立會話。客戶端通過在環中順時針循環來選擇伺服器。這種方法類似於一致性雜湊，除了這裡我們保證伺服器在環上的均勻分發。讓我們看下面的插圖，其中客戶端分別與從給定伺服器列表中選擇的伺服器建立會話。

[合併客戶端和伺服器環坐標](./merge.jpg)

在上圖中，客戶端 0 與伺服器 4、5 和 0 建立會話。客戶端 1 與伺服器 0、1 和 2 建立會話，而客戶端 2 與伺服器 2、3 和 4 建立會話。當孔徑在相同大小的給定陣列子集中旋轉或移動時，每個客戶端的服務都有新的可用伺服器來建立會話。每台伺服器建立的會話數如下圖所示。

[每台伺服器建立的會話數](./sessions.jpg)

我們可以看到上面的直方圖中沒有空閒伺服器或負載高的伺服器。因此，我們為屬於同一服務的客戶端實現了公平分發。顯然，與隨機孔徑 (解決方案 02) 相比，我們通過改進伺服器之間的會話分發解決了一半的問題。然而，隨著客戶端數量的增加，不公平分發的問題可能會升級。在這種情況下，當多個客戶端 (服務) 與後端伺服器對話時，某些伺服器會變得擁擠。讓我們看下面的插圖來了解這個問題。

[兩個不同的客戶端與後端伺服器建立會話](./2clients.jpg)

上圖描述了隨著我們增加客戶端 (服務) 的數量，問題變得複雜。解決方案是連續的環坐標，我們使用重疊的環切片而不是環上的特定點來推導客戶端和伺服器之間的關係。這裡重要的是環的重疊可以是部分的，因為環上的伺服器可能沒有足夠的實例在客戶端之間平均分配。讓我們看下面的插圖。

[客戶端服務和伺服器之間的重疊](./overlapping.jpg)

上圖顯示客戶端 0 和 1 (對稱地) 共享同一台伺服器 (伺服器 1)。這意味著關於環坐標存在部分重疊。但是，這種重疊也可能導致不對稱共享。對稱或不對稱，負載平衡都可以通過 P2C 完成。例如，在上圖中，伺服器 1 和 3 將接收伺服器 2 獲得的一半負載。這意味著伺服器可以接收更多或更少的負載，具體取決於其與客戶端的重疊切片大小。

現在，我們知道如何將客戶端映射到伺服器的子集。我們將使用帶有連續環坐標的 P2C。客戶端將在其範圍內選擇點 (坐標)，而不是選擇伺服器的實例。選擇客戶端與後端伺服器建立會話的過程如下：

1. 在其範圍內選取兩個坐標 (偏移量，偏移量 + 寬度) 並將這些坐標映射到離散實例 (伺服器)。

2. 通過其交集程度，從兩個選擇的實例 (P2C) 中選擇負載最可忽略的一個實例。

```
注意：連續孔徑是可擴展且公平的，代價是由於部分重疊而在邊界節點上增加了額外的會話。它還能夠實現極少的協調和最小的干擾。
```
