# Evaluation of a Distributed Cache's Design (分佈式快取設計的評估)
## High performance (高性能)
以下是我們做出的有助於整體良好性能的一些設計選擇：

- 我們使用了一致性哈希。在該演算法下查找鍵需要 O(log(N)) 的時間複雜度，其中 N 代表快取分片的數量。
- 在快取伺服器內部，使用平均需要恆定時間的哈希表來定位鍵。
- LRU 逐出方法使用恆定時間來訪問和更新雙向鏈表中的快取條目。
- 快取客戶端和伺服器之間的通訊是通過 TCP 和 UDP 協議完成的，這也非常快。
- 由於我們添加了更多副本，如果單台機器上請求負載很高，這些副本可以減少我們必須面對的性能損失。
- 該設計的一個重要特徵是從 RAM 中添加、檢索和提供資料。因此，執行這些操作的延遲非常低。

```
注意：高性能的一個關鍵參數是逐出演算法的選擇，因為快取命中和未命中的數量取決於它。快取命中率越高，性能越好。
```

為了了解逐出演算法的重要性，我們假設如下：

- 快取命中服務時間 (99.9th 百分位數)：5 毫秒
- 快取未命中服務時間 (99.9th 百分位數)：30 毫秒 (這包括從資料庫獲取資料並設置快取的時間)

假設我們使用最頻繁使用 (MFU) 演算法的快取未命中率為 10%，而使用 LRU 演算法的快取未命中率為 5%。然後，我們使用以下公式：

EAT = Ratio_{hit} x Time_{hit} + Ratio_{miss} x Time_{miss}

這裡，這意味著以下內容：

EAT：Effective access time (有效訪問時間)。

Ratio_{hit}：快取命中發生的百分比。

Ratio_{miss}：快取未命中發生的百分比。

Time_{hit}：服務快取命中所需的時間。

Time_{miss}：服務快取未命中所需的時間。

對於 MFU，我們看到以下內容：
EAT = 0.90 x 5 milliseconds + 0.10 x 30 milliseconds = 0.0045 + 0.003 = 0.0075 = 7.5 milliseconds (毫秒)
對於 LRU，我們看到以下內容：
EAT = 0.95 x 5 milliseconds + 0.05 x 30 milliseconds =  0.00475 + 0.0015 = 0.00625 = 6.25 milliseconds (毫秒)
上面的數字強調了逐出演算法對提高快取命中率的重要性。每個應用程式都應進行實證研究，以確定針對特定工作負載提供更好結果的逐出演算法。

## Scalability (可擴展性)
我們可以根據需求和不斷變化的伺服器負載創建分片。當我們向集群添加新的快取伺服器時，由於一致性哈希，我們還必須進行有限數量的重新哈希計算。

添加副本可以減少熱分片上的負載。處理熱鍵問題的另一種方法是在這些鍵的範圍內進行進一步的分片。雖然單個鍵變熱的情況很少見，但快取客戶端有可能設計解決方案來避免單個熱鍵爭用問題。例如，快取客戶端可以智能地避免單個鍵成為瓶頸的情況，或者我們可以對特定鍵使用動態複製等。儘管如此，解決方案很複雜，超出了本課的範圍。

## High availability (高可用性)
我們通過冗餘快取伺服器提高了可用性。冗餘為我們的設計增加了一層可靠性和容錯能力。我們還使用領導者-追隨者演算法來方便地管理集群分片。但是，我們還沒有實現高可用性，因為我們有兩個分片副本，目前我們假設副本位於資料庫中心內。

通過在不同的資料中心之間拆分領導者和追隨者伺服器，可能實現更高的可用性。但如此高的可用性是以一致性為代價的。我們假設在同一個資料中心內進行同步寫入。但是在不同資料中心進行強一致性的同步寫入具有嚴重的性能影響，這在快取系統中是不受歡迎的。我們通常跨資料中心使用異步複製。

對於資料中心內的複製，我們可以獲得具有良好性能的強一致性。我們可以妥協跨資料中心複製的強一致性以實現更好的可用性 (參見 CAP 和 PACELC 定理)。

## Consistency (一致性)
可以同步或異步模式將資料寫入快取伺服器。在快取的情況下，異步模式有利於提高性能。因此，我們的快取系統遭受不一致的困擾。或者，強一致性來自同步寫入，但這會增加整體延遲，並且性能會受到影響。

不一致也可能源於錯誤的配置文件和服務。想像一種情況，在寫入操作期間快取伺服器宕機，而在其恢復後立即對其執行讀取操作。我們可以通過不允許任何加入或重新加入的伺服器在合理確定其已更新之前服務請求來避免這種情況。

## Affordability (可負擔性)
我們提出的設計成本低廉，因為使用商品硬體創建這樣的系統是可行的且實用的。

```
Question 1
問題 1
如果領導者節點在領導者-追隨者協議中失敗會發生什麼？

Answer
答案
在這種情況下可以使用兩種可能的解決方案：

使用領導者選舉演算法在可用追隨者集合中選舉新領導者。

使用單獨的分佈式配置管理服務來監控和選擇領導者。
```

```
Question 2
問題 2
將同步複製引入快取伺服器是個好主意嗎？

Answer
答案
快取集群上的同步複製將引入性能損失，因為將相同資料複製到所有快取伺服器需要時間。因此，在分別使用異步與同步複製時，性能和一致性之間存在權衡。

答案取決於用例。在快取伺服器的情況下，如果複製的伺服器靠近主伺服器，則同步複製是一個不錯的選擇。
```

```
Question 3
問題 3
假設大量並發請求被轉發到單個分片伺服器。如果伺服器使用 LRU 演算法，一些請求將導致快取未命中並向快取寫入新條目，而另一些將導致快取命中並最終從伺服器讀取。這些並發請求可能會相互競爭。因此，可能需要一些鎖定機制。但是，為所有讀寫操作鎖定整個資料結構將大大降低性能。您認為將如何處理此類問題？

Answer
答案
通常，對於共享資料的並發訪問，像信號量、監視器、互斥鎖等鎖定機制是不錯的選擇。但是隨著使用者數量 (快取命中時的讀者或快取未命中時的寫者) 的增加，鎖定整個資料結構並不是合適的解決方案。在這種情況下，我們可以考慮以下選項：

- Limited locking (有限鎖定)：在此策略中，僅鎖定整個資料結構的特定部分。雖然一些線程或進程可以同時從資料結構中讀取，但一些線程可能會暫時阻止對資料結構特定部分的訪問。
- Offline eviction (離線逐出)：離線逐出可能是一種可能性，即不對資料結構進行實際更改，而是在執行不同操作時僅記錄所需的更改，直到有必要提交更改為止。如果快取命中率很高，這種解決方案是可取的且容易的，因為當快取未命中發生時可能需要更改資料結構。
- Lock-free implementation (無鎖實現)：已經提出了多種解決方案，建議在雙向鏈表上進行同時讀寫是可行的，以支持大量並發讀寫。

鎖定機制：一種將共享資料的訪問僅限制為單個線程的機制。從而實現同步。
```

## Summary (總結)
我們研究了快取的基礎知識，並設計了一個具有良好可用性、高性能、高可擴展性和低成本的分佈式快取。我們的機制使用副本保持高可用性，儘管如果所有副本都在一個資料中心，這種方案將無法解決完整的資料中心故障。既然我們已經了解了設計的基礎知識，讓我們探索像 Memcached 和 Redis 這樣流行的開源框架。
