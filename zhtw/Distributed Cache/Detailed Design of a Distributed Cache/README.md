# Detailed Design of a Distributed Cache (分佈式快取的詳細設計)
本課程將確定分佈式快取的高層設計的一些缺點，並改進設計以彌補差距。讓我們開始吧。

## Find and remove limitations (查找並消除限制)
在我們進行詳細設計之前，我們需要了解并克服一些挑戰：

- 快取客戶端無法意識到快取伺服器的添加或故障。
- 該解決方案將遭受單點故障 (SPOF) 的問題，因為我們為每組快取資料都有一個快取伺服器。不僅如此，如果任何快取伺服器上的某些資料被頻繁訪問 (通常稱為熱鍵問題)，那麼我們的性能也會變慢。
- 我們的解決方案也沒有突出快取伺服器的內部結構。也就是說，它將使用什麼樣的資料結構來存儲以及它將使用什麼逐出策略？

### Maintain cache servers list (維護快取伺服器列表)
讓我們從解決第一個問題開始。我們將採取漸進步驟來尋求最佳解決方案。讓我們看看下面的幻燈片，了解下面描述的每個解決方案：

[[解決方案 1] 在每個伺服器中維護一個快取客戶端可以使用的配置文件](./solution1.jpg)

[[解決方案 2] 在集中位置維護配置文件](./solution2.jpg)

[[解決方案 3] 使用配置服務監控快取伺服器並保持快取客戶端更新](./solution3.jpg)

- **Solution 1 (解決方案 1)**：可以在快取客戶端所在的每個服務主機中都有一個配置文件。配置文件將包含快取客戶端有效利用快取伺服器所需的更新的運行狀況和元資料。配置服務的每個副本都可以通過任何 DevOps 工具通過推送服務進行更新。該策略的主要問題是配置文件必須手動更新並通過一些 DevOps 工具進行部署。
- **Solution 2 (解決方案 2)**：我們可以將配置文件存儲在一個集中位置，快取客戶端可以使用該位置獲取有關快取伺服器的更新資訊。這解決了部署問題，但我們仍然需要手動更新配置文件並監控每個伺服器的運行狀況。
- **Solution 3 (解決方案 3)**：處理該問題的一種自動方法是使用持續監控快取伺服器運行狀況的配置服務。除此之外，當將新的快取伺服器添加到集群時，快取客戶端會收到通知。當我們使用此策略時，在發生故障或添加新節點的情況下不需要人工干預或監控。最後，快取客戶端從配置服務獲取快取伺服器列表。

```
配置服務具有最高的運營成本。同時，這是一個複雜的解決方案。但是，它是我們提出的所有解決方案中最健壯的。
```

### Improve availability (提高可用性)
第二個問題涉及如果快取伺服器出現故障，快取將不可用。一個簡單的解決方案是添加副本節點。我們可以從在快取分片中添加一個主節點和兩個備份節點開始。使用副本，總是有可能出現不一致。如果我們的副本距離很近，則對副本的寫入是同步執行的，以避免分片副本之間的不一致。將快取資料在分片之間分配至關重要，這樣既不會出現不可用問題，也不會浪費任何硬體。

該解決方案有兩個主要優點：

- 在發生故障時提高了可用性。
- 熱分片可以有多個節點 (主-輔助) 進行讀取。
這種解決方案不僅會提高可用性，還會增加性能。

### Internals of cache server (快取伺服器的內部結構)
每個快取客戶端應使用三種機制來存儲和從快取伺服器中逐出條目：

- **Hash map (哈希映射)**：快取伺服器使用哈希映射在快取伺服器的 RAM 內存儲或定位不同的條目。下圖顯示該映射包含指向每個快取值的指針。
- **Doubly linked list (雙向鏈表)**：如果我們必須從快取中逐出資料，我們需要一個鏈表，以便我們可以根據訪問頻率對條目進行排序。下圖描述了如何使用雙向鏈表連接條目。
- **Eviction policy (逐出策略)**：逐出策略取決於應用程式的需求。在這裡，我們假設最近最少使用 (LRU) 逐出策略。

## Detailed design (詳細設計)

在解決了前面強調的三個問題中的每一個之後，我們現在準備正式確定詳細設計。請看下面的詳細設計：

[分佈式快取系統的詳細設計](./caching.jpg)

讓我們用幾點總結建議的詳細設計：

- 客戶端的請求通過負載平衡器到達快取客戶端所在的服務主機。
- 每個快取客戶端使用一致性哈希來識別快取伺服器。接下來，快取客戶端將請求轉發到維護特定分片的快取伺服器。
- 每個快取伺服器都有主伺服器和副本伺服器。在內部，每個伺服器都使用相同的機制來存儲和逐出快取條目。
- 配置服務確保所有客戶端看到快取伺服器的更新和一致視圖。
- 可以額外使用監控服務來記錄和報告快取服務的不同指標。

```
注意：設計的一個重要方面是快取條目是從 RAM 存儲和檢索的。我們在上一課中討論了 RAM 用於設計快取系統的適用性。
```

Question
問題
雖然一致性哈希是一個不錯的選擇，但它可能會導致資料分佈不均，並且某些伺服器可能會過載。我們如何解決這個問題？

Answer
答案
隨著時間的推移，已經建議了許多一致性哈希演算法的變體。我們可以使用這樣一種變體，它可以均勻地分配負載，甚至可以在不同的快取伺服器上製作相同資料的多個副本。每個快取伺服器內部可以有虛擬伺服器，機器中虛擬伺服器的數量取決於機器的能力。這導致對快取伺服器上的負載量進行更精細的控制。同時，它提高了可用性。
