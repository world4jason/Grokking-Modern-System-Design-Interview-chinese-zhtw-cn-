## Writing policies (寫入策略)
通常，快取存儲資料的副本 (或部分)，這些資料持久存儲在資料存儲中。當我們將資料存儲到資料存儲時，會出現一些重要問題：
- 我們先將資料存儲在哪裡？資料庫還是快取？
- 每種策略對一致性模型有什麼影響？

簡短的回答是，這取決於應用程式的需求。讓我們看看不同寫入策略的細節，以更好地理解這個概念：

- **Write-through cache (直寫快取)**：直寫機制同時寫入快取和資料庫。在兩個存儲上寫入可以並發發生或相繼發生。這會增加寫入延遲，但確保資料庫和快取之間的強一致性。
- **Write-back cache (回寫快取)**：在回寫快取機制中，資料首先寫入快取，然後異步寫入資料庫。雖然快取已更新資料，但在客戶端從資料庫讀取陳舊資料的情況下，不一致是不可避免的。但是，使用此策略的系統將具有較小的寫入延遲。
- **Write-around cache (繞寫快取)**：此策略僅將資料寫入資料庫。後來，當觸發資料讀取時，在快取未命中後將其寫入快取。資料庫將擁有更新的資料，但這種策略不利於讀取最近更新的資料。

## Eviction policies (逐出策略)
快取執行速度快的主要原因之一是它們很小。小快取意味著存儲容量有限。因此，我們需要一種逐出機制來從快取中刪除訪問頻率較低的資料。

幾種眾所周知的策略用於從快取中逐出資料。最著名的策略包括：

- Least recently used (LRU，最近最少使用)
- Most recently used (MRU，最近最多使用)
- Least frequently used (LFU，最不頻繁使用)
- Most frequently used (MFU，最頻繁使用)

還存在如先進先出 (FIFO) 等其他策略。這些演算法中每一種的選擇取決於正在開發的快取系統。

根據訪問頻率，資料可分為三個溫度區域：

- **Hot (熱)**：這是高度訪問的資料。
- **Warm (溫)**：這是訪問頻率較低的資料。
- **Cold (冷)**：這是很少訪問的資料。
冷資料經常從快取中逐出，並被熱資料或溫資料替換。下圖顯示了資料溫度的範圍：

## Cache invalidation (快取失效)
除了逐出訪問頻率較低的資料外，駐留在快取中的某些資料可能會隨著時間的推移而變得陳舊或過期。此類快取條目是無效的，必須標記為刪除。

情況需要一個問題：我們如何識別陳舊條目？

解決該問題需要存儲與每個快取條目相對應的元資料。具體來說，維護生存時間 (TTL) 值以處理過期的快取項。

我們可以使用兩種不同的方法來處理使用 TTL 的過期項：

- **Active expiration (主動過期)**：此方法通過守護進程或線程主動檢查快取條目的 TTL。
- **Passive expiration (被動過期)**：此方法在訪問時檢查快取條目的 TTL。
```
TTL 是快取條目被認為過期之後的時間。
發現後，每個過期項都會從快取中刪除。

## Storage mechanism (存儲機制)
在快取中存儲資料並不像看起來那麼簡單，因為分佈式快取有多個快取伺服器。當我們使用多個快取伺服器時，需要回答以下設計問題：

- 我們應該將哪些資料存儲在哪個快取伺服器中？
- 我們應該使用哪種資料結構來存儲資料？

上述兩個問題是重要的設計問題，因為它們將決定我們分佈式快取的性能，這是我們最重要的需求。我們將使用以下技術來回答上述問題。

### Hash function (哈希函數)
可以在兩種不同的場景中使用哈希：

- 識別分佈式快取中的快取伺服器以存儲和檢索資料。
- 定位每個快取伺服器內的快取條目。

對於第一種情況，我們可以使用不同的哈希演算法。然而，一致性哈希或其變體通常在分佈式系統中表現良好，因為簡單哈希在崩潰或擴展的情況下並不理想。

在第二種情況下，我們可以使用典型的哈希函數來定位要讀取或寫入快取伺服器內的快取條目。但是，僅憑哈希函數只能定位快取條目。它沒有說明如何在快取伺服器內管理資料。也就是說，它沒有說明如何實施策略從快取伺服器中逐出訪問頻率較低的資料。它也沒有說明使用什麼資料結構來存儲快取伺服器內的資料。這正是存儲機制的第二個設計問題。接下來讓我們看看資料結構。

### Linked list (鏈表)
我們將使用雙向鏈表。主要原因是其廣泛使用和簡單性。此外，在我們的情況下，從雙向鏈表中添加和刪除資料將是一個恆定時間操作。這是因為我們要麼從鏈表的尾部逐出特定條目，要麼將條目重新定位到雙向鏈表的頭部。因此，不需要迭代。

```
注意：布隆過濾器是快速查找快取伺服器中是否存在快取條目的有趣選擇。我們可以使用布隆過濾器來確定快取條目絕對不存在於快取伺服器中，但其存在的可能性是概率性的。布隆過濾器在大型快取或資料庫系統中非常有用。
```

### Sharding in cache clusters (快取集群中的分片)
為了避免 SPOF 和單個快取實例上的高負載，我們引入了分片。分片涉及將快取資料拆分到多個快取伺服器之間。它可以通過以下兩種方式執行。

#### Dedicated cache servers (專用快取伺服器)
在專用快取伺服器方法中，我們將應用和 Web 伺服器與快取伺服器分開。

使用專用快取伺服器的優點如下：

- 每種功能在硬體選擇方面具有靈活性。
- 可以分別擴展 Web/應用伺服器和快取伺服器。

除了上述優點外，作為獨立快取服務工作還使其他微服務能夠從中受益——例如，快取即服務 (Cache as a Service)。在這種情況下，快取系統必須了解不同的應用程式，以便它們的資料不會衝突。

[服務主機與專用快取伺服器協調的描述](./cache_servers1.jpg)

#### Co-located cache (並置快取)
並置快取將快取和服務功能嵌入同一主機中。

這種策略的主要優點是減少了額外硬體的資本支出 (CAPEX) 和運營支出 (OPEX)。此外，隨著一項服務的擴展，另一項服務也會自動擴展。但是，一台機器的故障將導致兩項服務同時丟失。

```
CAPEX：資本支出是對長期持有的資產的重大投資。

OPEX：運營支出是維持公司運轉的日常費用。

## Cache client (快取客戶端)
我們討論過應該使用哈希函數來選擇快取伺服器。但是什麼實體執行這些哈希計算呢？

快取客戶端是駐留在託管伺服器中的一段代碼，它執行 (哈希) 計算以在快取伺服器中存儲和檢索資料。此外，快取客戶端可以與其他系統組件 (如監控和配置服務) 協調。所有快取客戶端都以相同的方式編程，以便來自不同客戶端的相同 PUT 和 GET 操作返回相同的結果。快取客戶端的一些特徵如下：

- 每個快取客戶端都知道所有快取伺服器。
- 所有客戶端都可以使用眾所周知的傳輸協議 (如 TCP 或 UDP) 與快取伺服器通訊。

```
PUT：向快取伺服器添加資料。

GET：從快取伺服器檢索資料。
```

```
Question
問題
如果其中一個快取伺服器死機，快取客戶端對訪問請求的行為將是什麼？

Answer
答案
由於快取伺服器內的資料將不再可用，快取客戶端將把該訪問請求標記為快取未命中。
```

## Conclusion (結論)
在本課中，我們了解了什麼是分佈式快取，並強調了它們在分佈式系統中的重要性。我們還討論了不同的快取存儲和逐出機制。快取對於任何分佈式系統都至關重要，並且位於系統設計的不同點。了解如何將分佈式快取設計為大型系統的一部分非常重要。
