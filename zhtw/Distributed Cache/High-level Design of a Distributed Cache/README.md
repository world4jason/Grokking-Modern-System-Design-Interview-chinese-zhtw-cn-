# High-level Design of a Distributed Cache (分佈式快取的高層設計)
在本課中，我們將學習設計分佈式快取。我們還將討論隨著我們開發解決方案的過程中可能出現的權衡和設計選擇。

## Requirements (需求)
讓我們首先了解我們解決方案的需求。

### Functional (功能需求)
以下是功能需求：

- **Insert data (插入資料)**：分佈式快取系統的使用者必須能夠向快取中插入條目。
- **Retrieve data (檢索資料)**：使用者應該能夠檢索與特定鍵對應的資料。

[分佈式快取的功能和非功能需求](./req.jpg)

### Non-functional requirements (非功能需求)
我們將考慮以下非功能需求：

- **High performance (高性能)**：快取的主要原因是實現快速檢索資料。因此，插入和檢索操作都必須很快。

- **Scalability (可擴展性)**：快取系統應該在請求數量增加時水平擴展，沒有瓶頸。

- **High availability (高可用性)**：快取的不可用性將給資料庫伺服器增加額外負擔，這也可能在峰值負載間隔期間宕機。我們還要求我們的系統能夠在組件和網絡的偶爾故障以及停電中倖存下來。

- **Consistency (一致性)**：存儲在快取伺服器上的資料應該是一致的。例如，從不同快取伺服器 (主或輔助) 檢索相同資料的不同快取客戶端應該是最新資料。

- **Affordability (可負擔性)**：理想情況下，快取系統應從商品硬體設計，而不是系統設計中昂貴的支持組件。

## API design (API 設計)
這個問題的 API 設計相當簡單，因為只有兩個基本操作。


### Insertion (插入)
執行插入的 API 調用應如下所示：
```
insert(key, value)
```

Parameter (參數)     Description (描述)

key                  這是一個唯一標識符。

value                這是針對唯一鍵存儲的資料。
此函數返回確認或描述伺服器端問題的錯誤。

### Retrieval (檢索)
從快取中檢索資料的 API 調用應如下所示：
```
retrieve(key)
```

Parameter (參數)   Description (描述)

key                這返回針對鍵存儲的資料。
此調用將對象返回給調用者。

```
Question
問題
分佈式快取的 API 設計看起來與鍵值存儲完全相同。鍵值存儲和分佈式快取之間可能存在哪些差異？

Answer
答案
一些主要區別如下：

- 鍵值存儲需要持久地存儲資料 (持久性)。快取用於補充持久存儲以提高讀取性能。

- 快取從 RAM 提供資料。鍵值存儲將資料寫入非易失性存儲。

- 鍵值存儲是健壯的，應該在故障中倖存下來。但是，快取可能會崩潰並在恢復後從頭開始填充。
```

## Design considerations (設計注意事項)
在設計分佈式快取系統之前，考慮一些設計選擇很重要。這些選擇中的每一個都純粹基於我們的應用程式需求。但是，我們可以在這裡強調一些關鍵區別：

### Storage hardware (存儲硬體)
如果我們的資料很大，我們可能需要分片，因此使用分片伺服器進行快取分區。這些分片伺服器應該是專用硬體還是商品硬體？專用硬體將具有良好的性能和存儲容量，但成本更高。我們可以從商品伺服器構建大型快取。一般來說，分片伺服器的數量將取決於快取的大小和訪問頻率。

此外，我們可以考慮將資料存儲在這些伺服器的二級存儲中以實現持久性，同時我們仍然從 RAM 提供資料。二級存儲可用於發生重啟且快取重建需要很長時間的情況。但是，如果有專用的持久層 (如資料庫)，則快取系統中可能不需要持久性。

```
Facebook 在 2013 年使用商品機器構建了 28 TB 的快取。
```

### Data structures (資料結構)
設計的一個重要部分必須是訪問資料的速度。哈希表是平均需要恆定時間來存儲和檢索資料的資料結構。此外，我們需要另一個資料結構來對快取資料強制執行逐出演算法。特別是，鏈表是一個不錯的選擇 (如上一課所討論的)。

此外，我們需要了解快取可以存儲什麼樣的資料結構。儘管我們在 API 設計部分討論過，為了簡單起見我們將使用字符串，但可以在快取中存儲不同的資料結構或格式，如哈希映射、數組、集合等。在下一課中，我們將看到此類快取的一個實際例子。

### Cache client (快取客戶端)
發出插入和檢索調用的是客戶端進程或庫。客戶端進程的位置是一個設計問題。例如，如果快取僅供內部使用，則可以將客戶端進程放置在服務主機中。否則，如果快取系統作為服務提供以供外部使用，則專用快取客戶端可以將使用者的請求發送到快取伺服器。

### Writing policy (寫入策略)
快取和資料庫上的寫入策略具有一致性含義。一般來說，沒有最佳選擇，但根據我們的應用程式，寫入策略的偏好非常重要。

### Eviction policy (逐出策略)
根據設計，快取提供低延遲的讀取和寫入。為此，資料通常從 RAM 內存提供。通常，與完整資料集相比，由於快取大小有限，我們無法將所有資料放入快取中。因此，我們需要仔細決定什麼留在快取中以及如何為新條目騰出空間。

隨著新資料的添加，一些現有資料可能必須從快取中逐出。但是，選擇受害條目取決於逐出策略。存在許多逐出策略，但選擇再次取決於使用它的應用程式。例如，最近最少使用 (LRU) 對於最近上傳的內容可能會獲得最多觀看的社交媒體服務來說是一個不錯的選擇。

除了上述部分的詳細資訊外，優化生存時間 (TTL) 值在減少快取未命中次數方面也能發揮重要作用。

## High-level design (高層設計)
下圖描述了我們的高層設計：

[分佈式快取的高層設計](./design.jpg)

此高層設計中的主要組件如下：

- **Cache client (快取客戶端)**：此庫駐留在服務應用伺服器中。它保存有關快取伺服器的所有資訊。快取客戶端將使用哈希和搜尋演算法為每個傳入的插入和檢索請求選擇一個快取伺服器。所有快取客戶端都應該對所有快取伺服器具有一致的視圖。此外，將資料移入和移出快取伺服器的解析技術應該是相同的。否則，不同的客戶端將請求不同的伺服器以獲取相同的資料。

- **Cache servers (快取伺服器)**：這些伺服器維護資料的快取。所有快取客戶端都可以訪問每個快取伺服器。每個伺服器都連接到資料庫以存儲或檢索資料。快取客戶端使用 TCP 或 UDP 協議執行與快取伺服器的資料傳輸。但是，如果任何快取伺服器宕機，則對這些伺服器的請求將由快取客戶端解析為未命中快取。
