## Indexing (索引)
索引是對資料進行組織和操作，以促進快速準確的資訊檢索。

搜尋查詢的響應時間取決於幾個因素：

- 資料庫中的資料組織策略。
- 資料的大小。
- 用於構建索引和處理搜尋查詢的機器的處理速度和 RAM。

在數十億個文檔級索引的文檔上運行搜尋查詢將是一個緩慢的過程，可能需要幾分鐘甚至幾小時。讓我們看看另一種有助於減少搜尋時間的資料組織和處理技術。

#### Inverted index (倒排索引)
倒排索引是一種類似 HashMap 的資料結構，它採用文檔-術語矩陣。它不是按原樣存儲完整的文檔，而是將文檔拆分為單個單詞。此後，文檔-術語矩陣識別唯一單詞並丟棄頻繁出現的單詞，如“to”、“they”、“the”、“is”等。像這樣頻繁出現的單詞被稱為術語 (terms)。文檔-術語矩陣通過識別唯一單詞和刪除不必要的術語來維護術語級索引。

對於每個術語，索引計算以下資訊：

- 術語出現的文檔列表。
- 術語在每個文檔中出現的頻率。
- 術語在每個文檔中的位置。

倒排索引是文檔檢索中最受歡迎的索引機制之一。它能夠高效實現布爾、擴展布爾、鄰近度、相關性以及許多其他類型的搜尋算法。

**Advantages of using an inverted index (使用倒排索引的優點)**

- 倒排索引便於全文搜尋。
- 倒排索引減少了運行時計算單詞在每個文檔中出現次數的時間，因為我們有針對每個術語的映射。

**Disadvantages of using an inverted index (使用倒排索引的缺點)**

- 維護倒排索引以及實際文檔存在存儲開銷。但是，我們減少了搜尋時間。
- 添加、更新或刪除文檔時的維護成本 (處理)。要添加文檔，我們從文檔中提取術語。然後，對於每個提取的術語，我們要麼在倒排索引中添加新行，要麼如果該術語在倒排索引中已有條目，則更新現有行。同樣，對於刪除文檔，我們會進行處理以在倒排索引中查找已刪除文檔術語的條目，並相應地更新倒排索引。

```
布爾搜尋 (Boolean searching) 基於英國數學家喬治·布爾建立的符號邏輯方法。它允許您通過將單詞和短語與單詞 AND、OR 和 NOT (也稱為布爾運算符) 組合來限制、擴展或定義您的搜尋。來源：維基百科

擴展布爾搜尋 (Extended Boolean search) 克服了布爾搜尋的缺點。布爾搜尋的主要缺點是它不包含布爾查詢中的術語權重，產生的結果集要麼太小要麼太大。擴展布爾搜尋利用部分匹配和術語權重。它為查詢和文檔之間的相似性分配分數。這樣，如果文檔匹配部分搜尋詞，它可能相關並作為結果返回，而在布爾搜尋中則不然。來源：維基百科)

鄰近搜尋 (Proximity search) 查找兩個或多個分別匹配的術語出現在一定距離內的文檔，其中距離是中間單詞或字符的數量。來源：維基百科)

相關性搜尋 (Relevance search) 衡量搜尋查詢和搜尋結果之間關係的準確性。來源：維基百科
```

### Factors of index design (索引設計的因素)
以下是我們在設計索引時應牢記的一些因素：

- **Size of the index (索引的大小)**: How much computer memory, and RAM, is required to keep the index. We keep the index in the RAM to support the low latency of the search.
- **索引的大小**：保持索引需要多少計算機內存和 RAM。我們將索引保存在 RAM 中以支持搜尋的低延遲。
- **Search speed (搜尋速度)**: How quickly we can find a word from an inverted index.
- **搜尋速度**：我們能多快從倒排索引中找到一個單詞。
- **Maintenance of the index (索引的維護)**: How efficiently the index can be updated if we add or remove a document.
- **索引的維護**：如果我們添加或刪除文檔，索引的更新效率如何。
- **Fault tolerance (容錯性)**: How critical it is for the service to remain reliable. Coping with index corruption, supporting whether invalid data can be treated in isolation, - dealing with defective hardware, partitioning, and replication are all issues to consider here.
- **容錯性**：服務保持可靠的重要性。處理索引損壞，支持是否可以隔離處理無效資料，處理有缺陷的硬體、分區和複製都是這裡需要考慮的問題。
- **Resilience (彈性)**: How resilient the system is against someone trying to game the system and guard against search engine optimization (SEO) schemes, since we return only a handful of relevant results against a search.
- **彈性**：系統在應對試圖利用系統的人和防範搜尋引擎優化 (SEO) 方案方面的彈性如何，因為我們只返回少數相關的搜尋結果。

鑑於上述設計因素，讓我們看看在集中式系統上構建索引的一些問題。

```
無效資料：沒有意義或不存在的資料添加到索引後會影響我們搜尋的性能。我們必須在將此類資料添加到索引之前檢測到它。
```

## Indexing on a centralized system (集中式系統上的索引)
在集中式搜尋系統中，所有搜尋系統組件都在單個節點上運行，該節點的計算能力相當強。集中式搜尋系統的架構如下圖所示：

[集中式搜尋系統的架構](./arch.jpg)

- 索引過程將文檔作為輸入並將其轉換為倒排索引，該索引以二進制文件的形式存儲。
- 查詢處理或搜尋過程解釋包含倒排索引的二進制文件。它還計算給定查詢的倒排列表的交集，以返回針對該查詢的搜尋結果。


這些是集中式搜尋系統架構帶來的問題：

- SPOF (單點故障)
- 伺服器過載
- 索引過大

**SPOF**：集中式系統是單點故障。如果它死了，就無法執行搜尋操作。

**伺服器過載**：如果許多使用者執行查詢並且查詢很複雜，這會給伺服器 (節點) 帶來壓力。

**索引過大**：倒排索引的大小隨著文檔數量的增加而增加，對單個伺服器提出了資源需求。計算機系統越大，管理它的成本和複雜性就越高。

```
注意：使用分佈式系統，利用低成本計算機系統，總體上具有成本效益。
```

添加文檔或運行搜尋查詢時，需要將倒排索引加載到主內存中。為了提高效率，大部分倒排索引必須放入機器的 RAM 中。

根據 Google Analytics 2022 年的資料，有數千億個網頁，總大小約為 100 PB。如果我們為萬維網製作一個搜尋系統，倒排索引的大小也將是 PB 級。這意味著我們必須將 PB 級的資料加載到 RAM 中。增加單台機器的資源來索引十億個頁面，而不是轉向分佈式系統並利用並行化的力量，這是不切實際且低效的。在單個大型倒排索引上運行搜尋查詢會導致響應時間變慢。

```
注意：從放有一百本書的架子上搜尋一本書比從放有一百萬本書的架子上搜尋一本書更容易。搜尋時間隨著我們搜尋的資料量的增加而增加。
```

對集中式索引的攻擊比對分佈式索引系統的攻擊影響更大。此外，分佈式索引中出現瓶頸 (可能出現在伺服器帶寬或 RAM 中) 的機率也較低。
