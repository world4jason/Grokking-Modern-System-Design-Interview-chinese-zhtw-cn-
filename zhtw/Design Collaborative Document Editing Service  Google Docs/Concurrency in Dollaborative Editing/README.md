# Concurrency in Collaborative Editing (協同編輯中的併發)
## Introduction (簡介)
我們已經討論了協同文件編輯服務的設計，但我們還沒有解決如何處理不同使用者對文件的併發更改。然而，在討論併發問題之前，我們需要了解協同文字編輯器。

## What is a document editor? (什麼是文件編輯器？)
文件是按特定順序排列的字元的組合。每個字元都有一個值和一個位置索引。字元可以是字母、數字、Enter 鍵 (↵) 或空格。索引表示字元在有序字元列表中的位置。

文字或文件編輯器的工作是對文件中的字元執行諸如 insert() (插入)、delete() (刪除)、edit() (編輯) 等操作。下面是文件以及編輯器將如何執行這些操作的描述。

[文件編輯器如何執行不同的操作](./editor.jpg)

## Concurrency issues (併發問題)
不同使用者對同一文件的協作可能會導致併發問題。每當多個使用者編輯文件的同一部分時，就可能發生衝突。由於使用者擁有文件的本地副本，伺服器上的文件最終狀態可能與使用者在他們端看到的狀態不同。在伺服器推送更新版本後，使用者會發現意外的結果。

### Example 1 (範例 1)
讓我們考慮一個場景，其中兩個使用者想在相同的位置索引處新增一些字元。在下面，我們描述了兩個使用者修改同一個句子如何導致相互衝突的結果：

[兩個使用者修改同一文字如何導致併發問題](./concurrency.jpg)

如上所示，兩個使用者試圖修改同一個句子“Educative by developers”。兩個使用者都在索引 10 處執行 insert()。有兩種可能性如下：

- 短語“for developers”覆蓋了“platform”。這導致了“for developers”的結果。
- 短語“platform”重疊了“for developers”。這導致了“platformlopers”的結果。

此範例表明，以不同順序應用的操作不具有交換律 (commutative property)。

### Example 2 (範例 2)
讓我們看另一個簡單的例子，其中兩個使用者試圖從一個單詞中刪除同一個字元。讓我們使用單詞“EEDUCATIVE”。因為這個詞有一個額外的“E”，兩個使用者都想刪除這個額外的字元。在下面，我們看到可能會發生意外的結果：

[刪除同一字元如何導致意外更改](./deletion.jpg)

這第二個例子表明，應用相同操作的不同使用者不會是冪等的 (idempotent)。因此，在多個協作者同時編輯文件的同一部分時，衝突解決是必要的。

Idempotent (冪等)：具有相同輸入的操作無論重複多少次，都會產生相同的結果。
```

從上面的例子中，我們了解到協同編輯中併發問題的解決方案應該遵守兩條規則：

- Commutativity (交換律)：應用操作的順序不應影響最終結果。
- Idempotency (冪等性)：重複的類似操作應該只應用一次。

下面，我們確定了兩種眾所周知的衝突解決技術。

## Techniques for conflict resolution (衝突解決技術)
讓我們討論用於協同編輯中衝突解決的兩種領先技術。

### Operational transformation (操作轉換)
操作轉換 (OT) 是一種廣泛用於協同編輯中衝突解決的技術。OT 出現於 1989 年，並在多年來不斷改進。它是一種用於衝突解決的無鎖和非阻塞方法。如果協作者之間的操作發生衝突，OT 會解決衝突並將正確的收斂狀態推送到終端使用者。因此，OT 為使用者提供了一致性。

OT 使用位置索引方法執行操作來解決衝突，例如我們上面討論的那些。OT 通過保持交換律和冪等性來解決上述問題。

[確保交換律 1](./ot1.jpg)

[確保交換律 2](./ot2.jpg)

基於 OT 的協同編輯器如果具有以下兩個屬性，則是一致的：

- Causality preservation (因果關係保持)：如果操作 a 在操作 b 之前發生，則操作 a 在操作 b 之前執行。
- Convergence (收斂)：不同客戶端的所有文件副本最終將是相同的。

上述屬性是 CC 一致性模型的一部分，該模型是協同編輯中一致性維護的模型。

多年來，研究界提出了各種一致性模型。其中一些是特定於協同編輯的，而另一些是特定於 OT 演算法的。關鍵的一致性模型如下：

- CC model (CC 模型)：正如我們上面定義的，這包括因果關係保持和收斂。
- CCI model (CCI 模型)：這包括因果關係保持 (與 CC 模型相同)、收斂 (與 CC 模型相同) 和意圖保持 (此屬性確保操作按使用者的意圖執行)。

其他模型包括 CSM (因果關係、單操作效應和多操作效應) 模型和 CA (因果關係和可接受性) 模型。

建議了各種一致性模型，通常，較新的模型是早期模型的超集。因為有太多提出的演算法，討論它們超出了本課的範圍。感興趣的讀者可以在 https://dl.acm.org/doi/pdf/10.1145/289444.289469 中找到更多詳細資訊。
```

OT 有兩個缺點：

- 對字元的每個操作可能需要更改位置索引。這意味著操作彼此之間是順序依賴的。

- 它很難開發和實現。

操作轉換是一組複雜的演算法，其正確實現已被證明對現實世界的應用程式具有挑戰性。例如，Google Wave 團隊花了兩年時間來實現 OT 演算法。

### Conflict-free Replicated Data Type (CRDT) (無衝突複製資料類型)
無衝突複製資料類型 (CRDT) 的開發是為了改進 OT。CRDT 具有複雜的資料結構，但演算法簡化了。

CRDT 通過為每個字元分配兩個關鍵屬性來滿足交換律和冪等性：

- 它為每個字元分配一個全域唯一標識。
- 它全域排序每個字元。

每個操作現在都有一個更新的資料結構：

[CRDT 的簡化資料結構](./crdt.jpg)

SiteID 唯一標識請求帶有 Value (值) 和 PositionalIndex (位置索引) 操作的使用者站點。PositionalIndex 的值可以是分數，主要有兩個原因。

- 由於某些操作，其他字元的 PositionalIndex 不會改變。
- 將避免不同使用者之間操作的順序依賴性。

下面的範例描述了來自站點 ID 123e4567-e89b-12d3 的使用者正在 PositionalIndex 為 1.5 處插入值為 A 的字元。雖然新增了一個新字元，但使用分數索引保留了現有字元的位置索引。因此，避免了操作之間的順序依賴性。如下所示，在 O 和 T 之間插入 insert() 不會影響 T 的位置。

[防止操作之間的順序依賴性](./prevention.jpg)

CRDT 確保使用者之間的強一致性。即使某些使用者處於離線狀態，終端使用者的本地副本在重新上線時也會收斂。

雖然像 Google Docs、Etherpad 和 Firepad 這樣知名的線上編輯平台使用 OT，但 CRDT 使協同文件編輯中的併發和一致性變得容易。事實上，使用 CRDT，可以實現無伺服器的點對點協同文件編輯服務。

注意：OT 和 CRDT 是協同編輯中衝突解決的良好解決方案，但我們使用 WebSockets 可以突出顯示協作者的游標。其他使用者將預測協作者下一個操作的位置並自然地避免衝突。

Question 1 (問題 1)
為什麼我們不能使用鎖在使用者之間進行同步？

Answer (答案)
鎖要求我們將文件分割成小部分，使用者可以鎖定一部分並對其進行編輯。這將幫助開發人員想出一個簡單的解決方案，並避免像 OT 和 CRDT 這樣的複雜性。然而，這也會導致糟糕的使用者體驗。例如，兩個使用者可能想在文件的同一部分新增字元，但他們的操作不一定會衝突。

對於像 Google Sheets 這樣的服務來說，鎖是一個不錯的選擇。這是因為文件被分成大小相等的小單元格，只有一個使用者可以新增或編輯特定單元格的內容。
```

Question 2 (問題 2)
如果有兩個使用者在協作處理文件，並且他們的網際網路速度不同，會發生什麼？在哪種情況下，OT 或 CRDT 哪種技術更適合衝突解決？

Answer (答案)
隨著網際網路連接速度的變化，使用者之間的操作順序可能會導致問題。然而，操作在 OT 中是順序依賴的，而在 CRDT 中操作是順序無關的。這就是為什麼 CRDT 是解決此類問題的合適方案。
```
