# Final Design of Quora (Quora 的最終設計)
## Limitations of the proposed design (提議設計的局限性)
提議的設計滿足了所有功能需求。然而，隨著我們的擴展，它出現了一些嚴重的缺點。這意味著我們無法滿足非功能需求。讓我們在下面探討主要的缺點：

- **Limitations of web and application servers (Web 和應用程式伺服器的局限性)**：為了滿足使用者的請求，負載在 Web 和應用程式伺服器之間傳輸，由於這兩類伺服器之間的網路 I/O，這增加了延遲。即使我們通過將 Web 與應用程式伺服器 (即管理器和工作進程) 分開來實現並行計算，由於額外的網路鏈接導致的額外延遲也會損害使用者的體驗。除了資料傳輸之外，路由器庫與管理器和工作進程之間的控制通訊也會帶來額外的效能損失。

- **In-memory queue failure (記憶體中隊列故障)**：應用程式伺服器的內部架構記錄任務並將其轉發到記憶體中隊列，這些隊列為工作者提供服務。這些不同優先順序的記憶體中隊列可能會發生故障。例如，如果隊列丟失，則該隊列中的所有任務也會丟失，並且需要手動工程來恢復這些任務。這極大地降低了系統的效能。另一方面，複製這些隊列需要增加 RAM 大小。此外，隨著我們系統提供的功能 (功能需求) 數量的增加，許多任務可能會被組裝起來，從而導致記憶體不足。同時，不希望用不那麼緊急的任務阻塞應用程式伺服器。例如，應用程式伺服器不應背負諸如儲存答案的查看計數、向資料庫新增統計資料以供以後分析等任務。

- **Increasing QPS on MySQL (MySQL 上的 QPS 增加)**：因為我們的系統提供了更多的功能，所以很少有 MySQL 表收到大量使用者查詢。這導致某些 MySQL 伺服器上的 QPS 較高，從而導致較高的延遲。此外，我們的設計中沒有定義災難恢復管理的方案。

- **Latency of HBase (HBase 的延遲)**：儘管 HBase 允許高實時吞吐量，但其 P99 延遲並不是最好的。許多 Quora 功能需要具有自身延遲的 ML 引擎。由於增加了 HBase 的較高延遲，系統的整體效能會隨著時間的推移而下降。

```
P99 代表第 99 個百分位數。這意味著 99% 的查詢在特定數字以下得到處理。例如，20 毫秒的 P99 意味著 99% 的查詢將在 20 毫秒內由伺服器回复。
```

## Detailed design of Quora (Quora 的詳細設計)
讓我們了解我們設計中的改進：

### Service hosts (服務主機)
我們將 Web 和應用程式伺服器組合到一台可以同時處理所有進程的強大機器中。此技術消除了網路 I/O 以及管理器、工作者和路由庫進程之間所需的網路跳躍所引入的延遲。下圖提供了更新後的 Web 伺服器架構的抽象視圖：

[Web 和應用程式伺服器在服務主機中組合的更新設計](./servers.jpg)


### Vertical sharding of MySQL (MySQL 的垂直分片)
MySQL 伺服器中的表被轉換為單獨的分片，我們稱為分區。一個分區有一個主伺服器和多個副本伺服器。

目標是提高效能並減少由於單個資料庫表上查詢數量增加而導致的負載。為了實現這一點，我們以兩種方式進行垂直分片：

1. 我們將單個資料庫的表拆分為多個分區。該概念在分區 2 和 3 中描述，分別嵌入了表 4 和 3。
2. 我們將多個表合併到一個分區中，預計將進行連接操作。該概念在分區 1 中描述，它嵌入了表 1 和 2。
因此，我們能夠同地協作相關資料並減少熱點資料的流量。下圖描述了 Quora 的垂直分片。

[Quora 的垂直分片架構](./partitions.jpg)

完成分區後，我們需要兩種類型的映射或元資料來完成我們的擴展過程：

1. 哪些分區包含哪些表和列？
2. 哪些主機是特定分區的主伺服器和副本伺服器？
這兩種映射都由像 ZooKeeper 這樣的服務維護。

上面的分片設計確保了可擴展性，因為我們能夠在單個分區中定位相關資料，因此無需從多個分片查詢資料。此外，對於熱分片，可以增加讀取副本的數量，或者可以執行進一步的分片。對於可能需要連接的邊緣情況，我們可以在應用程式級別執行它。

```
注意：垂直分片在 Quora 的設計中特別受關注，因為水平分片在資料庫社區中更為常見。垂直分片背後的主要思想是通過仔細劃分或重新定位表並消除跨不同分片的連接操作來實現可擴展性。儘管如此，垂直分片的分區或表可以水平增長到一定程度，這時水平分片對於保持可接受的效能將是必要的。
```

新設計嵌入了 MyRocks 作為鍵值儲存而不是 HBase。我們使用 MyRocks 版本的 RocksDB 主要有兩個原因：

1. MyRocks 具有較低的 p99 延遲而不是 HBase。Quora 聲稱使用 MyRocks 將 P99 延遲從 80 毫秒降低到 4 毫秒。
2. 有操作工具可以在 MyRocks 和 MySQL 之間傳輸資料。

```
注意：Quora 通過從儲存在 MySQL 中的問題和答案中提取特徵來為 ML計算引擎提供服務。在這種情況下，操作工具可以派上用場，在 MyRocks 和 MySQL 之間傳輸資料。
```

我們更新的設計通過將不那麼緊急的任務與常規 API 調用分開來減少服務主機上的請求負載。為此，我們使用 Kafka，它可以將作業分發到各種隊列中，用於諸如查看計數器 (參見分片計數器)、通知系統、分析以及向使用者突出顯示主題等任務。這些作業中的每一個都是通過 cron 作業執行的。

```
cron 作業：也稱為“cron”，是一種命令行實用程式，用於在類 UNIX 操作系統上調度任務。
```

### Technology usage (技術使用)
快速擴展的服務幾乎沒有時間開發新功能和處理來自使用者越來越多的請求。此類服務利用雲基礎設施來處理流量高峰。此外，編程語言的選擇也很重要。就像我們提到 YouTube 選擇 Python 進行更快的編程一樣，我們可以將同樣的邏輯應用於 Quora。事實上，Quora 使用 Python Paste Web 框架。

最好使用像 C++ 這樣更快的編程語言來開發特徵提取服務。對於通過 ML 引擎的在線推薦服務，特徵提取服務應該很快，以使 ML 引擎能夠完成準確的推薦。不僅如此，減少 ML 引擎的延遲負擔使其能夠提供更廣泛的服務。我們可以利用 Thrift 服務來支持不同組件內編程語言之間的互操作性。

```
特徵提取服務：Quora 將其特徵提取服務稱為 Alchemy，這是一種可擴展的高效能工具。
```

諸如評論、贊成和反對等功能需要從客戶端頻繁更新頁面。輪詢是一種技術，其中客戶端 (瀏覽器) 頻繁請求伺服器進行新更新。伺服器可能有也可能沒有任何更新，但仍會響應客戶端。因此，伺服器可能會無用地負擔過重。為了解決這個問題，Quora 使用了一種稱為長輪詢的技術，如果客戶端請求更新，如果沒有更新，伺服器可能在長達 60 秒的時間內不會響應。但是，如果有更新，伺服器將立即回覆並允許客戶端發出新請求。

```
Question 1
服務主機內不同的管理器和工作進程之間的通訊什麼是好方法？

Answer
兩種通訊方法是可行的：

1. UNIX sockets (UNIX 套接字)
2. TCP connections (TCP 連接)

套接字 (Unix 或 TCP) 允許發送方和接收方之間進行具有適當流量控制 (在 TCP 情況下為擁塞控制) 的資料流傳輸。這意味著發送方和接收方可以以解耦的方式發送可變大小的資料。

其他進程間通訊技術 (如共享記憶體) 可能不可行，因為它們需要估算所需記憶體段的大小，這使得參與者更加耦合。此外，它無法跨物理伺服器工作。

因此，我們更喜歡套接字，因為它們具有高解耦性、流量控制以及適用於單個伺服器或網路的能力。
```

```
Question 2
在我們的詳細設計中，我們使用 Kafka 來處理我們的答案查看計數器。你認為我們為什麼做出這個決定？

Answer
根據主題標籤，許多使用者可以同時查看問題的回答。這可能會阻塞伺服器。瞬時更新查看計數器也不是一個重要的產品功能。因此，Kafka 適合處理這些任務。

Quora 在兩分鐘或更短的時間內處理這些任務。

儘管如此，我們可以使用分片計數器作為查看計數器問題的有效解決方案。
```

```
Question 3
使用長輪詢代替輪詢的主要優點是什麼？

Answer
長輪詢將控制權轉移到伺服器端而不是客戶端，客戶端沒有關於內容更新的資訊。如果伺服器處於控制之中，它可以一有新鮮內容就回覆。結果，它減少了自身的請求負載。然而，長輪詢是一種資源密集型解決方案，因為它使連接在較長時間內保持持久或活動狀態。

WebSockets 是另一種具有低開銷的低延遲解決方案。然而，WebSockets 對於 Quora 提供的功能來說可能有些大材小用。
```
