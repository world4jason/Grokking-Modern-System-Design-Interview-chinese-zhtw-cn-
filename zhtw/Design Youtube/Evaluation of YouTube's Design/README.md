# Evaluation of YouTube's Design (YouTube 設計的評估)

## Fulfilling requirements (滿足需求)
我們提出的設計需要滿足我們在前面課程中提到的需求。我們的主要需求是流暢的流媒體 (低延遲)、可用性和可靠性。讓我們一一討論。

1. **Low latency/Smooth streaming (低延遲/流暢流媒體)**：可以通過以下策略實現：
  - 在 ISP 級別分佈式快取伺服器，以保留觀看次數最多的內容。
  - 為不同類型的資料選擇合適的存儲系統。例如，我們可以將 Bigtable 用於縮略圖，Blob 儲存用於影片等。
  - 通過分佈式快取管理系統在各個層使用快取。
  - 利用內容分發網路 (CDN)，大量使用快取並主要從記憶體中提供影片。CDN 將其服務部署在靠近最終使用者的位置，以提供低延遲服務。

2. **Scalability (可擴展性)**：如下表所示，我們已採取各種措施來確保設計的可擴展性。隨著使用者的增長，Web 和應用伺服器的水平可擴展性不會成為問題。但是，MySQL 存儲無法擴展到超過某個點。正如下一節我們將看到的，這可能需要進行一些重組。

3. **Availablity (可用性)**：可以通過冗餘使系統可用，即將資料複製到盡可能多的伺服器，以避免單點故障。跨資料中心複製資料將確保高可用性，即使整個資料中心因電源或網路問題而發生故障也是如此。此外，本地負載平衡器可以排除任何死機伺服器，如果需要，全局負載平衡器可以將流量引導至不同區域。

4. **Reliability (可靠性)**：YouTube 的系統可以通過使用資料分區和容錯技術來變得可靠。通過資料分區，一種類型資料的不可用不會影響其他資料。我們可以使用冗餘的硬體和軟體組件來實現容錯。此外，我們可以使用心跳協議來監控伺服器的健康狀況，並忽略有故障和錯誤的伺服器。我們可以使用一致性雜湊的變體來無縫添加或刪除伺服器，並在負載不均勻的情況下減少特定伺服器的負擔。

## Trade-offs (權衡)
YouTube 如何實現可擴展性、可用性和良好效能

### Consistency (一致性)
我們的解決方案傾向於高可用性和低延遲。但是，由於高可用性 (參見 CAP 定理)，強一致性可能會受到影響。儘管如此，對於像 YouTube 這樣的系統，我們可以承受放棄強一致性。這是因為我們不需要向所有使用者顯示一致的提要。例如，訂閱同一頻道的不同使用者可能不會同時看到新上傳的影片。值得一提的是，我們將保持使用者資料的強一致性。這也是我們將使用者資料與影片元資料解耦的另一個原因。

### Distributed cache (分佈式快取)
在我們的 YouTube 設計中，我們更喜歡分佈式快取而不是集中式快取。這是因為運行 YouTube 所需的可擴展性、可用性和容錯因素需要一個不是單點故障的快取。這就是我們使用分佈式快取的原因。由於 YouTube 主要提供靜態內容 (縮略圖和影片)，因此 Memcached 是一個不錯的選擇，因為它是開源的並且使用流行的最近最少使用 (LRU) 演算法。由於 YouTube 影片訪問模式是長尾的，因此類似 LRU 的演算法適用於此類資料集。

### Bigtable versus MySQL (Bigtable 與 MySQL)
我們設計的另一個有趣方面是針對不同資料集使用不同的存儲技術。我們為什麼選擇 MySQL 和 Bigtable？

選擇的主要原因是效能和靈活性。YouTube 中的使用者數量可能不像影片和縮略圖的數量那樣擴展。此外，我們需要以結構化形式存儲使用者和元資料以便於搜尋。因此，MySQL 是這種情況的合適選擇。

但是，上傳的影片數量和每個影片的縮略圖數量將非常大。可擴展性需求將迫使我們為該存儲使用自定義或 NoSQL 類型的設計。人們可以使用 GFS 和 Bigtable 的替代品，例如 HDFS 和 Cassandra。

### Public versus private CDN (公共與私有 CDN)
我們的設計依賴 CDN 來實現內容的低延遲服務。但是，CDN 可以是私有的或公共的。YouTube 可以在兩個選項中任選其一。

這種選擇與其說是設計問題，不如說是成本問題。但是，對於流量很少的地區，YouTube 可以使用公共 CDN，原因如下：

1. 設置私有 CDN 將需要大量的資本支出 (CAPEX)。
2. 對於某些地區相當少的病毒式流量，將沒有足夠的時間來設置新的 CDN。
3. 可能沒有足夠的使用者來維持業務。

```
私有 CDN：僅供內部使用的 CDN 基礎設施。

公共 CDN：在按使用付費的基礎上向公眾提供的 CDN 基礎設施。
但是，如果使用者數量太高，YouTube 可以考慮建立自己的 CDN，因為如果流量很高，公共 CDN 可能會很昂貴。私有 CDN 還可以針對內部使用進行優化，以更好地為客戶服務。

### Duplicate videos (重覆影片)
當前的 YouTube 設計不處理使用者或垃圾郵件發送者上傳的重覆影片。重覆影片會佔用額外的空間，這會導致權衡。結果，我們要麼浪費儲存空間，要麼在處理重覆影片的上傳過程中面臨額外的複雜性。

讓我們執行一些計算來解決這個問題。假設上傳到 YouTube 的 500 小時影片中有 50 個是重覆的。考慮到一分鐘影片需要 6 MB 的儲存空間，重覆內容將佔用以下儲存空間：
```
(50 x 60) minutes x 6 MB/min = 18 GB
如果我們避免影片重覆，我們一年可以節省多達 9.5 PB 的儲存空間。計算如下：
```
18 GB/min x (60 x 24 x 365) total minutes in an year = 9.5 Peta Bytes
浪費的儲存空間和其他計算成本並不是重覆影片的唯一問題。重覆影片的一個重要方面是版權問題。沒有內容創作者希望他們的內容被剽竊。因此，在 YouTube 的設計中增加處理重覆影片的複雜性是合理的。

重覆可以通過簡單的技術 (如局部敏感雜湊) 來解決。但是，可能會有一些複雜的技術，如塊匹配演算法 (BMA) 和相位相關性來查找重覆項。在巨大的影片資料庫中實施此解決方案可能非常複雜。我們可能不得不使用人工智慧 (AI) 等技術。


## Future scaling (未來擴展)
到目前為止，我們專注於 YouTube 擬議設計的設計和分析。實際上，YouTube 的設計非常複雜，需要先進的系統。在本節中，我們將重點介紹資料存儲和 Web 伺服器的實用結構。

我們將從限制擴展 YouTube 的一些方面開始討論。特別是，我們將考慮如果我們服務的流量負載增加幾倍，我們必須進行哪些設計更改。

我們已經知道我們必須擴展現有的基礎設施，其中包括以下元素：

- Web 伺服器
- 應用伺服器
- 資料存儲
- 在上述每一層之間放置負載平衡器
- 實施分佈式快取

上述任何基礎設施都需要對應用級邏輯進行一些修改和適應。例如，如果我們繼續增加 MySQL 伺服器中的資料，它可能會成為瓶頸。為了有效地使用分片資料庫，我們可能必須更改資料庫客戶端以實現良好的效能並保持 ACID (原子性、一致性、隔離性、持久性) 屬性。但是，即使我們在擴展時繼續更改資料庫客戶端，其複雜性也可能達到無法管理的程度。另請注意，我們尚未將災難恢復機制納入我們的設計中。

為了解決上述問題，YouTube 開發了一個名為 Vitess 的解決方案。

[用於可擴展性的 Vitess 系統](./vitess.jpg)

Vitess 的關鍵思想是在所有資料庫層之上放置一個抽象，給資料庫客戶端一種它正在與單個資料庫伺服器對話的錯覺。在這種情況下，單個資料庫是 Vitess 系統。因此，所有資料庫客戶端的複雜性都遷移到 Vitess 並由其處理。這保持了 ACID 屬性，因為使用的內部資料庫是 MySQL。但是，我們可以通過分區啟用擴展。因此，我們將獲得一個 MySQL 結構化資料庫，它提供 NoSQL 存儲系統的效能。同時，我們不必忍受豐富的資料庫客戶端 (應用邏輯)。下圖強調了 Vitess 如何能夠實現可擴展性和結構。

[可擴展性與結構頻譜上的 Vitess](./spectrum.jpg)

人們可以想像使用資料非規範化等技術代替 Vitess 系統。但是，資料非規範化不起作用，因為它是以降低寫入效能為代價的。即使我們的工作是讀取密集型的，隨著系統的擴展，寫入效能也會下降到無法忍受的極限。

## Web server (Web 伺服器)
Web 伺服器是一個非常重要的組件，隨著規模的擴大，自定義 Web 伺服器可能是一個可行的解決方案。這是因為大多數商業或開源解決方案都是通用的，並且是考慮到廣泛的使用者而開發的。因此，對於如此成功的服務，自定義解決方案是可取的。
