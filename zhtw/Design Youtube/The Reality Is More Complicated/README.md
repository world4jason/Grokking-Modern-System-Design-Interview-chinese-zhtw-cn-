# The Reality Is More Complicated (現實更複雜)
## Introduction (介紹)
既然我們已經很好地了解了設計，讓我們看看 YouTube 如何在保持為最終使用者提供良好體驗品質 (QoE) 的同時優化儲存和網路需求的使用。

```
QoE 是衡量客戶對特定服務體驗滿意度的指標。
```

在談到為最終使用者提供有效服務時，以下三個步驟很重要：

- **Encode (編碼)**：上傳到 YouTube 的原始影片具有顯著的儲存需求。可以使用各種編碼方案來減小這些原始影片文件的大小。除了壓縮之外，編碼方案的選擇還取決於用於流式傳輸影片內容的終端設備類型。由於可以使用多個設備來流式傳輸同一個影片，我們可能必須使用不同的編碼方案對同一個影片進行編碼，導致一個原始影片文件被轉換為多個編碼不同的文件。這種策略將帶來良好的使用者感知體驗，原因有二：使用者將節省頻寬，因為影片文件將被編碼並壓縮到一定限度，並且編碼後的影片文件將適合客戶端以獲得流暢的播放體驗。
- **Deploy (部署)**：為了低延遲，內容必須智能部署，使其靠近大量最終使用者。這不僅會減少延遲，還會減輕網路以及 YouTube 核心伺服器的負擔。
- **Deliver (傳遞)**：向客戶端傳遞需要有關用於播放影片的客戶端或設備的知識。這些知識將有助於適應客戶端和網路狀況。因此，我們將使自己能夠有效地提供內容。

現在讓我們詳細了解每個階段。

## Encode (編碼)
到目前為止，我們已經考慮了使用不同的編碼方案對一個影片進行編碼。但是，如果我們在逐個鏡頭的基礎上對影片進行編碼，我們會將影片分成更小的時間幀並分別對它們進行編碼。我們可以將影片分成更短的時間幀，並將它們稱為片段。每個片段將使用多種編碼方案進行編碼，以生成稱為塊的不同文件。片段的編碼方案選擇將基於片段內的細節，以透過較少的儲存需求獲得優化的質量。最終，每個鏡頭將根據片段的內容和使用的編碼方案被編碼成多個塊大小。當我們將原始影片分成片段時，我們將在部署和每個階段看到它的優勢。

讓我們了解逐個片段編碼是如何工作的。對於任何具有動態顏色和高深度的影片，我們將使用與顏色較少的影片不同的編碼方式。這意味著一個不那麼動態的片段將被編碼，以便它被壓縮得更多以節省額外的儲存空間。最終，我們必須在部署和流式傳輸階段傳輸更小的文件大小並節省頻寬。

[從左到右需要更高比特率的更高質量](./bitrate.jpg)

使用上述策略，我們必須以各種格式對影片的各個鏡頭進行編碼。然而，這種方法的替代方案是在以各種格式編碼後存儲整個影片 (不使用分段)。如果我們在逐個鏡頭的基礎上進行編碼，我們將能夠通過在粒度級別上進行編碼來最佳地減小整個影片的大小。我們還可以以各種格式編碼音頻，以最佳地允許為各種客戶端 (如電視、手機和台式機) 進行流式傳輸。具體來說，對於像 Netflix 這樣的服務，音頻編碼更有用，因為音頻以各種語言提供。

## Deploy (部署)
正如我們在設計和評估部分所討論的那樣，我們必須將內容帶給使用者。這有三個主要優點：

1. 使用者將能夠快速流式傳輸影片。
2. 源伺服器上的負擔將減少。
3. 網際網路服務提供商 (ISP) 將有多餘的頻寬。
因此，我們可以將熱門影片的塊部署在 CDN 和 ISP 的存在點 (PoP) 中，而不是直接從我們的資料中心流式傳輸。在無法與 ISP 合作的地方，我們的內容可以放置在網際網路交換點 (IXP) 中。我們可以將內容放在 IXP 中，這不僅離使用者更近，而且還有助於填充 ISP PoP 的快取。

```
PoP 是兩個或多個大型網路結合以實現其客戶端之間通訊的點。
```

[通過 IXP 和 ISP 從資料中心流式傳輸到使用者](./streaming.jpg)

我們應該記住，由於存儲容量有限，ISP 或 IXP 處的快取僅針對流行內容或中等流行內容執行。由於我們的逐個鏡頭編碼方案節省了儲存空間，我們將能夠使用靠近最終使用者的快取基礎設施提供更多內容。

此外，我們可以在源伺服器上有兩種類型的存儲：

1. **Flash servers (快閃記憶體伺服器)**：這些伺服器保存流行和中等流行的內容。它們針對低延遲傳遞進行了優化。
2. **Storage servers (儲存伺服器)**：這種類型保存很大一部分不流行的影片。這些伺服器針對保存大存儲進行了優化。

```
源伺服器：負責監聽和回應客戶端請求的伺服器
```

```
注意：當我們傳輸流媒體內容時，可能會導致網路擁塞。這就是為什麼我們必須在非高峰時段將內容傳輸給 ISP。
```

### Recommendations (推薦)
YouTube 根據使用者的個人資料向其推薦影片，同時考慮了諸如他們的興趣、觀看和搜尋歷史、訂閱頻道、與已觀看內容相關的主題以及對內容的活動 (如評論和點讚) 等因素。

下面提供了 YouTube 推薦引擎的近似值。YouTube 分兩個階段過濾影片：

1. **Candidate generation (候選生成)**：在此階段，數百萬個 YouTube 影片根據使用者的歷史記錄和當前上下文被過濾為數百個。
2. **Ranking (排名)**：排名階段根據影片的功能以及使用者的興趣和歷史記錄對影片進行評級。在此階段，數百個影片被過濾並排名為幾十個影片。
YouTube 在這兩個階段都採用機器學習技術向使用者提供推薦。

```
Covington, Paul, Jay Adams, and Emre Sargin. “Deep neural networks for youtube recommendations.” Proceedings of the 10th ACM conference on recommender systems. 2016.
```

### Adaptive streaming (自适应流媒體)
在提供內容的同時，使用者的頻寬也一直在受到監控。由於影片被分成不同質量的塊，每個塊的時間幀相同，因此根據不斷變化的網路條件向客戶端提供塊。

如下所示，當頻寬較高時，較高品質的塊被發送到客戶端，反之亦然。

[根据频宽提供给客户的每个时间帧中的块大小变化](./adaptive_streaming.jpg)

自適應比特率演算法取決於以下四個參數：

1. 端到端可用頻寬 (從 CDN/伺服器到特定客戶端)。
2. 使用者的設備功能。
3. 使用的編碼技術。
4. 客戶端的緩衝空間 [來源：The Networking Channel: Netflix adaptive streaming and more by Renata and TY]。

## Potential follow-up questions (潛在的後續問題)

由於主題領域更加深入，YouTube 系統設計可能有很多不同的方面。因此，可能會出現許多問題。一些問題及其答案的方向如下：

**問題**：可以通過添加 99.99% 可用性或 99.999% 可用性等數字來量化可用性。在這種情況下，需要進行哪些設計更改？

   這是一個難題。實際上，這些數字是服務 SLA 的一部分，它們是從模型或長期實證研究中生成的。雖然了解上述數字是如何獲得的以及組織如何使用監控來保持高可用性是有好處的，但討論系統的容錯能力可能是一個更好的策略——如果出現軟體故障、伺服器故障、整個資料中心故障等會發生什麼。如果系統對故障具有彈性，這意味著系統將具有良好的可用性。

**問題**：我們假設了一些合理的數字來提出廣泛的資源需求。例如，我們說影片的平均長度是五分鐘。在這種情況下，我們是針對平均行為進行設計嗎？不遵循平均配置文件的使用者會發生什麼？

   一個可能的答案是，上述數字可能會隨著時間而改變。我們的系統設計應該是水平可擴展的，以便隨著使用者的增加，系統保持足夠的功能。實際上，當系統的某些方面增加一個數量級時，系統可能無法擴展。當系統的某些方面增加一個數量級 (例如 10 倍) 時，我們通常需要一個新的、不同的設計。設計 10 倍和 100 倍規模的成本點非常不同。

**問題**：為什麼我們不討論和估算影片評論和點讚的資源？

   並發使用者對影片的評論大致與設計訊息系統的複雜性相同。我們將在系統設計：WhatsApp 中討論該問題。

**問題**：如何管理系統負載的意外峰值？

   一個可能的答案是，因為我們的設計是水平可擴展的，我們可以由於其彈性特性將一些負載轉移到公共雲上。但是，公共雲不是無限可擴展的。它們通常需要先驗的商業合同，這可能會限制不同資料中心最大並發允許的資源使用。

**問題**：我們將如何部署全球網路來連接資料中心和 CDN 站點？

   在實踐中，YouTube 使用 Google 的網路，該網路為此目的而建，並與世界上許多 ISP 對等。這是一個迷人的研究領域，我們將其留給本課程以外進行進一步審查。

**問題**：為什麼沒有關於音頻/影片編碼的更多詳細資訊？

   有許多音頻/影片編碼選擇，許多是公開的，有些是專有的。由於多媒體內容中的過度冗餘，編碼通常能夠將巨大的原始格式內容減少到更小的大小 (例如，從 600 MB 到 30 MB)。如果您有興趣進一步探索，我們已將此類編碼演算法的詳細資訊留給您。

**問題**：我們不能使用專用硬體 (或像 GPU 這樣的加速器) 來加速 YouTube計算的某些方面嗎？

   當我們估算伺服器數量時，我們假設任何伺服器都可以滿足任何所需的功能。實際上，隨著摩爾定律的放緩，我們可以使用專用硬體 (例如，硬體編碼器/解碼器、像張量處理單元這樣的機器學習加速器等等)。所有這些平台都需要自己的課程來公正地對待內容。因此，我們在此設計問題中避免了討論。

```
摩爾定律由戈登·摩爾於 1965 年提出，他指出集成電路 (IC) 中的電晶體數量每年翻一番。
```


**問題**：在內容上傳階段應該在客戶端還是伺服器端執行壓縮？

   我們可能會在客戶端使用一些無損但快速的壓縮 (例如 Google Snappy) 來減少需要上傳的資料。這可能意味著我們需要一個富客戶端，或者如果壓縮器不可用，我們將不得不退回到純資料。這兩個選項都增加了系統的複雜性。

**問題**：除了自適應比特率之外，製作文件塊還有其他好處嗎？

   我們僅在自適應比特率的背景下討論了影片文件塊。這些塊還有助於並行化任何預處理，這對於滿足實時需求非常重要，尤其是對於直播流。並行處理本身又是一個成熟的話題，我們留給您進一步探索。
