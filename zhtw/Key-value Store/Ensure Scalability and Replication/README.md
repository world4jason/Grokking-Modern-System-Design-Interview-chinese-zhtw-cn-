# Ensure Scalability and Replication (確保可擴展性和複製)
## Add scalability (添加可擴展性)
讓我們從核心設計要求之一開始：可擴展性。我們將鍵值資料存儲在存儲節點中。隨著需求的變化，我們可能需要添加或刪除存儲節點。這意味著我們需要在系統中的節點上對資料進行分區，以將負載分佈在所有節點上。

例如，假設我們有四個節點，並且我們希望 25% 的請求進入每個節點以平均平衡負載。解決此問題的傳統方法是通過模運算符。當請求進來時，我們分配一個請求 ID，計算其哈希值，並通過與可用節點數取模來找到餘數。餘數值是節點編號，我們將請求發送到該節點進行處理。

以下幻燈片解釋了此過程：

[我們獲取 requestID 的哈希值並與節點數取模以找到應處理請求的節點](./add_scalability1.jpg)

[我們對 RequestID 執行所需的操作以獲取節點](./add_scalability2.jpg)

[節點 2 將處理請求](./add_scalability3.jpg)

我們希望以最小的基礎設施變更來添加和刪除節點。但是在這種方法中，當我們添加或刪除節點時，我們需要移動大量的鍵。這是低效的。例如，節點 2 被刪除，假設對於相同的請求 ID，處理請求的新伺服器將是節點 1，因為 10 % 3 = 1。節點在其本地緩存中保存資訊，例如鍵及其值。因此，我們需要將該請求的資料移動到必須處理該請求的下一個節點。但是這種複製可能代價高昂並且會導致高延遲。

接下來，我們將學習如何高效地複製資料。

```
Question
為什麼我們不使用負載平衡器將請求分發到所有節點？

Answer
負載平衡器根據算法分發客戶端請求。該算法可以像上面解釋的那樣簡單，也可以像下一節中描述的那樣詳細。我們將討論的下一種方法可以是負載平衡器在節點之間平衡請求的方式之一。
```

### Consistent Hashing (一致性哈希)
一致性哈希是管理節點集上的負載的有效方法。在一致性哈希中，我們認為我們有一個從 0 到 n-1 的概念哈希環，其中 n 是可用哈希值的數量。我們使用每個節點的 ID，計算其哈希值，並將其映射到環上。我們對請求應用相同的過程。每個請求都由它在環中順時針移動時找到的下一個節點完成。

每當向環中添加新節點時，直接的下一個節點都會受到影響。它必須與新添加的節點共享其資料，而其他節點不受影響。這很容易擴展，因為我們能夠將對節點的更改保持在最低限度。這是因為只需要移動一小部分總鍵。哈希是隨機分佈的，因此我們預計請求的負載是隨機的，並且平均均勻分佈在環上。

[一致性哈希](./consistent_hashing)

一致性哈希的主要好處是，隨著節點的加入或離開，它可以確保需要移動的鍵數量最少。但是，請求負載在實踐中並非均分。任何處理大量資料的伺服器都可能成為分佈式系統的瓶頸。該節點將收到不成比例的大量資料存儲和檢索請求，從而降低整體系統性能。因此，這些被稱為熱點。

如下圖所示，大多數請求都在 N4 和 N1 節點之間。現在，與其他節點相比，N1 必須處理大多數請求，並且它已成為熱點。這意味著非均勻負載分佈增加了單個伺服器上的負載。

```

#### Use virtual nodes (使用虛擬節點)
我們將使用虛擬節點來確保節點之間的負載分佈更均勻。我們將在同一個鍵上應用多個哈希函數，而不是應用單個哈希函數。

讓我們舉個例子。假設我們有三個哈希函數。對於每個節點，我們計算三個哈希值並將它們放入環中。對於請求，我們只使用一個哈希函數。無論請求落在環上的哪個位置，它都由順時針移動時找到的下一個節點處理。每個伺服器有三個位置，因此請求的負載更均勻。此外，如果一個節點比其他節點具有更多的硬件容量，我們可以通過使用額外的哈希函數來添加更多虛擬節點。這樣，它將在環中擁有更多位置並服務更多請求。

[虛擬節點](./virtual_nodes)

##### Advantages of virtual nodes (虛擬節點的優點)
以下是使用虛擬節點的一些優點：

```
如果節點發生故障或進行例行維護，工作負載將均勻分佈在其他節點上。對於每個新訪問的節點，當它重新上線或添加到系統時，其他節點收到的負載幾乎相等。

每個節點都要考慮物理基礎設施的異構性，決定它負責多少個虛擬節點。例如，如果一個節點的計算能力大約是其他節點的兩倍，它可以承擔更多的負載。
```

我們已經使鍵值存儲的擬議設計具有可擴展性。下一個任務是使我們的系統高度可用。

## Data replication (資料複製)
我們有多種方法來複製存儲。它可以是主從關係或點對點關係。

### Primary-secondary approach (主從方法)
在主從方法中，存儲區域之一是主存儲區域，其他存儲區域是輔助存儲區域。輔助存儲區域從主存儲區域複製其資料。主存儲區域服務寫請求，而輔助存儲區域服務讀請求。寫入後，複製會有延遲。此外，如果主存儲區域宕機，我們將無法寫入存儲，它將成為單點故障。

```
Question
主從方法是否滿足我們在系統設計：鍵值存儲課程中定義的鍵值存儲要求？

Answer
我們的要求之一是我們需要始終寫入的能力。這種方法適用於始終讀取選項。但是，這種方法不包括始終寫入的能力，因為它會使主存儲過載。此外，如果主伺服器發生故障，我們需要將輔助伺服器升級為主伺服器。寫入的可用性將受到影響，因為我們不允許在切換期間進行寫入。
```

### Peer-to-peer approach (點對點方法)
在點對點方法中，所有涉及的存儲區域都是主存儲區域，並且它們複製資料以保持更新。所有節點都允許讀寫。通常，在所有 n 個節點中複製是低效且昂貴的。相反，3 或 5 是要複製的存儲節點數量的常見選擇。

[點對點關係](./p2p.jpg)

我們將使用點對點關係進行複製。我們將在多個主機上複製資料以實現持久性和高可用性。每個資料項將在 n 個主機上複製，其中 n 是為每個鍵值存儲實例配置的參數。例如，如果我們選擇 n 為 5，這意味著我們希望我們的資料被複製到五個節點。

每個節點將其資料複製到其他節點。我們將處理讀或寫操作的節點稱為協調器。它直接負責鍵。協調器節點分配有鍵“K”。它還負責將鍵複製到環上的 n-1 個後繼者 (順時針)。這些後繼虛擬節點列表稱為首選列表。為了避免將副本放在同一個物理節點上，首選列表可以跳過其物理節點已在列表中的那些虛擬節點。

讓我們考慮下圖。我們將複製因子 n 設置為 3。對於鍵“K”，複製在接下來的三個節點上完成：B、C 和 D。同樣，對於鍵“L”，複製在節點 C、D 和 E 上完成。
