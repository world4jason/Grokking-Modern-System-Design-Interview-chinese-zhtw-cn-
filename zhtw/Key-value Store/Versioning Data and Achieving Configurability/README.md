# Versioning Data and Achieving Configurability (資料版本控制和實現可配置性)
## Data versioning (資料版本控制)
當更新期間發生網絡分區和節點故障時，對象的版本歷史記錄可能會變得支離破碎。因此，這需要系統方面進行協調工作。有必要構建一種明確接受同一資料的多個副本的可能性以避免丟失任何更新的方法。認識到某些故障場景可能導致系統中存在同一資料的多個副本至關重要。因此，這些副本可能是相同的，也可能是不同的。解決這些不同歷史之間的衝突對於一致性目的至關重要。

```
版本歷史包含已修改對象的詳細資訊。
[資料版本控制](./version)

為了處理不一致，我們需要維護事件之間的因果關係。我們可以使用時間戳來做到這一點，並使用最新請求的值更新所有衝突值。但是時間在分佈式系統中並不包含，因此我們不能將其用作決定因素。

有效維護因果關係的另一種方法是使用向量時鐘。向量時鐘是 (節點，計數器) 對的列表。對象的每個版本都有一個向量時鐘。如果兩個對象具有不同的向量時鐘，我們能夠判斷它們是否存在因果關係 (稍後會詳細介紹)。除非兩個更改之一得到協調，否則這兩個更改被視為不一致。

### Modify the API design (修改 API 設計)
我們討論了如何使用向量時鐘值來決定兩個事件是否存在因果關係。為此，我們需要有關哪個節點之前執行了操作及其向量時鐘值是多少的資訊。這是操作的上下文。因此，我們將按如下方式修改我們的 API 設計。

獲取值的 API 調用應如下所示：
```
get(key)
```

Parameter (參數)    Description (描述)
                    這是我們想要獲取值的鍵。

我們返回一個對象或衝突對象的集合以及一個上下文。上下文保存有關對象的編碼元資料，包括對象版本等詳細資訊。

將值放入系統的 API 調用應如下所示：
```
put(key, context, value)
```

Parameter (參數)      Description (描述)
                      這是我們必須存儲值的鍵。

                      這保存每個對象的元資料。

                      這是需要針對鍵存儲的對象。

函數根據鍵找到應該放置值的節點，並存儲與之關聯的值。上下文在 get 操作後由系統返回。如果我們在上下文中有一組引發衝突的對象，我們將要求客戶端解決它。

```
這裡的客戶端是我們受信任資料中心中的任何前端伺服器。這並不意味著最終使用者。
```

要更新鍵值存儲中的對象，客戶端必須提供上下文。我們通過提供先前讀取操作的上下文，使用向量時鐘確定版本資訊。如果鍵值存儲可以訪問多個分支，它會在處理讀取請求時提供葉節點處的所有對象以及上下文中各自的版本資訊。協調不同版本並將它們合併為單個新版本被視為更新。

```
注意：解決衝突的過程與 Git 中的過程相當。如果 Git 能夠將多個版本合併為一個版本，則合併將自動執行。如果無法自動解決衝突，則由客戶端 (開發人員) 手動解決衝突。同樣，我們的系統可以嘗試自動解決衝突，如果不可能，則要求應用程式提供最終解決的值。
```

### Vector clock usage example (向量時鐘使用示例)
讓我們考慮一個例子。假設我們有一個寫操作請求。節點 A 處理寫請求的第一個版本 E1。相應的向量時鐘具有節點資訊及其計數器——即 [A,1]。節點 A 處理對執行先前寫入的同一對象的另一個寫入。所以，對於 E2，我們有 [A,2]。不再需要 E1，因為 E2 在同一節點上更新。E2 讀取 E1 所做的更改，然後進行新的更改。假設發生網絡分區。現在，請求由兩個不同的節點 B 和 C 處理。具有更新版本的上下文 (即 E3) 及其相關時鐘 (即 ([A,2], [B,1]) 和 ([A,2], [C,1])) 現在已在系統中。

假設網絡分區已修復，客戶端再次請求寫入，但現在我們有衝突。衝突的上下文 ([A,3], [B,1], [C,1]) 返回給客戶端。在客戶端進行協調並且 A 協調寫入後，我們有帶有時鐘 ([A,4]) 的 E5。

### Compromise with vector clocks limitations (妥協向量時鐘的局限性)
如果多個伺服器同時寫入同一個對象，向量時鐘的大小可能會增加。這在實踐中不太可能發生，因為寫入通常由首選列表中的前 n 個節點之一處理。

例如，如果存在網絡分區或多個伺服器故障，則寫請求可能由不在首選列表中前 n 個節點的節點處理。結果我們可能會有這樣一個很長的版本：([A,10], [B,4], [C,1], [D,2], [E,1], [F,3], [G,5], [H,7], [I,2], [J,2], [K,1], [L,1])。存儲和維護如此長的版本歷史記錄很麻煩。

在這種情況下，我們可以限制向量時鐘的大小。我們採用時鐘截斷策略來存儲每個 (節點，計數器) 對的時間戳，以顯示節點上次更新資料項的時間。當 (節點，計數器) 對的數量超過預定閾值 (比如 10) 時，將清除向量時鐘對。由於無法精確計算後代鏈接，這種截斷方法會導致協調效率低下。

## The get and put operations (get 和 put 操作)
我們的功能需求之一是系統應該是可配置的。我們希望控制可用性、一致性、成本效益和性能之間的權衡。因此，讓我們通過實現鍵值存儲的基本 get 和 put 函數來實現可配置性。

每個節點都可以處理我們系統中的 get (讀) 和 put (寫) 操作。處理讀或寫操作的節點稱為協調器。協調器是首選列表中前 n 個節點中的第一個。

客戶端選擇節點的方式有兩種：
- 我們將請求路由到通用負載平衡器。
- 我們使用分區感知客戶端庫，將請求直接路由到適當的協調器節點。

這兩種方法都有其優點。客戶端在第一種方法中不與代碼鏈接，而在第二種方法中可以實現更低的延遲。由於躍點數減少，延遲較低，因為客戶端可以直接訪問特定伺服器。

讓我們通過能夠控制可用性、一致性、成本效益和性能之間的權衡的能力來使我們的服務可配置。我們可以使用類似於仲裁系統中使用的既定協議。

讓我們舉個例子。假設首選列表中前 n 個中的 n 等於 3。這意味著需要維護資料的三個副本。我們假設節點放置在一個環中。假設 A、B、C、D 和 E 是環中節點的順時針順序。如果在節點 A 上執行寫入功能，則該資料的副本將放置在 B 和 C 上。這是因為 B 和 C 是我們在環的順時針方向移動時找到的下一個節點。

```
仲裁是分佈式事務必須獲得的最小票數，以便允許在分佈式系統中執行操作。實施基於仲裁的技術以強制分佈式系統中的一致操作。(維基百科)
```

## Usage of r and w (r 和 w 的使用)
現在，考慮兩個變量，r 和 w。r 表示成功讀操作所需的最小節點數，而 w 是成功寫操作涉及的最小節點數。所以如果 r=2，這意味著當我們在三個節點中存儲資料時，我們的系統將從兩個節點讀取。我們需要選擇 r 和 w 的值，以便它們之間至少有一個公共節點。這確保了讀者可以獲得最新寫入的值。為此，我們將通過設置 r + w > n 來使用類似仲裁的系統。
```

在此模型中，get 操作的延遲由 r 個副本中最慢的一個決定。原因是對於較大的 r 值，我們更關注可用性並妥協一致性。

協調器為新版本生成向量時鐘，並在收到鍵的 put() 請求時在本地寫入新版本。協調器發送帶有更新版本和新向量時鐘的 n 個排名最高的節點。如果至少 w-1 個節點響應，我們認為寫入成功。請記住，協調器首先寫入自身，因此我們總共得到 w 次寫入。

對 get() 操作的請求是對鍵的首選列表中排名最高的 n 個可達節點發出的。它們在將結果返回給客戶端之前等待 r 個答案。如果協調器從同一來源獲得多個資料集 (需要協調的不同歷史記錄)，則它們將返回它們認為不相關的所有資料集版本。然後合併衝突版本，並重寫生成的鍵值以覆蓋以前的版本。
