# The RESHADED Approach for System Design (系統設計的 RESHADED 方法)

## Introduction (簡介)
系統設計問題並不直截了當。我們沒有可以用於所有設計問題的通用公式。然而，我們可以使用高層次的共同策略來為任何設計問題的良好解決方案定下基調。我們稱之為 RESHADED 方法。一般來說，我們所有設計問題的解決都牢記這一策略。RESHADED 是我們將用於解決不同設計問題的指導方針。雖然沒有所謂的萬用解決方案，但正如我們將看到的，使用這種方法會有其優勢。

## Advantages of RESHADED (RESHADED 的優點)
在我們瀏覽 RESHADED 每個字母所代表的單詞之前，讓我們先介紹一下我們整體方法的好處。這種方法的一些主要優點如下：

1. RESHADED 方法幫助我們記住解決每個設計問題的一些關鍵步驟。這意味著，在任何時間點，我們面前總會有下一步驟。
2. 我們想出的解決方案將包含解決任何設計問題所需的所有基本要素。不僅如此，通過 RESHADED 方法提供的解決方案將是系統化和深思熟慮的。

## Exploring RESHADED (探索 RESHADED)
在下文中，我們描述了我們在 RESHADED 每個字母下採取的步驟：

**Requirements (需求)**：在這一步驟中，我們收集設計問題的所有需求並定義其範圍。需求包括了解服務是什麼，它是如何運作的，以及它的主要功能是什麼。這一步驟的目標是收集我們即將設計的服務的功能和非功能需求。

**Estimation (估算)**：顧名思義，這一步驟估算向定義數量的使用者提供服務所需的資源。通過資源，我們指的是硬體或基礎設施資源。一些範例估算問題如下：

1. 我們需要多少台伺服器才能為 5 億每日活躍使用者 (DAU) 提供流暢的服務？
2. 如果我們每天必須儲存 1.25 億條推文，並且 20% 的推文包含媒體，我們需要多少儲存空間？

估算很重要，因為它們幫助我們了解我們將設計的系統規模。我們將根據估算做出關鍵決策。例如，我們將決定使用哪種類型的資料庫來儲存我們的資料，哪種資料結構將提供最佳性能，等等。

**Storage schema (optional) (儲存模式 (選填))**：這一步驟涉及闡明我們的資料模型——即我們定義我們需要哪些表以及每張表包含哪種類型的欄位。然而，這是一個選填步驟，我們可能不會在每個設計問題中都進行這項工作。

**High-level design (高階設計)**：這一步驟涉及識別我們將用於設計所需系統的主要組件和構建塊。我們要通過從我們的功能和非功能需求中獲得靈感來做到這一點。

這被視為邁向我們系統完整設計的第一步，因此需要進一步的迭代和改進。主要地，本節將專注於滿足功能需求。

**API design (API 設計)**：此階段的目標是為我們的服務構建介面。使用者可以使用這些介面呼叫我們系統內的各種服務。這些介面以 API 呼叫的形式存在，通常是我們功能需求的轉換。

**Detailed design (詳細設計)**：詳細設計始於認識到高階設計的局限性。我們將利用這些局限性來發展我們的設計。在這一步驟中，我們將通過提及我們將使用的所有組件和構建塊來完成我們的設計。

我們還定義了我們設計的工作流程及其對不同技術的使用。詳細設計旨在滿足問題的功能和非功能需求。

**Evaluation (評估)**：這一步驟將衡量我們解決方案的有效性。換句話說，我們證明我們的設計如何滿足功能和非功能需求。

我們討論我們在解決方案中做出的不同權衡，並找出改進的空間。

**Distinctive component/feature (獨特組件/功能)**：在本課開始時，我們討論了如何不存在萬用的解決方案。這一步驟是為每個設計問題識別一個獨特方面並進行討論。例如，Uber 設計問題具有支付服務和欺詐檢測作為其獨特功能。相比之下，Google Docs 具有並發控制，這是當不同使用者想要同時編輯文件同一部分時所需要的。
