在我們回答上面列出的問題之前，讓我們先看看我們如何為使用者建立抽象層，以隱藏 Blob 儲存的內部複雜性。這些抽象層也幫助我們做出與設計相關的決策。

有三個抽象層：
1. **User account (使用者帳戶)**：使用者在此層通過其 `account_ID` 唯一識別。使用者上傳的 Blob 維護在其容器中。
2. **Container (容器)**：每個使用者都有一組容器，這些容器都由 `container_ID` 唯一識別。這些容器包含 Blob。
3. **Blob**：此層包含有關 Blob 的資訊，這些 Blob 由其 `blob_ID` 唯一識別。此層維護有關 Blob 元數據的資訊，這對於實現系統的可用性和可靠性至關重要。

注意：我們使用唯一 ID 生成器為使用者帳戶、容器和 Blob 生成唯一 ID。
除了儲存實際的 Blob 資料外，我們還必須維護一些元數據來管理 Blob 儲存。讓我們看看那是什麼資料。

## Blob metadata (Blob 元數據)
當使用者上傳 Blob 時，它被分成小尺寸的區塊 (chunks)，以便能夠支援無法容納在一個連續位置、一個資料節點或與該資料節點關聯的一個磁碟區塊中的大型檔案的儲存。單個 Blob 的區塊隨後儲存在具有足夠儲存空間的可用資料節點上。儲存中有數十億個 Blob。主節點必須儲存有關 Blob 區塊及其儲存位置的所有資訊，以便它可以在讀取時檢索區塊。主節點為每個區塊分配一個 ID。

有關 Blob 的資訊包括區塊 ID 和每個區塊分配的資料節點名稱。我們將 Blob 分成大小相等的區塊。複製區塊是為了使它們能夠應對資料節點故障。因此，我們也儲存每個區塊的副本 ID。我們可以存取與每個 Blob 相關的所有這些資訊。

假設我們有一個 128 MB 的 Blob，我們將其分成兩個 64 MB 的區塊。此 Blob 的元數據如下表所示：

Chunk (區塊)：區塊是寫入和讀取的最小數據單位。

區塊 (Chunk)           資料節點 ID (Datanode ID)          副本 1 ID (Replica 1 ID)         副本 2 ID (Replica 2 ID)            副本 3 ID (Replica 3 ID)

1                       d1b1                               r1b1                              r2b1                                r3b1

2                       d1b2                               r1b2                              r2b2                                r3b2
注意：為了避免複雜性，Blob 儲存中所有 Blob 的區塊大小是固定的。區塊大小取決於 Blob 儲存的性能要求。我們希望區塊大小較大，以便在主節點維護較小的元數據，因為較大的區塊大小會導致較高的磁碟延遲，從而導致較慢的性能。有趣的是，磁碟在讀取和寫入一定範圍的資料時可以具有幾乎相同的延遲。例如，磁碟在寫入 4–8 MB 範圍內的資料時可以具有類似的延遲。此外，它們在寫入 9–20 MB 範圍內的資料時也可以具有類似的延遲。這是由於在磁碟上使用了連續磁區，以及由其作業系統在磁碟和伺服器上進行快取。

區塊是寫入和讀取的最小數據單位。
我們為每個區塊維護三個副本。在寫入 Blob 時，主節點使用其可用空間管理系統識別資料和副本節點。除了處理資料節點故障外，副本節點還用於服務讀取/寫入請求，以便主節點不會過載。

在上面的例子中，Blob 大小是區塊大小的倍數，因此主節點可以確定每個區塊要讀取的位元組數。

**問 (Question)**
如果 Blob 大小不是我們配置的區塊大小的倍數怎麼辦？主節點如何知道最後一個區塊要讀取多少位元組？

**答 (Answer)**
如果 Blob 大小不是區塊大小的倍數，則最後一個區塊將不會滿。

主節點還保留每個 Blob 的大小，以確定最後一個區塊要讀取的位元組數。

## Partition data (分區資料)
我們討論了 Blob 儲存中的不同抽象層級——帳戶層、容器層和 Blob 層。有數十億個 Blob 被儲存和讀取。我們將這些 Blob 儲存在大量的資料節點上。如果我們從所有資料節點中查找包含特定 Blob 的資料節點，那將是一個非常緩慢的過程。相反，我們可以將資料節點分組，並將每個組稱為一個分區 (partition)。我們維護一個分區映射表，其中包含每個分區中所有 Blob 的列表。如果我們獨立於容器 ID 和帳戶 ID 將 Blob 分佈在不同的分區上，我們會遇到一個問題，如下圖所示：

[數十億個 Blobs](./blobpath.jpg)

[基於 Blob ID 的範圍分區](./range_partition.jpg)

基於 Blob ID 的分區會導致某些問題。例如，特定容器或帳戶下的 Blob 可能駐留在增加讀取或列出連結到特定帳戶或特定容器的 Blob 時的開銷的不同分區中。

為了克服上述問題，我們可以根據 Blob 的完整路徑對 Blob 進行分區。這裡的分區鍵是帳戶 ID、容器 ID 和 Blob ID 的組合。這有助於將單個使用者的 Blob 共同定位在同一個分區伺服器上，從而提高性能。
注意：分區映射由主節點維護，這些映射儲存在分散式元數據儲存中。
```

## Blob indexing (Blob 索引)
隨著上傳到儲存的 Blob 數量增加，在 Blob 的海洋中尋找特定的 Blob 變得更加困難和耗時。Blob 索引解決了 Blob 管理和查詢的問題。

為了填充 Blob 索引，我們在上傳 Blob 時在 Blob 上定義鍵值標籤屬性。我們使用多個標籤，如容器名稱、Blob 名稱、上傳日期和時間，以及一些其他類別，如圖像或影片 Blob 等。

如下圖所示，Blob 索引引擎讀取新標籤，將其索引，並將其暴露給可搜尋的 Blob 索引：

[索引和搜尋 Blobs](./indexing.jpg)

我們可以使用索引對 Blob 進行分類以及排序。讓我們看看我們如何在分頁中利用索引。

## Pagination for listing (列出分頁)
列表是關於根據使用者輸入的前綴向使用者返回 Blob 列表。前綴是一個字元或字串，返回名稱以該特定字元或字串開頭的 Blob。

[分頁](./list_blobs.jpg)

使用者可能想要列出與特定帳戶關聯的所有 Blob，列出特定容器內存在的所有 Blob，或者他們可能想要根據前綴列出一些公共 Blob。問題是這個列表可能很長。我們無法一次將整個列表返回給使用者。因此，我們必須分部分返回 Blob 列表。

假設使用者想要與其帳戶關聯的 Blob 列表，並且該帳戶總共有 2,000 個 Blob。一次搜尋、返回和載入太多 Blob 會影響性能。這就是分頁變得重要的地方。我們可以返回前五個結果並給使用者一個“下一頁”按鈕。每次點擊“下一頁”按鈕，它都會返回接下來的五個結果。這稱為分頁 (pagination)。

應用程式擁有者根據以下因素設置要返回的結果數量：

- 他們假設使用者應該等待查詢回應的時間。
- 他們可以在該時間內返回多少結果。我們每頁顯示五個結果，這是一個非常小的數字。我們僅出於視覺化目的使用此數字。

問 (Question)
我們如何決定在總共 2,000 個 Blob 中先返回哪五個 Blob？

答 (Answer)
在這裡，我們利用索引對 Blob 進行排序和分類。我們應該在儲存 Blob 時預先執行此操作。否則，在向使用者返回列表時會變得具有挑戰性。可能會有數百萬或數十億個 Blob，我們無法在收到列表請求時快速對它們進行排序。
```

對於分頁，我們需要一個接續權杖 (continuation token) 作為接下來返回的列表部分的起點。接續權杖是一個字串權杖，如果查詢結果的總數超過了我們可以一次返回的最大結果數，則該權杖包含在查詢的回應中。結果，它作為一個指標，允許重新查詢從我們上次中斷的地方繼續。

## Replication (複製)
複製在兩個層面上進行，以支援可用性和強一致性。為了保持資料的強一致性，我們在執行寫入操作後立即在用於服務讀取請求的節點之間同步複製資料。為了實現可用性，我們可以在執行寫入操作後將資料複製到不同的區域或資料中心。在我們尚未在那裡複製資料之前，我們不會從其他資料中心或區域服務讀取請求。

這是兩個複製層級：
- 儲存叢集內的同步複製。
- 跨資料中心和區域的非同步複製。


### Synchronous replication within a storage cluster (儲存叢集內的同步複製)
儲存叢集由 N 個儲存節點機架組成，每個機架都配置為具有冗餘網路和電源的故障域 (fault domain)。

我們確保寫入儲存叢集的每個資料在該儲存叢集中保持持久。主節點在不同故障域的節點之間維護足夠的資料副本，以確保在磁碟、節點或機架故障的情況下叢集內的資料持久性。

注意：這種叢集內複製是在客戶端寫入請求的關鍵路徑上完成的。
一旦寫入在該儲存叢集內同步複製，就可以向客戶端返回成功。這允許快速寫入，因為：
- 我們在所有節點都在附近的儲存叢集內複製資料，從而減少了延遲。
- 我們使用內聯 (in-lined) 資料複製，我們使用冗餘網路路徑並行複製資料到所有副本。

這種複製技術有助於維持儲存叢集內的資料一致性和可用性。

### Asynchronous replication across data centers and region (跨資料中心和區域的非同步複製)
Blob 儲存的資料中心存在於不同的區域——例如，亞太地區、歐洲、美國東部等。在每個區域中，我們在不同位置放置了多個資料中心，以便如果一個資料中心發生故障，我們有同一區域的其他資料中心介入並服務使用者請求。每個區域內至少有三個資料中心，每個資料中心相隔數英里，以防止火災、洪水等局部事件。

Blob 的副本數量稱為複製因子 (replication factor)。大多數情況下，複製因子為 3 就足夠了。

[這些是區域和可用區。深黃色是主要資料，淺黃色是副本](./replication.jpg)

我們保留 Blob 的四個副本。一個是主要區域資料中心內的本地副本，以防止伺服器機架和磁碟機故障。Blob 的第二個副本放置在同一區域內的另一個資料中心，以防止資料中心發生火災或洪水。第三個副本放置在不同區域的資料中心，以防止區域性災難。

## Garbage collection while deleting a blob (刪除 Blob 時的垃圾回收)
由於 Blob 區塊放置在不同的資料節點上，從許多不同的節點刪除需要時間，而讓客戶端等待直到完成並不是一個可行的選擇。由於即時延遲優化，我們實際上並不會針對刪除請求從 Blob 儲存中刪除 Blob。相反，我們只是在元數據中將 Blob 標記為“DELETED”(已刪除)，使其對使用者不可存取。Blob 在回應使用者的刪除請求後稍後被刪除。

將 Blob 標記為已刪除，但此刻並未實際刪除它，會導致內部元數據不一致，這意味著事物繼續佔用應該空閒的儲存空間。這些元數據不一致對使用者沒有影響。例如，對於在元數據中標記為已刪除的 Blob，我們仍然在元數據中擁有該 Blob 區塊的條目。資料節點仍然持有該 Blob 的區塊。因此，我們有一個稱為垃圾回收器 (garbage collector) 的服務，稍後會清理元數據不一致。刪除 Blob 會導致釋放與該 Blob 關聯的區塊。然而，在使用者刪除 Blob 的時間與 Blob 儲存中可用空間相應增加的時間之間可能會有明顯的時間延遲。我們可以忍受這種明顯的時間延遲，因為作為回報，我們為使用者的刪除 Blob 請求獲得了即時快速回應的好處。

## Cache the blob store (快取 Blob 儲存)
快取可以在多個層面上進行。以下是一些例子：

- 第一次讀取 Blob 區塊的元數據時，會將其快取在客戶端。客戶端可以直接轉到資料節點，而無需在第二次讀取同一 Blob 時與主節點通訊。
- 在前端伺服器，我們快取分區映射並使用它來確定將每個請求轉發到哪個分區伺服器。
- 頻繁存取的區塊在主節點處快取，這有助於我們有效地串流大型物件。它還減少了磁碟 I/O。

注意：Blob 儲存的快取通常使用 CDN 完成。Azure Blob 儲存服務將可公開存取的 Blob 快取在 Azure 內容傳遞網路 (Content Delivery Network) 中，直到該 Blob 的 TTL (存活時間) 經過。源伺服器定義 TTL，CDN 從源伺服器的 HTTP 回應中的 Cache-Control 標頭確定它。
我們涵蓋了設計 Blob 儲存時應考慮的設計因素。現在，我們將評估我們設計的內容。
