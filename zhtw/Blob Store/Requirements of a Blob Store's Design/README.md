# Requirements of a Blob Store's Design (Blob 儲存設計的需求)
## Requirements (需求)
讓我們了解以下的功能和非功能需求：

### Functional requirements (功能性需求)
以下是 Blob 儲存設計的功能需求：

- **Create a container (建立容器)**：使用者應該能夠建立容器來將 Blob 分組。例如，如果應用程式想要儲存特定於使用者的資料，它應該能夠將不同使用者帳戶的 Blob 儲存在不同的容器中。此外，使用者可能希望將影片 Blob 分組，並將它們與一組圖片 Blob 分開。單個 Blob 儲存使用者可以建立許多容器，並且每個容器可以有許多 Blob，如下圖所示。為簡單起見，我們假設我們無法在容器內建立容器。

容器就像檔案系統中用於將 Blob 分組的資料夾。不要將此容器與 Docker 容器混淆。
```

[與單個儲存帳戶關聯的多個容器，以及單個容器內的多個 Blob](./blob.jpg)

- **Put data (放入資料)**：Blob 儲存應該允許使用者將 Blob 上傳到已建立的容器中。
- **Get data (獲取資料)**：系統應該為上傳的 Blob 生成 URL，以便使用者以後可以通過此 URL 存取該 Blob。
- **Delete data (刪除資料)**：使用者應該能夠刪除 Blob。如果使用者希望將資料保留一段指定的時間 (保留時間)，我們的系統應該支援此功能。
- **List blobs (列出 Blob)**：使用者應該能夠獲取特定容器內的 Blob 列表。
- **Delete a container (刪除容器)**：使用者應該能夠刪除容器及其內的所有 Blob。
- **List containers (列出容器)**：系統應該允許使用者列出特定帳戶下的所有容器。

### Non-functional requirements (非功能性需求)
以下是 Blob 儲存系統的非功能需求：

- **Availability (可用性)**：我們的系統應該是高可用的。
- **Durability (持久性)**：資料一旦上傳，除非使用者明確刪除該資料，否則不應遺失。
- **Scalability (可擴展性)**：系統應該能夠處理數十億個 Blob。
- **Throughput (吞吐量)**：對於傳輸 gigabytes (GB) 的資料，我們應該確保高資料吞吐量。
- **Reliability (可靠性)**：由於故障是分散式系統中的常態，我們的設計應該能夠及時檢測並從故障中恢復。
- **Consistency (一致性)**：系統應該是強一致的。不同的使用者應該看到 Blob 的相同視圖。

## Resource estimation (資源估算)
讓我們估算 Blob 儲存系統所需的伺服器總數、儲存和頻寬。由於 Blob 可以有各種資料，因此在我們的估算中提及所有這些類型的資料可能並不實際。因此，我們將使用 YouTube 作為範例，它將影片和縮圖儲存在 Blob 儲存中。此外，我們將做出以下假設來完成我們的估算。

Assumptions (假設)：

- 上傳或觀看影片的每日活躍使用者數為 500 萬 (5 million)。
- 單個 Blob 儲存伺服器每秒可以處理的請求數為 500。這個數字可能會高得多，具體取決於 Blob 儲存。例如，Microsoft Azure 可以處理高達 20,000 IOPS。
- 影片的平均大小為 50 MB。
- 縮圖的平均大小為 20 KB。
- 每天上傳的影片數量為 250,000。
- 單個使用者每天的讀取請求數為 20。

### Number of servers estimation (伺服器數量估算)
根據我們的假設，我們使用每日活躍使用者數 (DAU) 和 Blob 儲存伺服器每秒可以處理的查詢數。我們所需的伺服器數量是使用下面給出的公式計算的：
活躍使用者數 / 每台伺服器處理的查詢數 = 10 K 台伺服器
```

### Storage estimation (儲存估算)
考慮上面寫的假設，我們使用下面給出的公式來計算 YouTube 一天所需的總儲存空間：

每日總儲存量 = 每天影片數 x (每個影片的儲存量 + 每個縮圖的儲存量)
```

將上面的數字代入公式，得出 12.51 TB /天，這是 YouTube 每天以單一解析度保留上傳影片的單個副本所需的近似儲存空間。

### Bandwidth estimation (頻寬估算)
讓我們估算將資料上傳到 Blob 儲存和從中檢索資料所需的頻寬。

Incoming traffic (傳入流量)：為了估算傳入流量所需的頻寬，我們考慮每天上傳的總資料量，這間接意味著我們上面計算的每天所需的總儲存量。每秒傳輸到伺服器的資料量可以使用以下公式計算：

       總頻寬 = 每天總儲存量 / (24x60x60)
```
                 YouTube 上傳影片所需的頻寬
 每天總儲存量 (TB)      	一天的秒數       	頻寬 (Gb/s)
 12.51                     86400              1.16
```

Outgoing traffic (傳出流量)：由於 Blob 儲存是一個讀取密集型儲存，大部分頻寬都需要用於傳出流量。考慮上述假設，我們使用以下公式計算傳出流量所需的頻寬：

總頻寬 = (每天活躍使用者數 x 每位使用者每天的請求數 x 總資料大小) / 一天的秒數
```

```

## Building blocks we will use (我們將使用的構建塊)
我們在 Blob 儲存系統的設計中使用以下構建塊：

[任務排程器設計的構建塊](./bb.jpg)

- **Rate Limiter (速率限制器)**：需要速率限制器來控制使用者與系統的互動。
- **Load balancer (負載平衡器)**：需要負載平衡器將請求負載分發到不同的伺服器上。
- **Database (資料庫)**：資料庫用於儲存 Blob 的元數據資訊。
- **Monitoring (監控)**：需要監控以檢查儲存設備及其可用空間，以便在需要時及時新增儲存。
