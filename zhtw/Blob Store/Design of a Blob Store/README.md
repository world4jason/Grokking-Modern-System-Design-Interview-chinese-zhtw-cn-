# Design of a Blob Store (Blob 儲存的設計)

## High-level design (高階設計)
讓我們識別並連接 Blob 儲存系統的組件。在高階層面上，組件包括客戶端、前端伺服器和儲存磁碟。

[Blob 儲存的高階設計](./design.jpg)

客戶端的請求在處理請求的前端伺服器處接收。前端伺服器將客戶端的 Blob 儲存到連接到它們的儲存磁碟上。

## API design (API 設計)
讓我們來看看 Blob 儲存的 API 設計。以下所有功能只能由已註冊和經過身份驗證的使用者執行。為了簡潔起見，我們不包括使用者的註冊和身份驗證等功能。

**Create container (建立容器)**

`createContainer` 操作在產生此請求的登入帳戶下建立一個新容器。

```
createContainer(containerName)
```

參數 (Parameter)        描述 (Description)

containerName         這是容器的名稱。它在儲存帳戶內應該是唯一的。
```

**Upload blobs (上傳 Blobs)**

客戶端的資料以 Bytes 的形式儲存在 Blob 儲存中。資料可以使用以下程式碼放入容器中：

```
putBlob(containerPath, blobName, data)
```

參數 (Parameter)         描述 (Description)

containerPath          這是我們上傳 Blob 的容器路徑。它由 accountID 和 containerID 組成。

blobName               這是 Blob 的名稱。它在容器內應該是唯一的，否則我們的系統將為後來上傳的 Blob 提供版本號。

data                   這是使用者想要上傳到 Blob 儲存的檔案。
```


注意：此 API 只是說明需求的一種邏輯方式。如果資料量非常大，我們可能會在實際實作中使用多步驟串流呼叫。
```

**Download blobs (下載 Blobs)**

Blob 由其唯一名稱或 ID 識別。

```
getBlob(blobPath)
```

參數 (Parameter)        描述 (Description)

blobPath               這是資料或檔案的完全限定路徑 (fully qualified path)，包括其唯一 ID。
```

**Delete blob (刪除 Blob)**

`deleteBlob` 操作標記指定的 Blob 以進行刪除。實際的 Blob 在垃圾回收期間被刪除。

```
deleteBlob(blobPath)
```

參數 (Parameter)       描述 (Description)

blobPath              這是使用者想要刪除的 Blob 的路徑。
```

**List blobs (列出 Blobs)**
`listBlobs` 操作返回指定容器或路徑下的 Blob 列表。

```
listBlobs(containerPath)
```

參數 (Parameter)        描述 (Description)

containerPath         這是使用者想要從中獲取 Blob 列表的容器路徑。
```

**Delete container (刪除容器)**

`deleteContainer` 操作標記指定的容器以進行刪除。容器及其中的任何 Blob 稍後在垃圾回收期間被刪除。

```
deleteContainer(containerPath)
```

參數 (Parameter)        描述 (Description)

containerPath         這是使用者想要刪除的容器路徑。
```

**List containers (列出容器)**

`listContainers` 操作返回指定使用者 Blob 儲存帳戶下的容器列表。

```
listContainers(accountID)
```

參數 (Parameter)     描述 (Description)

accountID           這是想要列出其容器的使用者的 ID。
```

注意：用於檢索 Blob 的 API 提供包含大小、版本號、存取權限、名稱等的元數據。
```

## Detailed design (詳細設計)
我們首先識別完成 Blob 儲存設計所需的關鍵組件。然後，我們看看這些組件如何連接以滿足我們的功能需求。

### Components (組件)
以下是我們在 Blob 儲存設計中使用的組件列表：

- **Client (客戶端)**：這是執行任何指定 API 功能的使用者或程式。
- **Rate limiter (速率限制器)**：速率限制器根據使用者的訂閱限制請求數量，或限制同一時間來自同一 IP 地址的請求數量。它不允許使用者超過預定義的限制。
- **Load balancer (負載平衡器)**：負載平衡器將傳入的網路流量分發到一組伺服器中。它還用於根據使用者的位置將請求重新路由到不同的區域、同一區域內的不同資料中心或同一資料中心內的不同伺服器。可以使用 DNS 負載平衡根據使用者的位置在不同區域之間重新路由請求。
- **Front-end servers (前端伺服器)**：前端伺服器將使用者新增或刪除資料的請求轉發到適當的儲存伺服器。
- **Data nodes (資料節點)**：資料節點保存實際的 Blob 資料。它們也可能包含 Blob 資料的一部分。Blob 被分成固定大小的小塊，稱為區塊 (chunks)。一個資料節點可以容納 Blob 的所有區塊或至少其中一些。
- **Master node (主節點)**：主節點是管理所有資料節點的核心組件。它儲存有關儲存路徑和 Blob 存取權限的資訊。有兩種類型的存取權限：私有和公開。私有存取權限意味著 Blob 只能由包含該 Blob 的帳戶存取。公開存取權限意味著任何人都可以存取該 Blob。

注意：叢集中的每個資料節點定期向主節點發送心跳 (heartbeat) 和區塊報告 (chunk report)。心跳的存在表示資料節點正在運作。區塊報告列出了資料節點上的所有區塊。如果資料節點未能發送心跳，主節點會認為該節點已死亡，然後在副本節點上處理使用者請求。主節點維護待處理操作的日誌，這些操作應在當死去的資料節點恢復時在其上重播。
- **Metadata storage (元數據儲存)**：元數據儲存是一個分散式資料庫，由主節點用來儲存所有元數據。元數據包括帳戶元數據、容器元數據和 Blob 元數據。
 - 帳戶元數據包含每個使用者的帳戶資訊和每個帳戶持有的容器。
 - 容器元數據包括每個容器中 Blob 的列表。
 - Blob 元數據包括每個 Blob 的儲存位置。Blob 元數據將在下一課詳細討論。

- **Monitoring service (監控服務)**：監控服務監控資料節點和主節點。在發生需要人工干預的磁碟故障時，它會向管理員發出警報。它還獲取有關磁碟上剩餘總可用空間的資訊，以提醒管理員新增更多磁碟。
- **Administrator (管理員)**：管理員負責處理來自監控服務的通知，並對整體服務進行例行檢查以確保可靠性。

### Workflow (工作流程)
我們根據可以在 Blob 儲存上執行的基本操作來描述工作流程。我們假設使用者已成功登入並且已經建立了容器。每個使用者和容器都分配了一個唯一 ID。使用者在特定容器中執行以下操作。

**Write a blob (寫入 Blob)**

1. 客戶端生成上傳 Blob 請求。如果客戶端的請求成功通過速率限制器，負載平衡器將客戶端的請求轉發到其中一個前端伺服器。前端伺服器隨後向主節點請求它應該聯繫以儲存 Blob 的資料節點。
2. 主節點使用唯一 ID 生成器系統為 Blob 分配唯一 ID。然後，它將大尺寸的 Blob 分成較小的固定大小區塊，並為每個區塊分配一個資料節點，該區塊最終將儲存在該資料節點中。主節點使用可用空間管理系統確定資料節點上的可用儲存空間量。
3. 確定區塊到資料節點的映射後，前端伺服器將區塊寫入分配的資料節點。
4. 我們複製每個區塊以達到冗餘目的。所有關於區塊複製的選擇都在主節點進行。因此，主節點也分配儲存和資料節點來儲存副本。
5. 主節點將 Blob 元數據儲存在元數據儲存中。我們在下一課詳細討論 Blob 的元數據模式。
6. 寫入 Blob 後，將 Blob 的完全限定路徑返回給客戶端。路徑包括使用者 ID、使用者新增 Blob 的容器 ID、Blob ID 和 Blob 的存取級別。

問 (Question)
如果使用者在同一個容器內並發寫入兩個同名的 Blob，主節點會做什麼？

答 (Answer)
主節點將此類操作序列化，並為後來上傳的 Blob 分配版本號。
```

**Reading a blob (讀取 Blob)**

1. 當 Blob 的讀取請求到達前端伺服器時，它會向主節點詢問該 Blob 的元數據。
2. 主節點首先根據 Blob 的路徑以及我們是否被授權傳輸該 Blob 來檢查該 Blob 是私有的還是公開的。
3. 授權 Blob 後，主節點在元數據中尋找該 Blob 的區塊，並查看它們到資料節點的映射。主節點將區塊及其映射 (資料節點) 返回給客戶端。
4. 客戶端隨後從資料節點讀取區塊資料。

注意：用於讀取 Blob 的元數據資訊快取在客戶端機器上，以便下次客戶端想要讀取同一個 Blob 時，我們不必加重主節點的負擔。此外，客戶端的下次讀取操作會更快。
```

問 (Question)
假設主節點因為即將發生的磁碟故障而將資料從一個資料節點移動到另一個資料節點。如果使用者使用快取的元數據存取資料，他們現在將擁有過時的資訊。我們如何處理這種情況？

答 (Answer)
在這種情況下，客戶端呼叫失敗。然後客戶端刷新快取並從主節點獲取新的元數據資訊。
```

**Deleting a blob (刪除 Blob)**
收到刪除 Blob 請求後，主節點在元數據中將該 Blob 標記為已刪除，並稍後使用垃圾回收器釋放空間。我們在下一課了解更多關於垃圾回收器的資訊。

問 (Question)
主節點可以被視為單點故障嗎？如果是，那我們如何應對這個問題？

答 (Answer)
是的，因為主節點是 Blob 儲存的中心點，並且是單點故障。因此，我們必須有一個備份或影子伺服器 (shadow server) 來代替主節點。

我們為此使用的技術稱為檢查點 (checkpointing)，這意味著我們在不同的時間間隔對資料進行快照。快照捕獲運行中主節點的狀態、資料、硬體配置以及主節點和資料節點之間傳輸的訊息。它在外部儲存區域或快照存儲庫中維護操作日誌。如果主節點發生故障，自動化系統或管理員使用快照從其發生故障的狀態重新啟動該主節點並重播操作日誌。
```

Operation log (操作日誌)：定義並發操作序列化順序的邏輯時間線
```
