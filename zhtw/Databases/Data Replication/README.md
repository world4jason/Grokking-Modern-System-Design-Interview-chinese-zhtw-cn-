# Data Replication (資料複製)
資料是組織的資產，因為它驅動著整個業務。資料提供了關於什麼是重要的以及什麼需要改變的關鍵業務洞察。組織還需要安全地保存並按需提供其客戶的資料。需要在不同條件下 (增加的讀取和寫入、磁碟和節點故障、網路和電源中斷等) 及時存取所需的資料，才能成功運營線上業務。

我們需要資料儲存具有以下特徵：

Availability under faults (故障下的可用性)：某些磁碟、節點故障以及網路和電源中斷。

Scalability (可擴展性)：隨著讀取、寫入和其他操作的增加。

Performance (效能)：為客戶端提供低延遲和高吞吐量。
在單個節點上實現上述特徵具有挑戰性，甚至是不可能的。

## Replication (複製)
複製 (Replication) 是指在各個節點 (最好是地理上分散的) 上保留資料的多個副本，以實現可用性、可擴展性和效能。在本課中，我們假設單個節點足以容納我們的整個資料。在討論多個節點中的資料分區時，我們不會使用此假設。通常，複製和分區的概念是一起使用的。

然而，複製在帶來許多好處 (如可用性) 的同時，也帶來了複雜性。如果複製的資料不需要頻繁更改，那麼複製相對簡單。複製的主要問題出現在我們必須隨著時間的推移維護複製資料的更改時。

由於複製可能產生的其他複雜性如下：

我們如何保持資料的多個副本彼此一致？

我們如何處理發生故障的副本節點？

我們應該同步複製還是非同步複製？
    +如果是非同步複製，我們如何處理複製延遲？
  
我們如何處理併發寫入？

需要向終端程式設計師公開什麼一致性模型？
我們將在本課中探討這些問題的答案。

## Synchronous versus asynchronous replication (同步與非同步複製)
有兩種方法可以將更改傳播到副本節點：

Synchronous replication (同步複製)
Asynchronous replication (非同步複製)
```

在同步複製中，主節點 (primary node) 等待輔助節點 (secondary nodes) 關於更新資料的確認。在收到所有輔助節點的確認後，主節點向客戶端報告成功。而在非同步複製中，主節點不等待輔助節點的確認，並在更新自身後向客戶端報告成功。

同步複製的優點是所有輔助節點都與主節點完全保持最新。然而，這種方法有一個缺點。如果其中一個輔助節點由於網路故障或錯誤而沒有確認，則主節點將無法確認客戶端，直到它收到崩潰節點的成功確認。這會導致主節點對客戶端的回應延遲很高。

另一方面，非同步複製的優點是即使所有輔助節點都宕機，主節點也可以繼續其工作。然而，如果主節點發生故障，未複製到輔助節點的寫入將會丟失。

上一段解釋了當系統的不同組件可能發生故障時，資料一致性和可用性之間的權衡。

## Data replication models (資料複製模型)
現在，讓我們討論資料複製的各種機制。在本節中，我們將討論以下模型及其優缺點：

Single leader or primary-secondary replication (單一領導者或主從複製)
Multi-leader replication (多領導者複製)
Peer-to-peer or leaderless replication (點對點或無領導者複製)
```

### Single leader/primary-secondary replication (單一領導者/主從複製)
在主從複製 (primary-secondary replication) 中，資料在多個節點之間複製。一個節點被指定為主節點。它負責處理對儲存在叢集上的資料的任何寫入。它還將所有寫入發送到輔助節點並保持它們同步。

當我們的工作負載是讀取密集型時，主從複製是合適的。為了更好地隨著讀者的增加而擴展，我們可以新增更多追隨者 (followers) 並將讀取負載分佈在可用的追隨者之間。然而，將資料複製到許多追隨者可能會造成主節點瓶頸。此外，如果我們的工作負載是寫入密集型的，則主從複製是不合適的。

主從複製的另一個優點是它具有讀取彈性。在主節點發生故障的情況下，輔助節點仍然可以處理讀取請求。因此，這是讀取密集型應用程式的一種有用方法。

如果我們使用非同步複製，通過這種方法的複製會帶來不一致。在主節點發生故障且無法將更新的資料傳播到輔助節點的情況下，從不同副本讀取的客戶端可能會看到不一致的資料。因此，如果主節點發生故障，任何未傳遞給輔助節點的錯過更新都可能丟失。

[資料從主節點複製到輔助節點的主從資料複製模型](./1primary.jpg)

問 (Question)
當主節點發生故障時會發生什麼？

答 (Answer)
在主節點發生故障的情況下，可以將輔助節點指定為主節點，這可以加速恢復初始主節點的過程。有兩種方法可以選擇新的主節點：手動和自動。

在手動方法中，操作員決定哪個節點應該是主節點並通知所有輔助節點。

在自動方法中，當輔助節點發現主節點發生故障時，它們通過進行稱為領導者選舉 (leader election) 的選舉來任命新的主節點。領導者通常基於某個因素分配，例如選擇具有最高識別碼的處理器。
```

#### Primary-secondary replication methods (主從複製方法)
主從複製中有許多不同的複製方法：

Statement-based replication (基於語句的複製)
Write-ahead log (WAL) shipping (預寫日誌傳送)
Logical (row-based) log replication (邏輯 (基於行) 日誌複製)
讓我們詳細討論每一個。

##### Statement-based replication (基於語句的複製)
在基於語句的複製方法中，主節點保存其執行的所有語句，如 insert、delete、update 等，並將它們發送到輔助節點執行。MySQL 在 5.1 版本之前使用了這種類型的複製。

這種類型的方法看起來不錯，但也有其缺點。例如，任何非確定性函式 (如 NOW()) 都可能導致追隨者和領導者上的寫入不同。此外，如果寫入語句依賴於先前的寫入，並且它們都以錯誤的順序到達追隨者，則追隨者節點上的結果將是不確定的。

##### Write-ahead log (WAL) shipping (預寫日誌傳送)
在預寫日誌 (WAL) 傳送方法中，主節點在執行查詢之前將其保存在稱為預寫日誌檔案的日誌檔案中。然後它使用這些日誌將資料複製到輔助節點上。這在 PostgreSQL 和 Oracle 中使用。WAL 的問題在於它只定義了非常底層的資料。它與資料庫引擎的內部結構緊密耦合，這使得升級領導者和追隨者上的軟體變得複雜。

##### Logical (row-based) log replication (邏輯 (基於行) 日誌複製)
在邏輯 (基於行) 日誌複製方法中，所有輔助節點複製實際的資料更改。例如，如果在資料表中插入或刪除了一行，輔助節點將在該特定資料表中複製該更改。二進位日誌在記錄級別上記錄對主節點上資料庫表的更改。為了建立主節點的副本，輔助節點讀取此資料並相應地更改其記錄。基於行的複製沒有與 WAL 相同的困難，因為它不需要有關資料庫引擎內部資料佈局的資訊。

### Multi-leader replication (多領導者複製)
如上所述，使用非同步複製的單一領導者複製有一個缺點。只有一個主節點，所有的寫入都必須經過它，這限制了效能。在主節點發生故障的情況下，輔助節點可能沒有更新的資料庫。

多領導者複製是單一領導者複製的替代方案。有多個主節點處理寫入並將其發送到所有其他主節點和輔助節點進行複製。這種類型的複製與 MySQL 的 Tungsten Replicator 等外部工具一起在資料庫中使用。

這種複製在我們可以離線繼續工作的應用程式中非常有用——例如，即使我們無法存取網際網路也可以設定會議的行事曆應用程式。一旦我們上線，它就會將其本地資料庫 (我們的手機或筆記型電腦充當主節點) 的更改複製到其他節點。

#### Conflict (衝突)
多領導者複製比單一領導者複製提供更好的效能和可擴展性，但它也有一個顯著的缺點。由於所有主節點同時處理寫入請求，它們可能會修改相同的資料，這可能會在它們之間產生衝突。例如，假設同一資料由兩個客戶端同時編輯。在這種情況下，它們的寫入將在其關聯的主節點中成功，但是當它們非同步到達其他主節點時，會產生衝突。

#### Handle conflicts (處理衝突)
衝突可能導致不同節點上的資料不同。這些應該在不丟失任何資料的情況下得到有效處理。讓我們討論一些處理衝突的方法：

##### Conflict avoidance (衝突避免)
處理衝突的一個簡單策略是首先防止它們發生。如果應用程式可以驗證給定記錄的所有寫入都通過同一個領導者，則可以避免衝突。

但是，如果使用者移動到不同的位置並且現在靠近不同的資料中心，則仍可能發生衝突。如果發生這種情況，我們需要重新路由流量。在這種情況下，衝突避免方法失敗並導致併發寫入。

##### Last-write-wins (最後寫入者獲勝)
所有節點使用其本地時鐘為每個更新分配時間戳。當發生衝突時，選擇具有最新時間戳的更新。

這種方法也可能造成困難，因為在分散式系統中跨節點的時鐘同步具有挑戰性。時鐘偏差可能導致資料丟失。

##### Custom logic (自定義邏輯)
在這種方法中，我們可以編寫自己的邏輯來根據應用程式的需求處理衝突。此自定義邏輯可以在讀取和寫入時執行。當系統檢測到衝突時，它會調用我們的自定義衝突處理程序。

#### Multi-leader replication topologies (多領導者複製拓撲)
有多種拓撲可以用來實現多領導者複製，例如環形拓撲、星形拓撲和全對全拓撲。最常見的是全對全拓撲。在星形和環形拓撲中，同樣存在類似的缺點，即如果其中一個節點發生故障，它可能會影響整個系統。這就是為什麼全對全是使用最多的拓撲。

### Peer-to-peer/leaderless replication (點對點/無領導者複製)
在主從複製中，主節點是瓶頸和單點故障。此外，它有助於實現讀取可擴展性，但在提供寫入可擴展性方面失敗。點對點複製模型通過沒有單一主節點來解決這些問題。所有節點具有相同的權重，並且可以接受讀取和寫入請求。Amazon 在其 DynamoDB 資料儲存中普及了這種方案。

[所有節點對所有資料應用讀取和寫入的點對點資料複製模型](./p2p.jpg)

與主從複製一樣，此複製也可能產生不一致。這是因為當多個節點接受寫入請求時，可能會導致併發寫入。用於解決寫入-寫入不一致的一種有用方法稱為法定人數 (quorums)。

#### Quorums (法定人數)
讓我們假設我們有三個節點。如果三個節點中至少有兩個保證返回成功的更新，這意味著只有一個節點失敗了。這意味著如果我們從兩個節點讀取，其中至少有一個將具有更新的版本，並且我們的系統可以繼續工作。

如果我們有 n 個節點，那麼每次寫入必須在至少 w 個節點中更新才能被視為成功，並且我們必須從 r 個節點讀取。只要 w + r > n，我們就可以通過讀取獲得更新的值，因為至少有一個節點必須具有我們可以從中讀取的更新寫入。法定人數讀取和寫入遵守這些 r 和 w 值。這些 n、w 和 r 在 Dynamo 風格的資料庫中是可設定的。
