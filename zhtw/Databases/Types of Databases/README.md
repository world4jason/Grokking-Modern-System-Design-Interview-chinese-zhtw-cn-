# Types of Databases (資料庫類型)
正如我們之前討論的，資料庫分為兩種類型：關聯式和非關聯式。讓我們詳細討論這些類型。

## Relational databases (關聯式資料庫)
關聯式資料庫在儲存資料之前會堅持特定的模式。儲存在關聯式資料庫中的資料具有先前的結構。大多情況下，該模型將資料組織成一個或多個關係 (也稱為表)，每個元組 (實例) 都有一個唯一的鍵。資料的每個實體由實例和屬性組成，其中實例儲存在行中，每個實例的屬性儲存在列中。由於每個元組都有一個唯一的鍵，因此可以通過在其他表中儲存主鍵 (通常稱為外鍵) 將一個表中的元組連結到其他表中的元組。

結構化查詢語言 (SQL) 用於操作資料庫。這包括資料的插入、刪除和檢索。

關聯式資料庫的流行和主導地位有多種原因，包括簡單性、穩健性、靈活性、效能、可擴展性和管理通用資料的兼容性。

關聯式資料庫提供原子性 (Atomicity)、一致性 (Consistency)、隔離性 (Isolation) 和持久性 (Durability) (ACID) 屬性來維護資料庫的完整性。ACID 是一個強大的抽象，它簡化了與資料的複雜互動，並在簡單的事務中止背後隱藏了許多異常 (如髒讀、髒寫、讀取偏差、丟失更新、寫入偏差和幻讀)。

但在設計上，ACID 就像一把大錘子，足以應對所有問題。如果某些特定應用程式只需要處理一些異常，那麼有機會使用自定義解決方案來獲得更高的效能，儘管會增加複雜性。

讓我們詳細討論 ACID：

- **Atomicity (原子性)**：事務被視為原子單位。因此，要麼事務中的所有語句都成功執行，要麼都不執行。如果事務中的語句失敗，它應該中止並回滾。

- **Consistency (一致性)**：在任何給定時間，資料庫都應處於一致狀態，並且在每次事務後都應保持一致狀態。例如，如果多個使用者想要從資料庫中查看記錄，它每次都應該返回類似的結果。

- **Isolation (隔離性)**：在多個事務並發執行的情況下，它們不應相互影響。資料庫的最終狀態應該與事務按順序執行時相同。

- **Durability (持久性)**：系統應保證即使在系統故障事件中，已完成的事務也能永久保存在資料庫中。

各種資料庫管理系統 (DBMS) 用於定義關聯式資料庫模式以及其他操作，例如存取、檢索和在資料上執行 SQL 查詢。一些流行的 DBMS 如下：

```

Microsoft SQL Server

### Why relational databases? (為什麼選擇關聯式資料庫？)
關聯式資料庫是軟體專業人員進行結構化資料儲存的預設選擇。這些資料庫有很多優點。關聯式資料庫的最大優勢之一是其 ACID 事務和相關程式設計語義的抽象。這使得終端程式設計師使用關聯式資料庫非常方便。讓我們回顧一下關聯式資料庫的一些重要特徵：

#### Flexibility (靈活性)
在 SQL 的背景下，資料定義語言 (DDL) 為我們提供了修改資料庫的靈活性，包括表、列、重命名表和其他更改。DDL 甚至允許我們在進行其他查詢和資料庫伺服器運行時修改模式。

DDL 是一種用於建立和修改資料庫中資料庫物件結構的電腦語言。
```

#### Reduced redundancy (減少冗餘)
關聯式資料庫的最大優點之一是它消除了資料冗餘。與特定實體相關的資訊出現在一個表中，而與該特定實體相關的資料出現在通過外鍵連結的其他表中。這個過程稱為標準化 (normalization)，並且具有消除不一致依賴關係的額外好處。

當使用者在不相關的表中搜尋某些資料或相關表中缺少資料時，就會出現不一致的依賴關係 (Inconsistent dependencies)。例如，要查詢客戶的地址，應該在客戶表中搜尋而不是在產品表中搜尋。
```

#### Concurrency (併發性)
併發性是設計企業資料庫時的一個重要因素。在這種情況下，資料由許多使用者同時讀取和寫入。我們需要協調這種互動以避免資料不一致——例如，飯店客房的重複預訂。關聯式資料庫中的併發性通過對資料的事務性存取來處理。如前所述，事務被視為原子操作，因此它在錯誤處理中也起作用，以便在成功執行時回滾或提交事務。

#### Integration (整合)
從多個來源聚合資料的過程是企業應用程式中的常見做法。執行此聚合的常見方法是整合共享資料庫，其中多個應用程式儲存其資料。這樣，所有應用程式都可以輕鬆存取彼此的資料，同時併發控制措施處理多個應用程式的存取。

#### Backup and disaster recovery (備份和災難恢復)
關聯式資料庫保證資料狀態隨時一致。匯出和匯入操作使備份和恢復更容易。大多數基於雲端的關聯式資料庫執行連續鏡像以避免資料丟失並使恢復過程更容易和更快速。

### Drawback (缺點)

#### Impedance mismatch (阻抗失配)
阻抗失配是關聯式模型與記憶體中資料結構之間的差異。關聯式模型將資料組織成具有關係和元組的表格結構。對這種結構化資料的 SQL 操作產生與關聯代數一致的關係。但是，它有一些限制。特別是，表中的值採用簡單的值，不能是結構或列表。記憶體中的情況不同，可以儲存複雜的資料結構。為了使複雜結構與關係兼容，我們需要根據關聯代數對資料進行轉換。因此，阻抗失配需要兩種表示之間的轉換，如下圖所示：

## Why non-relational (NoSQL) databases? (為什麼選擇非關聯式 (NoSQL) 資料庫？)
NoSQL 資料庫專為各種資料模型設計，用於存取和管理資料。有各種類型的 NoSQL 資料庫，我們將在下一節中解釋。這些資料庫用於需要大量半結構化和非結構化資料、低延遲和靈活資料模型的應用程式中。這可以通過放寬其他資料庫的一些資料一致性限制來實現。以下是 NoSQL 資料庫的一些特徵：

Simple design (簡單設計)：與關聯式資料庫不同，NoSQL 不需要處理阻抗失配——例如，將所有員工資料儲存在一個文件中，而不是需要連接操作的多個表中。這種策略使其簡單且更易於編寫更少的程式碼、除錯和維護。
 
Horizontal scaling (水平擴展)：主要由於其在大規模叢集上運行資料庫的能力，NoSQL 受到青睞。這解決了併發使用者數量增加時的問題。NoSQL 更容易擴展，因為與特定員工相關的資料儲存在一個文件中，而不是跨節點的多個表中。NoSQL 資料庫通常將資料分佈在多個節點上，並自動在節點之間平衡資料和查詢。在節點故障的情況下，可以在不中斷任何應用程式的情況下透明地替換它。

Availability (可用性)：為了增強資料的可用性，可以在沒有應用程式停機的情況下執行節點替換。大多數非關聯式資料庫變體支援資料複製，以確保高可用性和災難恢復。

Support for unstructured and semi-structured data (支援非結構化和半結構化資料)：許多 NoSQL 資料庫處理在資料庫設定或資料寫入時沒有模式的資料。例如，文件資料庫是無結構的；它們允許文件 (JSON、XML、BSON 等) 具有不同的欄位。例如，一個 JSON 文件可以比另一個擁有更少的欄位。

Cost (成本)：許多 RDBMS 的許可證非常昂貴，而許多 NoSQL 資料庫是開源且免費提供的。同樣，一些 RDBMS 依賴於昂貴的專有硬體和儲存系統，而 NoSQL 資料庫通常使用廉價的商用伺服器叢集。
```

Unstructured data (非結構化資料)：在寫入資料時不知道資料的模式。模式通常在讀取此類資料時定義。
```

NoSQL 資料庫根據操作和功能的性質分為各種類別，包括文件儲存、列式資料庫、鍵值儲存和圖形資料庫。我們將在以下部分從系統設計的角度討論它們中的每一個及其用例。

### Types of NoSQL databases (NoSQL 資料庫類型)
下面描述了各種類型的 NoSQL 資料庫：

[NoSQL 資料庫的類型](./nonrelational.jpg)

#### Key-value database (鍵值資料庫)
鍵值資料庫使用鍵值方法 (如雜湊表) 將資料儲存在鍵值對中。我們可以在下面幾段的圖中看到這一點。在這裡，鍵充當唯一鍵或主鍵，值可以是從簡單標量值到複雜物件的任何內容。這些資料庫允許輕鬆對資料進行分區和水平擴展。一些流行的鍵值資料庫包括 Amazon DynamoDB、Redis 和 Memcached DB。

Use case (用例)：鍵值資料庫對於面向對談 (session-oriented) 的應用程式非常有效。面向對談的應用程式，例如 Web 應用程式，在會話期間將使用者資料儲存在主記憶體或資料庫中。此資料可能包括使用者個人資料資訊、推薦、有針對性的促銷、折扣等。唯一的 ID (鍵) 分配給每個使用者的會話，以便於存取和儲存。因此，儲存此類資料的更好選擇是鍵值資料庫。

下圖顯示了鍵值資料庫的範例。項目的 Product ID (產品 ID) 和 Type (類型) 被統稱為主鍵。這被認為是此鍵值資料庫的鍵。此外，用於儲存項目屬性的模式是根據項目的性質及其擁有的屬性數量定義的。

[以鍵值對形式儲存在 DynamoDB 中的資料，其中鍵是兩個屬性 (產品 ID 和類型) 的組合](./dynamo.jpg)

#### Document database (文件資料庫)
文件資料庫旨在以 XML、JSON、BSON 等格式儲存和檢索文件。這些文件由分層樹狀資料結構組成，可以包括映射、集合和標量值。此類資料庫中的文件可能具有不同的結構和資料。MongoDB 和 Google Cloud Firestore 是文件資料庫的範例。

Use case (用例)：文件資料庫適用於非結構化目錄資料，如 JSON 檔案或其他複雜結構的分層資料。例如，在電子商務應用程式中，產品具有數千個屬性，由於其對讀取效能的影響，將其儲存在關聯式資料庫中是不可行的。這就輪到文件資料庫發揮作用了，它可以有效地將每個屬性儲存在單個檔案中，以便於管理和更快的讀取速度。此外，這對於內容管理應用程式 (如部落格和影片平台) 也是一個不錯的選擇。應用程式所需的實體在此類應用程式中儲存為單個文件。

以下範例顯示儲存在 JSON 文件中的資料。此資料關於一個人。檔案中儲存了各種屬性，包括 id、姓名、電子郵件等。

            "$date": "2021-12-10" } }]}
 
               包含商人資料的 JSON 檔案
 ```

#### Graph database (圖形資料庫)
圖形資料庫使用圖形資料結構來儲存資料，其中節點代表實體，邊顯示實體之間的關係。基於關係的節點組織導致節點之間有趣的模式。該資料庫允許我們儲存一次資料，然後根據關係以不同方式解釋它。流行的圖形資料庫包括 Neo4J、OrientDB 和 InfiniteGraph。圖形資料保存在儲存檔案中以進行持久儲存。每個檔案都包含圖形特定部分的資料，例如節點、連結、屬性等。

在下圖中，一些資料使用圖形資料結構儲存在通過代表節點之間關係的邊相互連接的節點中。每個節點都有一些屬性，如姓名、ID 和年齡。ID:2 的節點姓名為 James，年齡為 29 歲。

[圖形由節點和連結組成。此圖形捕獲實體及其相互關係](./graphdb.jpg)

Use case (用例)：圖形資料庫可用於社交應用程式，並提供不同類型的使用者及其活動之間的有趣事實和數據。圖形資料庫的重點是儲存資料，並為基於實體之間關係驅動分析和決策鋪平道路。圖形資料庫的性質使其適用於各種應用程式，例如資料監管和隱私、機器學習研究、基於金融服務的應用程式等等。

#### Columnar database (列式資料庫)
列式資料庫將資料儲存在列而不是行中。它們能夠快速高效地存取資料庫列中的所有條目。流行的列式資料庫包括 Cassandra、HBase、Hypertable 和 Amazon SimpleDB。

Use case (用例)：列式資料庫對於大量的聚合和資料分析查詢非常有效。它大大降低了磁碟 I/O 需求和從磁碟加載所需的資料量。例如，在與金融機構相關的應用程式中，需要對一段時間內的金融交易進行求和。列式資料庫通過僅讀取金額列、忽略客戶的其他屬性來使此操作更快。

### Drawbacks of NoSQL databases (NoSQL 資料庫的缺點)
#### Lack of standardization (缺乏標準化)
NoSQL 不遵循任何特定標準，就像關聯式資料庫遵循關聯代數一樣。將應用程式從一種類型的 NoSQL 資料庫移植到另一種可能是一個挑戰。

#### Consistency (一致性)
NoSQL 資料庫根據可能發生故障時一致性和可用性之間的特定權衡提供不同的產品。我們不會擁有強大的資料完整性，例如關聯式資料庫中的主鍵和參照完整性。資料可能不是強一致性的，而是使用弱模型 (如最終一致性) 緩慢收斂。
