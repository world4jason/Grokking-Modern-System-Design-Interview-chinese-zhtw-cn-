# Data Partitioning (資料分區)
## Why do we partition data? (為什麼我們要對資料進行分區？)
資料是任何組織的資產。增加的資料和對資料的併發讀/寫流量給傳統資料庫帶來了可擴展性壓力。結果，延遲和吞吐量受到影響。傳統資料庫因其特性而具有吸引力，例如範圍查詢、二級索引和具有 ACID 屬性的事務。

在某個時候，單個基於節點的資料庫不足以處理負載。我們可能需要將資料分佈在多個節點上，但仍要匯出關聯式資料庫的所有優良屬性。在實踐中，已經證明在分散式資料庫上提供類似單節點資料庫的屬性具有挑戰性。

一種解決方案是將資料移動到類似 NoSQL 的系統。然而，歷史程式碼庫及其與傳統資料庫的緊密凝聚力使其成為一個昂貴的問題。

組織可能會使用第三方解決方案擴展傳統資料庫。但通常，整合第三方解決方案有其複雜性。更重要的是，有大量機會針對手頭的特定問題進行優化，並獲得比通用解決方案更好的效能。

資料分區 (Data partitioning) 或分片 (sharding) 使我們能夠使用多個節點，其中每個節點管理整個資料的一部分。為了處理不斷增加的查詢率和資料量，我們致力於平衡的分區和平衡的讀/寫負載。

我們將在本課中討論各種分區資料的方法、相關挑戰及其解決方案。

範圍查詢 (Range query) 是一種常見的資料庫操作，用於檢索某個值在上限和下限之間的所有記錄。

二級索引 (Secondary index) 是一種通過主鍵以外的某些資訊片段有效存取資料庫中記錄的方法。

事務 (Transaction) 是一個單一的邏輯工作單元，它存取並可能修改資料庫的內容。
```

## Sharding (分片)
為了在多個節點之間分配負載，我們需要在稱為分區 (partitioning) 或分片 (sharding) 的現象下對資料進行分區。在這種方法中，我們將大型資料集分割成儲存在網路上不同節點的較小資料塊。

分區必須是平衡的，以便每個分區接收大約相同數量的資料。如果分區不平衡，大部分查詢將落在少數幾個分區中。負載過重的分區將造成系統瓶頸。分區的功效將受到損害，因為大部分資料檢索查詢將被發送到承載高度擁塞分區的節點。這些分區被稱為熱點 (hotspots)。通常，我們使用以下兩種方式對資料進行分片：

Vertical sharding (垂直分片)
Horizontal sharding (水平分片)
### Vertical sharding (垂直分片)
我們可以將不同的資料表放在各種資料庫實例中，這些實例可能在不同的實體伺服器上執行。我們可以將一個資料表拆分為多個資料表，以便某些欄位在一個資料表中，而其餘欄位在另一個資料表中。如果多個資料表之間存在連接 (joins)，我們應該小心。我們可能希望將這些表一起保留在一個分片上。

通常，垂直分片用於提高從包含非常寬的文字或二進位大型物件 (blob) 欄位的資料表中檢索資料的速度。在這種情況下，具有大文字或 blob 的欄位被拆分到不同的資料表中。

如下圖所示，Employee (員工) 表被分為兩個表：縮減的 Employee 表和 EmployeePicture (員工圖片) 表。EmployeePicture 表只有兩欄，EmployeID 和 Picture，與原始表分開。此外，Employee 表的主鍵 EmpoloyeeID 被新增到兩個分區表中。這使得資料讀寫更容易，並且有效地執行資料表的重建。

垂直分片有其複雜性，更適合手動分區，利益相關者仔細決定如何對資料進行分區。相比之下，即使在動態條件下，水平分片也適合自動化。

### Horizontal sharding (水平分片)
有時，資料庫中的某些資料表變得太大並影響讀/寫延遲。水平分片或分區用於通過按行拆分資料將一個資料表劃分為多個資料表，如下一節中的圖所示。分佈在資料庫伺服器上的原始資料表的每個分區稱為一個分片 (shard)。通常，有兩種策略可用：

Key-range based sharding (基於鍵範圍的分片)
Hash based sharding (基於雜湊的分片)
```

#### Key-range based sharding (基於鍵範圍的分片)
在基於鍵範圍的分片中，每個分區被分配一個連續的鍵範圍。

在下圖中，使用基於鍵範圍的分片對 Invoice (發票) 表執行水平分區，將 Customer_Id 作為分區鍵。兩個不同顏色的表代表分區。

[水平分區](./horizontal.jpg)

有時，資料庫由通過外鍵關係綁定的多個資料表組成。在這種情況下，使用相同的分區鍵對關係中的所有資料表執行水平分區。屬於同一分區鍵的資料表 (或子表) 分佈到一個資料庫分片。下圖顯示具有相同分區鍵的多個資料表放置在單個資料庫分片中：

[一組資料表上的水平分區](./horizontal_tables.jpg)

多表分片中使用的基本設計技術如下：

- Customer 映射表中在存在一個分區鍵。此資料表駐留在每個分片上，並儲存分片中使用的分區鍵。應用程式通過從所有分片讀取此表來建立分區鍵和資料庫分片之間的映射邏輯，以使映射高效。有時，應用程式使用進階演算法來確定屬於特定分片的分區鍵的位置。

- 分區鍵欄位 Customer_Id 在所有其他資料表中複製，作為資料隔離點。它在增加儲存的影響與有效定位所需分片之間進行權衡。除此之外，它還有助於將資料和工作負載分佈到不同的資料庫分片。資料路由邏輯在應用層使用分區鍵來映射為資料庫分片指定的查詢。

- 主鍵在所有資料庫分片中是唯一的，以避免在分片之間的資料遷移和線上分析處理 (OLAP) 環境中資料合併期間發生鍵衝突。

- 欄位 Creation_date 用作資料一致性點，假設所有節點的時鐘是同步的。此欄位用作在必要時將所有資料庫分片的資料合併到全域視圖的標準。


Online analytical processing (線上分析處理) 或 OLAP，是一種在計算中快速回答多維分析 (MDA) 查詢的方法。MDA 查詢經常針對事實資料庫發出，其中包含 (分類或是序數) 維度上的謂詞和一個或多個度量上的聚合。來源：維基百科
##### Advantages (優點)
使用這種方法，基於範圍查詢的方案易於實現。

可以使用分區鍵執行範圍查詢，並且可以按排序順序將這些鍵保留在分區中。
##### Disadvantages (缺點)
無法使用分區鍵以外的鍵執行範圍查詢。

如果未正確選擇鍵，由於流量分佈不均，某些節點可能必須儲存更多資料。
```

#### Hash-based sharding (基於雜湊的分片)
基於雜湊的分片在屬性上使用類似雜湊的函式，它根據執行分區的屬性產生不同的值。主要概念是對鍵使用雜湊函式以獲取雜湊值，然後對分區數取模。一旦我們找到了適合鍵的雜湊函式，我們就可以給每個分區一個雜湊範圍 (而不是鍵範圍)。任何雜湊發生在該範圍內的鍵都將保留在該分區中。

在下面的圖示中，我們使用 Value mod = n 的雜湊函式。n 是節點數，即 4。我們通過檢查每個鍵的模數將鍵分配給節點。模數值為 2 的鍵分配給節點 2。模數值為 1 的鍵分配給節點 1。模數值為 3 的鍵分配給節點 3。因為沒有模數值為 0 的鍵，所以節點 0 為空。

[基於雜湊的分片](./hash.jpg)

##### Advantages (優點)
鍵在節點之間均勻分佈。

##### Disadvantages (缺點)
我們無法使用此技術執行範圍查詢。鍵將分佈在所有分區上。

注意：每個資料庫有多少個分片？

憑經驗，我們可以確定每個節點能夠以可接受的效能服務多少資料。它可以幫助我們找出我們希望保留在任何一個節點上的最大資料量。例如，如果我們發現我們可以在一個節點上放置最多 50 GB 的資料，我們有以下內容：

Database size (資料庫大小) = 10 TB
Size of a single shard (單個分片的大小) = 50 GB
Number of shards the database should be distributed in (資料庫應分佈的分片數) 10 TB/50 GB = 200 shards (分片)
```

#### Consistent hashing (一致性雜湊)
一致性雜湊將分散式雜湊表中的每個伺服器或項目分配給抽象圓上的一個位置，稱為環，而不管表中伺服器的數量如何。這允許伺服器和物件在不損害系統整體效能的情況下進行擴展。

##### Advantages of consistent hashing (一致性雜湊的優點)
它易於水平擴展。
它增加了應用程式的吞吐量並改善了延遲。

##### Disadvantages of consistent hashing (一致性雜湊的缺點)
在環中隨機分配節點可能會導致分佈不均勻。

### Rebalance the partitions (重新平衡分區)
由於多種原因，查詢負載在節點之間可能不平衡，包括以下原因：

資料的分佈不相等。
單個分區上的負載過多。
查詢流量增加，我們需要新增更多節點來跟上。
我們可以應用以下策略來重新平衡分區。


#### Avoid hash mod n (避免 hash mod n)
通常，我們避免使用鍵的雜湊進行分區 (我們之前使用這種方案簡單地解釋了雜湊的概念)。在 hash mod n 的情況下，新增或刪除節點的問題在於每個節點的分區號都會發生變化，並且大量資料會移動。例如，假設我們有 hash(key)=1235。如果開始時有五個節點，則鍵將在節點 1 上 (1235 mod 5 = 0)。現在，如果新增一個新節點，則鍵必須移動到節點 6 (1235 mod 6 = 5)，依此類推。將鍵從一個節點移動到另一個節點使得重新平衡變得昂貴。

#### Fixed number of partitions (固定數量的分區)
在這種方法中，要建立的分區數量在我們設定資料庫時固定。我們建立比節點數量多的分區，並將這些分區分配給節點。因此，當向系統新增新節點時，它可以從現有節點中獲取幾個分區，直到分區被平均分割。

這種方法有一個缺點。由於所有分區都包含總資料的一小部分，因此每個分區的大小隨著叢集中總資料量的增加而增長。如果分區非常小，它將導致過多的開銷，因為我們可能必須製作大量的小型分區，每個分區都會花費我們一些開銷。如果分區非常大，重新平衡節點和從節點故障中恢復將是昂貴的。選擇正確的分區數量非常重要。Elasticsearch、Riak 等使用了固定數量的分區。

#### Dynamic partitioning (動態分區)
在這種方法中，當分區的大小達到閾值時，它會平均拆分為兩個分區。兩個拆分分區之一分配給一個節點，另一個分配給另一個節點。這樣，負載被平均分配。分區的數量適應總體資料量，這是動態分區的一個優點。

然而，這種方法有一個缺點。在服務讀取和寫入時應用動態重新平衡很困難。HBase 和 MongoDB 使用這種方法。

#### Partition proportionally to nodes (按節點比例分區)
在這種方法中，分區的數量與節點的數量成正比，這意味著每個節點都有固定的分區。在早期的方法中，分區的數量取決於資料集的大小。這裡情況並非如此。雖然節點數量保持不變，但每個分區的大小會根據資料集大小而增加。然而，隨著節點數量的增加，分區會縮小。當新節點進入網路時，它會隨機拆分一定數量的當前分區，然後取拆分的一半，留下另一半。這可能導致不公平的拆分。Cassandra 和 Ketama 使用這種方法。

問 (Question)
誰執行重新平衡？是自動還是手動？

答 (Answer)
有兩種執行重新平衡的方法：自動和手動。在自動重新平衡中，沒有管理員。系統決定何時執行分區以及何時將資料從一個節點移動到另一個節點。

在手動重新平衡中，管理員決定何時以及如何執行分區。組織根據自己的需要執行重新平衡。有些使用自動重新平衡，有些使用手動。

```
### Partitioning and secondary indexes (分區和二級索引)
我們已經討論了鍵值資料模型分區方案，其中記錄是用主鍵檢索的。但是如果我們必須通過二級索引存取記錄怎麼辦？二級索引是不由主鍵識別的記錄，而只是搜尋某些值的一種方式。例如，上面的水平分區圖示包含客戶表，搜尋具有相同建立年份的所有客戶。

我們可以通過以下方式對二級索引進行分區。

#### Partition secondary indexes by document (按文件分區二級索引)
在這種索引方法中，每個分區都是完全獨立的。每個分區都有其二級索引，僅覆蓋該分區中的文件。它不關心其他分區中保存的資料。如果我們想向我們的資料庫寫入任何內容，我們只需要處理包含我們要寫入的文件 ID 的分區。它也被稱為本地索引 (local index)。在下面的圖示中，有三個分區，每個分區都有自己的標識和資料。如果我們想獲取名為 John 的所有客戶 ID，我們必需向所有分區請求。

然而，這種類型的二級索引查詢可能很昂貴。由於受到效能不佳分區延遲的限制，讀取查詢延遲可能會增加。

[按文件分區二級索引](./partition1.jpg)

#### Partition secondary indexes by the term (按術語分區二級索引)
我們可以為包含來自所有分區資料的二級術語建立全域索引 (global index)，而不是為每個分區建立二級索引 (本地索引)。

在下面的圖示中，我們在 name (我們正在分區的術語) 上建立索引，並將所有 name 索引儲存在單獨的節點上。為了獲取名為 John 的所有客戶的 cust_id，我們必須確定我們的術語索引位於何處。索引 0 包含所有名稱以“A”到“M”開頭的客戶。索引 1 包括所有名稱以“N”到“Z”開頭的客戶。因為 John 位於索引 0 中，所以我們從索引 0 獲取名為 John 的 cust_id 列表。

按術語分區二級索引比按文件分區二級索引更具讀取效率。這是因為它只存取包含該術語的分區。然而，這種方法中的單個寫入會影響多個分區，使得該方法寫入密集且複雜。

## Request routing (請求路由)
我們已經學會了如何對資料進行分區。然而，這裡出現了一個問題：客戶端在發出請求時如何知道要連接到哪個節點？重新平衡後，分區對節點的分配會發生變化。如果我們想讀取特定的鍵，我們如何知道我們需要連接哪個 IP 地址來讀取？

這個問題也被稱為服務發現 (service discovery)。以下是針對此問題的一些方法：

允許客戶端請求網路中的任何節點。如果該節點不包含請求的資料，它將該請求轉發給確實包含相關資料的節點。

第二種方法包含一個路由層。所有請求首先轉發到路由層，它決定連接哪個節點以滿足請求。

客戶端已經擁有與分區相關的資訊以及哪個分區連接到哪個節點。因此，他們可以直接聯繫包含他們所需資料的節點。
```

在所有這些方法中，主要挑戰是確定這些組件如何知道節點分區的更新。

為了跟蹤叢集中的更改，許多分散式資料系統需要像 ZooKeeper 這樣的單獨管理伺服器。ZooKeeper 跟蹤網路中的所有映射，並且每個節點都連接到 ZooKeeper 以獲取資訊。每當分區發生變化，或者新增或刪除節點時，ZooKeeper 都會更新並通知路由層有關更改的資訊。HBase、Kafka 和 SolrCloud 使用 ZooKeeper。

## Conclusion (結論)
對於所有當前的分散式系統，分區已成為標準協定。因為系統包含越來越多的資料，所以對資料進行分區是有意義的，因為它可以加速寫入和讀取。它提高了系統的可用性、可擴展性和效能。
