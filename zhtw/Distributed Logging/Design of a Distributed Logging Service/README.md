# Design of a Distributed Logging Service (分佈式日誌服務的設計)
如果是現在，我們將設計分佈式日誌系統。我們的日誌系統應該記錄所有的活動或消息 (我們不會在我們的設計中加入採樣能力)。

## Requirements (需求)
讓我們列出設計分佈式日誌系統的需求：

### Functional requirements (功能需求)
我們系統的功能需求如下：

- **Writing logs (寫入日誌)**：分佈式系統的服務必須能夠寫入日誌系統。
- **Searchable logs (可搜索的日誌)**：系統應該很容易找到日誌。同樣，從端到端的應用程式流程也應該很容易。
- **Storing logging (存儲日誌)**：日誌應駐留在分佈式存儲中以便於訪問。
- **Centralized logging visualizer (集中式日誌可視化器)**：系統應提供全球分離服務的統一視圖。

### Non-functional requirements (非功能需求)
我們系統的非功能需求如下：

- **Low latency (低延遲)**：日誌記錄是一種 I/O 密集型操作，通常比 CPU 操作慢得多。我們需要設計系統，使日誌記錄不在應用程式的關鍵路徑上。
- **Scalability (可擴展性)**：我們希望我們的日誌系統具有可擴展性。它應該能夠處理隨時間增加的日誌數量和不斷增長的並發使用者數量。
- **Availability (可用性)**：日誌系統應該具有高可用性來記錄資料。

## Building blocks we will use (我們將使用的構建模塊)
分佈式日誌系統的設計將利用以下構建模塊：

- **Pub-sub system (發布-訂閱系統)**：我們將使用發布-訂閱系統來處理巨大的日誌大小。
- **Distributed search (分佈式搜索)**：我們將使用分佈式搜索來有效地查詢日誌。

## API design (API 設計)
此問題的 API 設計如下：

**Write a message (寫入消息)**

執行寫入的 API 調用應如下所示：
```
write(unique_ID, message_to_be_logged)
```
Parameter (參數)        Description (描述)

unique_ID               它是一個包含 application-id、service-id 和時間戳的數字 ID。

message_to_be_logged    這是針對唯一鍵存儲的日誌消息。
```

**Search log (搜索日誌)**

搜索資料的 API 調用應如下所示：
```
searching(keyword)
```
此調用會返回包含關鍵字的日誌列表。

Parameter (參數) Description (描述)

keyword         它用於查找包含關鍵字的日誌。
```

## Initial design (初始設計)
在分佈式系統中，全球各地的客戶端通過請求不同服務節點的服務來生成事件。節點在處理每個請求時生成日誌。這些日誌積累在各自的節點上。

除了構建模塊之外，讓我們列出我們系統的主要組件：

- **Log accumulator (日誌累積器)**：從每個節點收集日誌並將其轉儲到存儲中的代理。因此，如果我們想知道某個特定事件，我們不需要訪問每個節點，我們可以從我們的存儲中獲取它們。
- **Storage (存儲)**：累積後需要將日誌存儲在某處。我們將選擇 blob 存儲來保存我們的日誌。
- **Log indexer (日誌索引器)**：不斷增長的日誌文件數量影響了搜索能力。日誌索引器將使用分佈式搜索來有效地進行搜索。
- **Visualizer (可視化器)**：可視化器用於提供所有日誌的統一視圖。

## Logging at various levels (各級日誌記錄)
讓我們探討日誌系統如何在各個級別工作。

### In a server (在伺服器中)
在本節中，我們將了解屬於不同應用程式的各種服務如何登錄伺服器。

讓我們考慮一種情況，我們在伺服器上有多個不同的應用程式，例如 App 1、App 2 等。每個應用程式也運行著各種微服務。例如，電子商務應用程式可以同時運行驗證使用者、獲取購物車等服務。每個服務都會生成日誌。我們使用帶有 application-id、service-id 及其時間戳的 ID 來唯一標識多個應用程式的各種服務。時間戳可以幫助我們確定事件的因果關係。

每個服務都會將其資料推送到日誌累積器服務。它負責這些操作：
- Receiving the logs. (接收日誌。)
- Storing the logs locally. (本地存儲日誌。)
- Pushing the logs to a pub-sub system. (將日誌推送到發布-訂閱系統。)

[在伺服器中](./in_a_server)

我們應該注意，在記錄大量消息的過程中資料可能會丟失。在使用者感知的延遲和日誌資料持久化的保證之間存在權衡。為了降低延遲，日誌服務通常將資料保存在 RAM 中並異步持久化它們。此外，我們可以通過添加冗餘日誌累積器來處理不斷增長的並發使用者，從而最大限度地減少資料丟失。

```
Question
問題
當我們將服務託管在多租戶雲 (如 AWS) 上時，與組織擁有基礎設施的獨家控制權 (如 Facebook) 時相比，日誌記錄會發生什麼變化，特別是在日誌方面？

Answer
答案
安全性可能是多租戶和單租戶設置之間不同的一個方面。當我們加密所有日誌並端到端地保護日誌服務時，它不是免費的，並且會帶來性能損失。此外，多租戶設置需要嚴格分離日誌，而在單租戶設置下，我們可以提高存儲和處理利用率。

讓我們以 Meta 的 Facebook 為例。他們有數百萬台生成日誌的機器，日誌的大小可能每小時幾 PB。因此，每台機器都將其日誌推送到名為 Scribe 的發布-訂閱系統。Scribe 將資料保留幾天，其他各種系統處理駐留在 Scribe 中的資訊。他們還將日誌存儲在分佈式存儲中。管理日誌可以是特定於應用程式的。

另一方面，對於多租戶，我們每個租戶 (或每個應用程式) 需要一個單獨的發布-訂閱實例，以嚴格分離日誌。
```

```
注意：對於銀行和金融應用程式等應用程式，日誌必須非常安全，以便黑客無法竊取資料。通常的做法是加密資料並記錄。這樣，沒人能夠使用日誌中的資料解密加密資訊。
```

### At datacenter level (在資料中心級別)
資料中心中的所有伺服器都將日誌推送到發布-訂閱系統。由於我們使用水平可擴展的發布-訂閱系統，因此可以管理大量日誌。我們可以在每個資料中心使用多個發布-訂閱實例。它使我們的系統具有可擴展性，我們可以避免瓶頸。然後，發布-訂閱系統將資料推送到 blob 存儲。

[日誌累積器將資料發送到發布-訂閱系統](./datacenter.jpg)

資料不會永遠駐留在發布-訂閱中，並且在存儲到歸檔存儲之前幾天後會被刪除。但是，我們可以利用發布-訂閱系統中可用的資料。以下服務將處理發布-訂閱資料：

- **Filterer (過濾器)**：它識別應用程式並將日誌存儲在為該應用程式保留的 blob 存儲中，因為我們不想混合兩個不同應用程式的日誌。

- **Error aggregator (錯誤聚合器)**：盡快識別錯誤至關重要。我們使用一種服務，該服務從發布-訂閱系統中獲取錯誤消息並通知相應的客戶端。它省去了我們搜索日誌的麻煩。

- **Alert aggregator (警報聚合器)**：警報也很重要。因此，儘早意識到它們很重要。此服務識別警報，如果遇到致命錯誤，則通知相關利益相關者，或向監控工具發送消息。

```
Question
問題
我們早些時候了解到，對大型服務的簡單使用者級 API 調用可能涉及數百個內部微服務和數千個節點。我們如何將一個請求的日誌端到端地拼接在一起，並保持因果關係完整？

Answer
答案
大多數複雜的服務都使用前端伺服器來處理最終使用者的請求。收到請求後，前端伺服器可以使用定序器獲取唯一標識符。此唯一標識符將附加到所有扇出的服務。系統中任何地方生成的每個日誌消息也會發出唯一標識符。

稍後，我們可以根據唯一標識符過濾日誌 (或預處理它)。在此步驟中，我們能夠針對唯一請求收集跨微服務的所有日誌。在定序器構建模塊中，我們討論了我們可以獲取維持發生前因果關係的唯一標識符。這種標識符具有這樣的屬性：如果 ID 1 小於 ID 2，則 ID 1 表示發生在 ID 2 之前的時間。現在，每個日誌項都可以使用時間戳，我們可以按升序對特定請求的日誌條目進行排序。

按時間順序 (或因果) 順序正確排序日誌可簡化日誌分析。
```

## Conclusion (結論)
- 我們了解了日誌記錄對於理解分佈式系統中的事件流是多麼重要。它通過引導我們找到問題的根本原因來幫助減少平均修復時間 (MTTR)。

- 日誌記錄是一項 I/O 密集型操作，耗時且緩慢。必須小心處理它，不要影響其他服務執行的關鍵路徑。

- 日誌記錄對於監控至關重要，因為從日誌中獲取的資料有助於監控應用程式的運行狀況。(警報和錯誤聚合器用於此目的。)
