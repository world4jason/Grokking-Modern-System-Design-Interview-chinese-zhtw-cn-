# High-level Design of Sharded Counters (分片計數器的高層設計)

## High-level solution sketch (高層解決方案草圖)
管理數百萬個推文點贊需要許多在許多節點上運行的計數器。為了管理這些計數器，我們需要一個高效的系統，隨著使用者數量的增長，該系統可以提供高性能和可擴展性。

當 Twitter 上的一條推文獲得一百萬個讚，並且應用程式伺服器針對每個讚收到寫入請求以增加相關計數器時，會發生什麼？這些數百萬個請求最終會在隊列中序列化以實現資料一致性。這種序列化是處理並發活動的一種方式，但代價是增加了延遲。實時應用程式希望通過為最終使用者提供盡可能低的延遲來保持高體驗質量。

讓我們看下面的插圖來理解這個問題：

[名人與普通人的推文](./twitter.jpg)

名人發布的每條推文只有一個計數器不足以處理數百萬使用者。這個問題的解決方案是分片計數器，也稱為分佈式計數器，其中每個計數器根據需要具有指定數量的分片。這些分片在不同的計算單元上並行運行。我們可以通過平衡跨分片的數百萬個寫入請求來提高性能並減少爭用。

首先，當使用者點贊該推文時，寫入請求將轉發到指定的推文計數器。然後，系統選擇指定推文計數器的可用分片來增加點贊數。讓我們看下面的插圖來了解具有指定分片的分片計數器：

[計數器及其分片在不同的計算單元上工作](./counters.jpg)

在上圖中，每個計數器的分片總數為 (N+1)。我們將根據需要使用適當的 N 值。讓我們討論一個例子，以了解分片計數器如何處理單個帖子的數百萬個寫入和讀取請求。

假設一個擁有數百萬訂閱者的著名 YouTube 頻道上傳了一個新視頻。伺服器收到來自全球使用者的視頻觀看寫入請求的爆發。首先，為新上傳的視頻啟動一個新計數器。伺服器將請求轉發到相應的計數器，我們的系統隨機選擇分片並更新分片值，初始值為零。相反，當伺服器收到讀取請求時，它會將計數器所有分片的值相加以獲得當前總數。

我們可以在任何需要可擴展計數的場景 (例如 Facebook 帖子和 YouTube 視頻) 中使用分片計數器。

## API design for sharded counters (分片計數器的 API 設計)
本節討論將為分片計數器調用的 API。我們的 API 設計將幫助我們了解分片計數器與其調用者之間的交互。為了使我們的討論具體化，我們將在 Twitter 的背景下討論每個 API 函數。讓我們為以下每個功能開發 API：

- **Create counter (創建計數器)**
- **Write counter (寫入計數器)**
- **Read counter (讀取計數器)**

雖然上面的 API 函數列表並不詳盡，但它們代表了一些最重要的函數。

### Create counter (創建計數器)
`createCounter` API 初始化一個分佈式計數器以供使用。`createCounter` API 如下所示：

```
createCounter(counter_id, number_of_shards)
```

Parameter (參數)            Description (描述)

                           它表示計數器的唯一 ID。此 API 的調用者可以使用定序器獲取唯一標識符。有關更多詳細資訊，請參見定序器構建塊課程。

                           它指定計數器的分片數量。
```

我們可以使用適當的資料存儲來保存我們的元資料，其中包括計數器標識符、它們的分片數量以及分片到物理機器的映射。

讓我們以 Twitter 為例來了解應用程式如何使用上述 API。當使用者在社交媒體上發布內容時使用 `createCounter` API。例如，如果使用者在 Twitter 上發布推文，應用程式伺服器將調用 `createCounter` API。content_type 參數是系統用於決定需要創建的計數器數量的帖子類型。例如，僅當推文包含視頻剪輯時，系統才需要觀看計數器。

為了找到 `number_of_shards` 的適當值，我們可以使用以下啟發式方法：

- `followers_count` 參數表示發布推文的使用者的粉絲數。
- `post_type` 參數指定帖子是公開的還是受保護的。受保護的推文僅供關注者使用，在這種情況下，我們可以更好地預測分片數量。

### Write counter (寫入計數器)
當我們想要增加 (或減少) 計數器時使用 `writeCounter` API。實際上，計數器的特定分片被增加或減少，我們的服務根據多個因素做出該決定，這將在後面討論。`writeCounter` API 如下所示：

```
writeCounter(counter_id, action_type)
```

Parameter (參數)         Description (描述)

                        它是唯一標識符 (在創建計數器時提供)。

                        它指定預期的操作 (增加或減少計數器的值)。我們從資料存儲中提取有關計數器的所需資訊。
```
在我們的 Twitter 示例中，當使用者對他人的帖子或自己的帖子採取行動 (通過點贊、回覆等) 時，使用 `writeCounter` API。

### Read counter (讀取計數器)
當我們想知道計數器的當前值時使用 `readCounter` API。我們的系統從資料存儲中獲取適當的資訊以從所有分片收集值。`readCounter` API 如下所示：

```
readCounter(counter_id)
```

Parameter (參數)       Description (描述)

                      它是唯一標識符 (在創建計數器時提供)。
                      對於 Twitter，counter_id 將根據以下指標決定：
                      tweet_id 指定為其生成請求的推文的唯一 ID。我們可以使用 tweet_id 來獲取特徵的所有計數器 (點贊、轉發等) 的 counter_id。
```
當使用者想查看特定推文的點贊數或觀看次數時，會調用 `readCounter` API。通常，當使用者想查看他們的主頁或使用者時間軸時，另一個 API 會觸發此 API。
