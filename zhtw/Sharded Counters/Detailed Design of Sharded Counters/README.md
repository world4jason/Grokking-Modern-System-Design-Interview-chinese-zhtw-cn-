# Detailed Design of Sharded Counters (分片計數器的詳細設計)

## Detailed design (詳細設計)
我們現在將詳細討論分片計數器的這三個主要功能——創建、寫入和讀取。我們將以 Twitter 為例來回答許多重要問題。這些問題包括：

- 針對每個新推文應該創建多少個分片？
- 如何為特定推文增加分片值？
- 當來自最終使用者的讀取請求到來時，系統會發生什麼？

### Sharded counter creation (分片計數器的創建)
正如我們之前討論的，當使用者在 Twitter 上發布推文時，會調用 `createCounter` API。系統為使用者每個新創建的帖子創建多個計數器。以下是針對每個新推文創建的主要計數器列表：

- Tweet like counter (推文點贊計數器)
- Tweet reply counter (推文回覆計數器)
- Tweet retweet counter (推文轉發計數器)
- Tweet view counter in case a tweet contains video (如果推文包含視頻，則為推文觀看計數器)

現在，問題是系統如何決定每個計數器中的分片數量？分片數量對於良好的性能至關重要。如果特定寫入工作負載的分片計數很小，我們將面臨高寫入爭用，從而導致寫入緩慢。另一方面，如果特定寫入配置文件的分片計數太高，我們會在讀取操作上遇到更高的開銷。讀取速度較慢的原因是從不同分片收集值，這些分片可能駐留在地理分佈的資料中心內的不同節點上。計數器值的讀取成本隨著分片數量的增加而線性上升，因為相應計數器的所有分片的值都被相加。由於請求增加，當我們添加新分片時，寫入會線性擴展。因此，在使寫入快速與讀取性能之間存在權衡。我們將在稍後討論如何提高讀取性能。

關於分片數量的決定取決於許多因素，這些因素共同試圖預測短期內特定計數器的寫入負載。對於推文，這些因素包括粉絲數。擁有數百萬粉絲的使用者的推文比在 Twitter 上擁有很少粉絲的使用者獲得更多的分片，因為他們的推文可能會獲得很多 (通常是數百萬) 個贊。有時，名人推文包含一個或多個主題標籤。系統還為此主題標籤創建分片計數器，因為它很有可能被標記為趨勢。

許多以人為中心的活動通常具有長尾活動模式，其中許多人集中在相對較小的一組活動上。也許縮短的注意力持續時間可能在這裡起作用。這意味著一段時間後，點讚的熱潮將平息，我們現在可能不需要像以前那樣多的分片用於計數器。同樣，我們要未來寫入的初步預測可能會被證明是錯誤的，我們可能需要更多分片來處理寫入請求。我們需要我們的系統能夠根據當前需求動態擴展或縮小分片數量。

我們需要監控所有分片的寫入負載，以便適當地將請求路由到特定分片，可能使用負載平衡器。這種反饋機制還可以幫助我們決定何時關閉計數器的某些分片以及何時添加額外的分片。這個過程不僅為最終使用者提供了良好的性能，而且還以接近最佳水平利用了我們的資源。

```
Question
當一個只有少數粉絲的使用者在 Twitter 上發布的帖子病毒式傳播時會發生什麼？

Answer
系統需要檢測計數器意外開始獲得非常高寫入流量的此類情況。我們將動態增加受影響計數器的分片數量以緩解這種情況。
```

### Burst of writes requests (寫入請求的爆發)
正如我們之前提到的，數百萬使用者與我們示例名人的推文互動，最終向系統發送大量寫入請求。系統將每個寫入請求分配給特定推文的指定計數器的可用分片。系統如何選擇在不同計算單元 (節點) 上運行的這些分片來分配寫入請求？我們可以用三種方法來做到這一點：

#### Round-robin selection (輪詢選擇)
解決上述問題的一種方法是使用分片的輪詢選擇。例如，假設分片數量為 100。系統從 shard_1 開始，然後是 shard_2，並持續到達到 shard_100。通常，輪詢工作分配要麼超載要麼未充分利用資源，因為調度是在不考慮當前負載條件的情況下完成的。但是，如果每個請求都相似 (並且大致需要相同的時間來服務)，則可以使用輪詢方法，並且因其簡單性而具有吸引力。

在下面的插圖中，我們假設使用者請求首先由負載平衡器分發到合適的伺服器。然後，每個這樣的伺服器都使用自己的輪詢調度來使用分片：

[輪詢技術](./rr)

#### Random selection (隨機選擇)
另一種簡單的方法可以是均勻隨機地選擇一個分片進行寫入。輪詢選擇和隨機選擇的挑戰在於節點 (分片託管的位置) 上可變的負載變化。很難在可用分片上適當地分配負載。節點上的負載可變性很常見，因為物理節點通常用於多種目的。

#### Metrics-based selection (基於指標的選擇)
第三種方法是基於特定指標的分片選擇。例如，專用節點 (負載平衡器) 通過讀取分片狀態來管理分片的選擇。以下幻燈片介紹瞭如何創建分片計數器：

### Manage read requests (管理讀取請求)
當使用者發送讀取請求時，系統將聚合指定計數器所有分片的值，以返回特徵 (例如點贊或回覆) 的總計數。在每個讀取請求上累積所有分片的值將導致低讀取吞吐量和高讀取延遲。

系統何時匯總所有分片值的決定也非常關鍵。如果有高寫入流量和讀取流量，幾乎不可能獲得真實的當前值，因為當我們向客戶端報告讀取值時，它已經改變了。因此，定期讀取計數器的所有分片並將其緩存應該可以滿足大多數用例。通過減少累積週期，我們可以提高讀取值的準確性。

## Using sharded counters for the Top K problem (將分片計數器用於 Top K 問題)
本節將討論如何使用分片計數器來解決稱為 Top K 問題的現實世界問題。我們將繼續使用實時應用程式 Twitter 作為示例，其中計算趨勢是 Twitter 的 Top K 問題之一。這裡，K 代表熱門趨勢的數量。許多使用者在他們的推文中使用各種主題標籤。管理數百萬個主題標籤的計數以根據其位置在單個使用者的趨勢時間軸中顯示它們是一個巨大的挑戰。

分片計數器是上述問題的關鍵。如前所述，在 Twitter 上，系統為每個主題標籤創建計數器，並根據在推文中使用該主題標籤的使用者的粉絲決定分片計數。當 Twitter 上的使用者再次在他們的推文中使用相同的主題標籤時，計數將維持在首次使用該主題標籤時創建的同一計數器。

Twitter 主要根據特定主題標籤在使用者所在地區的受歡迎程度來顯示趨勢。Twitter 將使用全局主題標籤計數器為每個討論的指標維護一個單獨的計數器。讓我們討論下面的每個指標：

- 區域主題標籤計數表示在特定地理區域內使用相同主題標籤的推文數量。例如，來自紐約市的數千條帶有相同標籤的推文表明，紐約地區的使用者可能會在他們的趨勢時間軸中看到此主題標籤。
- 時間窗口表示發布帶有特定標籤的推文的時間量。

[系統計算指定主題標籤的 24 小時計數](./topk.jpg)

## Placement of sharded counters (分片計數器的放置)
一個重要的問題是我們應該將分片計數器放置在哪裡。它們應該駐留在與應用程式伺服器相同的節點上，資料中心的各個獨立節點中，還是靠近最終使用者的網絡邊緣的 CDN 節點中？這個問題的確切答案取決於我們的具體用例。對於 Twitter，我們可以通過將分片計數器放置在靠近使用者的地方來計算計數，這也有助於有效地處理重擊者和 Top K 問題。

```
Question
我們應該在累積其值之前鎖定計數器的所有分片嗎？

Answer
不。讀取可以與寫入並發發生，而無需跨分片鎖。這個鎖會嚴重降低寫入性能，這是我們使用分片計數器的最初原因。在寬鬆一致性模型下，計數器的值可能無法反映確切的當前值，因此無需跨所有分片同時進行讀取鎖定。

但是，根據具體用例，當讀取頻率非常低時，可能會使用這種機制。
```

讀取可以將計數器值存儲在適當的資料存儲中，並依靠各自的資料存儲來實現讀取可擴展性。Cassandra 存儲可用於維護指定區域中使用者的觀看、點贊、評論和更多計數。這些計數表示特定計數器的所有分片的最後計算總和。

當使用者生成時間軸時，讀取請求被轉發到最近的伺服器，然後可以使用存儲中的持久值進行響應。此存儲還有助於顯示區域性的 Top K 趨勢。本地 Top K 趨勢列表發送到應用程式伺服器，然後應用程式伺服器對所有列表進行排序以製作全局 Top K 趨勢列表。最終，應用程式伺服器將所有計數器的詳細資訊發送到緩存。

我們還需要用於分片計數器的存儲，它將所有關於它們的資訊與其元資料一起存儲。Redis 或 Memcache 伺服器可以在這裡發揮至關重要的作用。例如，每條推文的唯一 ID 可以成為鍵，此鍵的值可以是計數器 ID 或計數器 ID 列表 (例如點贊計數器、回覆計數器等)。此外，每個計數器 ID 都有自己的鍵值存儲，其中計數器 (例如點贊計數器) ID 是鍵，值是分配的分片列表。

識別相關計數器並將所有寫入請求映射到分片計數器中適當計數器的工作可以並行完成。我們將所有寫入請求映射到適當的計數器，然後每個計數器根據某些指標隨機選擇一個分片進行遞增和遞減。相反，我們定期減少以聚合特定計數器所有分片的值。然後，這些計數器值可以存儲在 Cassandra 存儲中。下面的幻燈片有助於說明這些點：

## Evaluation of the sharded counters (分片計數器的評估)
本節將評估分片計數器，並解釋分片計數器將如何通過提供高可用性和可擴展性來提高性能。

### Availability (可用性)
任何特徵 (如點贊、觀看或回覆) 的單個計數器都有很高的單點故障風險。分片計數器通過為特定計數器運行許多分片來消除單點故障。即使某些分片宕機或發生故障，系統仍保持可用。通過這種方式，分片計數器提供了高可用性。

### Scalability (可擴展性)
分片計數器允許根據需要進行高水平擴展。在額外節點上運行的分片可以輕鬆添加到系統中，以擴大我們的操作能力。最終，這些額外的分片也提高了系統的性能。

### Reliability (可靠性)
分片計數器的另一個主要目的是通過將每個寫入請求映射到特定分片來減少大量寫入請求。每個寫入請求在到來時都會被處理，並且沒有請求在隊列中等待。因此，命中率增加，系統的可靠性也增加。此外，系統定期將計算的計數保存在穩定的存儲中——在這種情況下是 Cassandra。

## Conclusion (結論)
如今，分片計數器是提高巨型服務整體性能的關鍵參與者。它們提供高可擴展性、可用性和可靠性。分片計數器解決了重大問題，包括重擊者和 Top K 問題，這些問題在大型應用程式中非常常見。
