# Design of a Newsfeed System (動態消息系統的設計)
讓我們根據上一課討論的需求討論動態消息系統的高層和詳細設計。

## High-level design of a newsfeed system (動態消息系統的高層設計)
動態消息系統主要負責以下兩項任務：

1. **Feed generation (動態消息生成)**：動態消息是根據某種排名機制聚合朋友和追蹤者的貼文 (或動態項目) 生成的。

2. **Feed publishing (動態消息發布)**：發布動態時，相關資料將寫入快取和資料庫。這些資料可以是文字或任何媒體內容。包含來自朋友和追蹤者資料的貼文將填充到使用者的動態消息中。

[動態消息系統的高層設計](./hld.jpg)

讓我們討論高層設計中顯示的主要組件：

1. **User(s) (使用者)**：使用者可以發布帶有一些內容的貼文或請求他們的動態消息。

2. **Load balancer (負載平衡器)**：它將流量重定向到其中一個 Web 伺服器。

3. **Web servers (Web 伺服器)**：Web 伺服器封裝了後端服務，並作為使用者和各種服務之間的中間層。除了強制執行身份驗證和速率限制外，Web 伺服器還負責將流量重定向到其他後端服務。

4. **Notification service (通知服務)**：每當朋友或關注者有新貼文時，它會通知動態消息生成服務，並發送推播通知。

5. **Newsfeed generation service (動態消息生成服務)**：此服務從使用者的追蹤者/朋友的貼文中生成動態消息，並將其保存在動態消息快取中。

6. **Newsfeed publishing service (動態消息發布服務)**：此服務負責將動態消息從動態消息快取發布到使用者的時間線。它還從 blob 儲存中附加媒體內容的縮略圖並將其連結到為使用者準備的動態消息。

7. **Post-service (貼文服務)**：每當使用者請求建立貼文時，都會調用貼文服務，並將建立的貼文儲存在貼文資料庫和相應的快取中。貼文中的媒體內容儲存在 blob 儲存中。

### API design (API 設計)
API 是客戶端與伺服器通訊的主要方式。通常，動態消息 API 是基於 HTTP 的，允許客戶端執行操作，包括發布狀態、檢索動態消息、新增朋友等。我們的目標是生成和獲取使用者的動態消息；因此，以下 API 至關重要：

#### Generate user’s newsfeed (生成使用者動態消息)
以下 API 用於生成使用者的動態消息：
```
generateNewsfeed(user_id)
此 API 獲取使用者 ID，並確定其朋友和追蹤者。此 API 生成由多個貼文組成的動態消息。由於內部系統組件使用此 API，因此可以離線調用它以為使用者預生成動態消息。預生成的動態消息儲存在持久性儲存和關聯的快取中。

此 API 調用中使用以下參數：
Parameter (參數)    Description (描述)

user_id            為其生成動態消息的使用者的唯一標識。
```

#### Get user’s newsfeed (獲取使用者動態消息)
以下 API 用於獲取使用者的動態消息：
```
getNewsfeed(user_id, count)
getNewsfeed(.) API 調用返回一個由帖子列表組成的 JSON 物件。

此 API 使用以下參數：
Parameter (參數)    Description (描述)

user_id            系統將為其獲取動態消息的使用者的唯一標識。

count              每個請求將檢索的動態項目 (貼文) 數量。
```

## Storage schema (儲存模式)
動態消息系統的資料庫關係如下：

- **User (使用者)**：此關係包含有關使用者的資料。使用者也可以是其他使用者的追蹤者或朋友。

- **Entity (實體)**：此關係儲存與任何實體 (如頁面、群組等) 相關的資料。

- **Feed_item (動態項目)**：使用者建立的貼文資料儲存在此關係中。

- **Media (媒體)**：有關媒體內容的資訊儲存在此關係中。

## Detailed design (詳細設計)
讓我們詳細探討動態消息系統的設計。

如前所述，動態消息系統有兩個部分：動態消息發布和動態消息生成。因此，我們將從動態消息生成服務開始討論這兩個部分。

### The newsfeed generation service (動態消息生成服務)
動態消息是由來自用戶朋友、追蹤者和其他實體 (頁面和群組) 的聚合貼文 (或動態項目) 生成的。

在我們提出的設計中，動態消息生成服務負責生成動態消息。當 Web 伺服器收到來自使用者 (比如 Alice) 檢索動態消息的請求時，Web 伺服器要麼：

- 調用動態消息生成服務來生成動態，因為某些使用者不經常訪問該平台，因此他們的動態是根據請求生成的。
- 它獲取經常訪問平台的活躍使用者的預生成動態消息。
按順序執行以下步驟為 Alice 生成動態消息：

1. 動態消息生成服務從圖資料庫中檢索 Alice 關注的所有使用者和實體的 ID。
2. 當從圖資料庫中檢索 ID 後，下一步是從使用者快取中獲取其朋友 (追蹤者和實體) 的資訊，每當使用者資料庫更新/修改時，該快取都會定期更新。
3. 在此步驟中，服務從貼文快取中檢索這些 ID 的最新、最受歡迎和相關的貼文。這些是我們可能能夠在 Alice 的動態消息上顯示的貼文。
4. 排名服務根據貼文與 Alice 的相關性對其進行排名。這代表了 Alice 當前的動態消息。
5. 動態消息儲存在動態消息快取中，從中將前 N 個貼文發布到 Alice 的時間線。(發布過程將在下一節中詳細討論)。
6. 最後，每當 Alice 到達其時間線的末尾時，下一個前 N 個貼文將從動態消息快取中獲取到她的螢幕上。

Question (問題)
在快取中為每個使用者建立和儲存動態消息需要大量的記憶體 (上一節中的第 5 步)。有沒有辦法減少這種記憶體消耗？

Answer (答案)
一種節省記憶體的方法是在快取的表中僅儲存使用者與其相應貼文之間的映射，即 < Post_ID, User_ID>。在動態發布階段，系統將從貼文資料庫中檢索貼文，並為關注另一個擁有 User_ID 的使用者生成動態消息。

```
### The newsfeed publishing service (動態消息發布服務)
在此階段，動態消息是為使用者從他們各自的朋友、追蹤者和實體生成的，並以 <Post_ID, User_ID> 的形式儲存在動態消息快取中。

現在的問題是為 Alice 生成的動態消息將如何發布到她的時間線上？

動態消息發布服務從動態消息快取中獲取從貼文 ID 列表。從動態消息快取中獲取的資料是貼文和使用者 ID 的元組，即 <Post_ID, User_ID>。因此，有關貼文和使用者的完整資料是從使用者和貼文快取中檢索的，以建立完全構建的動態消息。

在最後一步中，完全構建的動態消息使用扇出 (fan-out) 方法之一發送給客戶端 (Alice)。流行的動態消息和媒體內容也儲存在 CDN 中以便快速檢索。

```
假設如果我們的服務一次收到數十億個請求，並且系統開始生成實時動態消息。這種情況將使大量使用者處於擱置狀態，並可能導致伺服器崩潰。為了避免這種情況，我們可以分配專用伺服器，持續對動態消息進行排名和生成，並將它們儲存在動態消息資料庫和記憶體中。因此，在收到使用者對新貼文的請求時，我們的系統將提供預生成的動態。
```

Question (問題)
當使用者建立新貼文時，朋友和追蹤者的動態消息如何更新？

Answer (答案)
當使用者 (比如 Bob) 建立新貼文時，它將儲存在貼文資料庫和快取中。在下一步中，動態消息生成服務為 Bob 的朋友和追蹤者生成動態消息，並更新動態消息快取。更新的動態消息將在下一次頁面/螢幕重新整理事件時交付給相應的使用者。
```

### The newsfeed ranking service (動態消息排名服務)
每當我們登入社交媒體帳戶時，我們經常會在動態消息的頂部看到相關且重要的貼文。這種排名涉及多種高級排名和推薦演算法。

在我們的設計中，動態消息排名服務由這些演算法組成，這些演算法基於各種特徵工作，例如使用者的過去歷史、按讚、不按讚、評論、點擊等等。這些演算法還執行以下功能：

- 選擇“候選”貼文顯示在動態消息中。
- 從候選貼文中消除包含錯誤資訊或點擊誘餌的貼文。
- 建立一個使用者經常互動的朋友列表。
- 選擇使用者花費更多時間的主題。
排名系統考慮上述所有點來預測使用者的相關和重要貼文。

[排名的動態消息儲存在快取伺服器中](./ranked_newsfeed.jpg)

### Posts ranking and newsfeed construction (貼文排名和動態消息構建)
貼文資料庫包含不同使用者發布的貼文。假設資料庫中有 5 個不同使用者發布的 10 個貼文。我們的目標是為關注這五個不同使用者的使用者 (例如 Bob) 在 10 個貼文中僅排名 4 個貼文。我們執行以下操作來對每個貼文進行排名並為 Bob 建立動態消息：

1. 從每個貼文中提取各種特徵，如按讚、評論、分享、類別、持續時間等。
2. 根據儲存在使用者資料庫中的 Bob 以前的歷史記錄，通過不同的排名和機器學習演算法計算每個貼文的相關性。
3. 分配相關性分數，例如從 1 到 5，其中 1 表示最不相關的貼文，5 表示高度相關的貼文。
4. 根據分配的分數從 10 個貼文中選擇前 4 個貼文。
5. 將前 4 個貼文組合起來，並按分配分數的降序呈現在 Bob 的時間線上。
下圖顯示了在 Bob 的時間線上發布的前 4 個貼文：

[基於相關性分數的前 4 個貼文組成的動態消息](./newsfeed_example.jpg)

使用各種機器學習和排名演算法進行動態消息排名是一項計算密集型任務。在我們的設計中，排名服務對貼文進行排名並構建動態消息。此服務由大數據處理系統組成，可能 利用圖形處理單元 (GPU) 和張量處理單元 (TPU) 等專用硬體。
注意：根據 Facebook 的說法：

“對於 Facebook 上的每個人，我們需要評估數千個特徵，以確定該人可能發現什麼最相關，從而預測每個人希望在他們的動態消息中看到什麼。”

這意味著我們需要巨大的計算能力和複雜的學習演算法來整合所有特徵，以便在相當短的時間內獲得高質量的動態消息。
