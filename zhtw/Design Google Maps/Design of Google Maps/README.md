# Design of Google Maps (Google Maps 的設計)
## High-level design (高層設計)
讓我們從地圖系統的高層設計開始。我們將討論分為兩部分：

1. 我們在設計中需要的組件。
2. 連接這些組件的工作流程。

### Components (組件)
我們將在設計中使用以下組件：

- **Location finder (位置查找器)**：位置查找器是一項用於查找使用者當前位置並將其顯示在地圖上的服務，因為我們不可能親自記住世界上每個地方的緯度和經度。

- **Route finder (路線查找器)**：對於剛到某個地方的人來說，因為不知道正確的路線，所以很難出行。路線查找器是一項用於查找兩個位置或點之間路徑的服務。

- **Navigator (導航器)**：通過路線查找器建議路線是不夠的。使用者可能會偏離最佳路徑。在這種情況下，將使用導航器服務。該服務跟蹤使用者的旅程，並在使用者偏離建議路線後立即向使用者發送更新的指示和通知。

- **GPS/Wi-Fi/Cellular technology (GPS/Wi-Fi/蜂窩技術)**：這些是用於查找使用者地面位置的技術。

- **Distributed search (分散式搜尋)**：為了將地名轉換為緯度/經度值，我們需要在來源和目標欄位後面有一個轉換系統。分散式搜尋維護由地名及其到緯度和經度的映射組成的索引。使用此服務搜尋使用者輸入的關鍵字以在地圖上查找位置。

- **Area search service (區域搜尋服務)**：區域搜尋服務在分散式搜尋和圖處理服務之間進行協調，以根據使用者查詢獲得最短路徑。區域搜尋服務將請求分散式搜尋以獲取地圖上起點和終點的位置。然後，它將使用圖處理服務來找到從起點到終點的最佳路徑。

- **Graph processing service (圖處理服務)**：從一個地方到另一個地方可能有多條路徑。圖處理服務根據跨越起點和終點的區域在較短的圖上運行最短路徑演算法，並幫助我們確定要遵循的路徑。

- **Database (資料庫)**：正如在上一課中所討論的，我們有來自各種來源的道路資料，以圖的形式儲存。我們將把這些資料映射到資料庫以開發道路網路圖。我們正在使用像 DataStax Graph 這樣的圖資料庫來儲存我們設計的圖。

- **Pub-sub system (發布-訂閱系統)**：使用者可能會偏離第一條建議的路徑。在這種情況下，他們將需要有關通往目的地的新路徑的資訊。發布-訂閱是一個系統，它偵聽來自服務的各種事件並相應地觸發另一個服務。例如，當使用者偏離建議的路徑時，它會 ping 區域搜尋服務以查找從使用者當前位置到其目的地點的新路線。它還從導航器收集不同使用者的位置資料流。以後可以處理這些資料以查找不同時間不同道路上的交通模式。我們將在設計中使用 Kafka 作為發布-訂閱系統。

- **Third-party road data (第三方道路資料)**：如果我們沒有道路網路資料，我們如何建立地圖系統？我們需要從第三方資源收集道路資料並對收集到的資料進行預處理，使其成為可以用於構建圖的單一格式。

- **Graph building (圖形構建)**：我們將使用一項服務，該服務利用給定的資料 (從第三方資源或使用者那裡收集) 構建圖。

- **User (使用者)**：指使用地圖系統服務的人或程式。

- **Load balancer (負載平衡器)**：這是一個用於在不同伺服器和服務之間分配使用者請求的系統。

### Workflow (工作流程)
我們通過假設使用者必須在兩點之間旅行但不知道他們當前在位置或如何到達目的地來解釋工作流程。所以，讓我們看看地圖系統如何提供幫助。

對於本練習，我們假設有關道路網路和地圖的資料已經從第三方收集，並且圖已構建並儲存在圖資料庫中。
- 在地圖系統中，使用者必須輸入他們的起點和終點才能在兩者之間建立路徑。對於起始源點，使用者使用當前位置服務。

- 位置查找器通過與使用者保持持久連接來確定當前位置。使用者將使用 GPS、Wi-Fi 和蜂窩技術提供更新的位置。這將是使用者的源點。

- 對於目標點，使用者以文字格式輸入地址。在這裡使用我們的 Typeahead 服務是一個好主意，可以提供有用的建議並避免拼寫錯誤。

- 輸入起點和終點後，使用者請求最佳路徑。

- 使用者的路徑請求被轉發到路線查找器服務。

  - 路線查找器將請求轉發給帶有起點和終點的區域搜尋服務。

  - 區域搜尋服務使用分散式搜尋來查找起點和終點的緯度/經度。然後它計算地圖上跨越兩個 (起點和終點) 緯度/經度點的區域。
  
  - 找到區域後，區域搜尋服務要求圖處理服務根據區域處理部分圖以找到最佳路徑。
  
  - 圖處理服務從資料庫中獲取該指定區域內的邊和節點，找到最短路徑，並將其返回給路線查找器服務，該服務將最佳路徑與完成路線所需的距離和時間一起可視化。它還顯示使用者導航應遵循的步驟。

- 現在使用者可以在地圖上可視化最短路徑，他們也想獲得前往目的地的指示。指示請求由導航器處理。

- 導航器跟蹤使用者是否遵循它從路線查找器服務獲得的正確路徑。它會在使用者移動時在地圖上更新使用者的位置，並顯示在哪裡轉彎以及距離。如果使用者偏離路徑，它會生成一個事件，該事件被饋送到 Kafka。

- 收到導航器的事件後，Kafka 更新區域搜尋服務的訂閱主題，這反過來會重新計算最佳路徑並將其建議給使用者。導航器還向圖提供實時位置資料流，通過發布-訂閱系統構建它。稍後，這些資料可用於改進提供給使用者的路線建議。

## API design (API 設計)

讓我們看看地圖服務的不同 API。

**Show the user’s current location on the map (在地圖上顯示使用者的當前位置)**

currLocation 函式在地圖上顯示使用者的位置。
```
currLocation(location)
```

Parameter (參數)      Description (描述)

location             這描述了使用者位置是開啟還是關閉。此調用將在客戶端和伺服器之間建立持久連接，客戶端將定期向伺服器更新其當前位置。如果 location 為 false，服務會請求使用者開啟他們的位置。
```

**Find the optimal route (尋找最佳路線)**

findRoute 函式有助於找到兩點之間的最佳路線。
```
findRoute(source, destination, transport_type)
```

Parameter (參數)                  Description (描述)

source                           這是使用者想要開始旅程的地方 (文字格式)。

destination                      這是使用者想要結束旅程的地方 (文字格式)。

transport_type (optional)        這可以是自行車、汽車、飛機等。如果使用者未提供此參數，則預設交通類型設定為汽車。
```

**Get directions (獲取指示)**

directions 函式幫助我們以文字或聲音的形式獲取警報，指示我們下一步該在哪裡轉彎以及我們已經行駛了多遠。
```
directions(curr_location, steps)       
```

Parameter (參數)         Description (描述)

current_location        這是使用者在地圖上當前位置的緯度/經度值。

steps                   這是使用者為到達目的地應遵循的步驟。
