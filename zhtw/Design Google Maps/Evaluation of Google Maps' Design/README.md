# Evaluation of Google Maps' Design (Google Maps 設計的評估)
讓我們看看我們設計的系統將如何處理每秒數百萬次的查詢，確保快速的響應時間。

## Availability (可用性)
由於單個伺服器上託管的大型道路網路圖，我們遇到了以下問題：

- 我們無法處理使用者查詢，因為不可能將如此大的圖加載到記憶體中，導致系統對使用者不可用。
- 不可能在伺服器和每秒數百萬使用者之間建立持久的雙向連接 (用於導航)。
- 它也是一個單點故障。

我們通過將世界劃分為小段來解決上述問題。每個小段包含一個可以輕鬆加載到伺服器記憶體中的圖。通過段，我們完成了以下目標：

- 我們將每個段託管在單獨的伺服器上，減輕了加載大型全域圖的問題。
- 負載平衡器根據使用者的搜尋區域將請求負載分配給不同的段伺服器。它減輕了將負單放在單個伺服器上的問題，這曾影響系統的可用性。
- 我們沒有討論複製，但我們可以複製每個段，這將有助於處理作為單點故障的段伺服器，並將段的請求負載分配給副本。
注意：Google Maps 使用資料的延遲加載 (lazy loading)，這減少了系統負擔，從而提高了可用性。
```

Lazy loading (延遲加載) 是將資源或物件的加載或初始化推遲到需要它們的時候。它通過減少要加載的內容數量來減少初始加載時間，通過在需要時向使用者交付內容來節省頻寬，並通過僅渲染部分內容來保留伺服器和客戶端資源。因此，它提高了效能並節省了系統資源。

## Scalability (可擴展性)
我們針對大型道路網路擴展了我們的系統。可擴展性可以從兩個方面來看：

- 系統處理不斷增加的使用者請求量的能力。
- 系統處理更多資料 (段) 的能力。

我們將世界劃分為小段。每個段託管在分散式系統中的不同伺服器上。對不同路線的使用者請求由不同的段伺服器提供服務。通過這種方式，我們可以為數百萬使用者請求提供服務。

注意：如果我們有一個跨越整個道路網路的單個大圖，就不可能為數百萬使用者請求提供服務。加載和處理巨大圖形會出現記憶體問題。
我們還可以輕鬆新增更多段，因為我們不必更改整個圖。我們可以通過非均勻選擇段大小來進一步提高可擴展性——在連接密集的區域選擇較小的段大小，在郊區選擇較大的段。

## Smaller response times (更小的響應時間)
我們正在小段圖上運行使用者請求。處理數百個頂點的小子圖遠快於數百萬個頂點的圖。我們可以將處理後的子圖快取在主記憶體中，並快速響應使用者請求。這就是我們的系統如何在更短的時間內響應使用者的方式。

還有另一個方面有助於我們的系統快速響應，那就是將段資訊保留在鍵值儲存中。鍵值儲存有助於不同服務快速獲取所需資訊。

- 圖處理服務通過查詢鍵值儲存中的 segmentID 值來檢查起點和終點緯度/經度所在的相關段。
- 為了在不同段伺服器之間負載平衡使用者請求，將查詢鍵值儲存以獲取針對特定請求應在其上運行圖處理的段的 serverID。
```

## Conclusion (結論)
Google Maps 是世界上使用最廣泛的應用程式之一，使用者可以在其中找到兩個位置之間的最短路線。地圖系統使用圖資料結構對道路網路進行建模。為了找到路線，最短路徑演算法在圖上運行。我們已經看到了大型道路網路圖的可擴展性問題。我們通過將世界劃分為小段解決了這個問題。每個段由一個可以加載到記憶體中的小圖組成，以便快速查找路徑。我們還看到，通過分析實時位置資料可以改進預計到達時間。
